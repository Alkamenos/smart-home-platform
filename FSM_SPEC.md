# FSM — Конечные автоматы для принятия решений в платформе умного дома

**Версия:** 0.1.0 (черновик спецификации)
**Дата:** 2026-09-03
**Статус:** Проектирование

---

## 1. Мотивация и проблематика

### 1.1 Текущая модель: реактивные правила без состояния

Сейчас платформа использует **реактивную модель**: каждый тик (раз в 60 сек) фича
вычисляет желаемое действие «с нуля», исходя из текущих условий. Это работает
для простых сценариев, но имеет фундаментальные ограничения по мере роста системы.

**Проблема 1: Нет памяти о контексте.**
Система не знает, *почему* штора сейчас закрыта — потому что ночь, потому что
пользователь ушёл, или потому что он закрыл её вручную. Каждый тик пересчитывает
решение заново, что приводит к конфликтам (например, автоматика открывает штору,
которую пользователь только что закрыл).

**Проблема 2: Нет явных переходов.**
Переход из «авто закрыто» в «ручное открыто» — это просто смена значения
позиции, а не событие с причиной, приоритетом и условиями возврата. Невозможно
ответить на вопрос: «Что именно привело систему в текущее состояние?»

**Проблема 3: Конфликты решаются неявно.**
Если «Климат» хочет открыть штору (жарко), а «День сна» хочет закрыть — кто
победит? Сейчас это зависит от порядка в реестре и флага override, но логика
размазана по коду и не декларирована явно.

**Проблема 4: Сложность отладки.**
Невозможно просто спросить: «В каком состоянии сейчас спальня и *почему*?»
Нужно читать логи, вычислять условия вручную, воспроизводить тайминги.

### 1.2 Почему конечные автоматы

Конечный автомат (Finite State Machine, FSM) решает все четыре проблемы разом:

- **Явное состояние:** система всегда знает, в каком состоянии она находится.
- **Явные переходы:** каждый переход имеет триггер, условие (guard), приоритет и причину.
- **Детерминированность:** из одного состояния по одному триггеру возможен только один переход (или ни одного, если guard не выполнен).
- **Аудируемость:** история переходов = полная история поведения системы.

### 1.3 Цели внедрения

| Цель | Метрика успеха |
|---|---|
| Предсказуемость | Пользователь может сказать: «Штора закрыта, потому что сейчас состояние "Ночь" и я не трогал её вручную» |
| Отладка | За один взгляд на дашборд видно: состояние, время входа, причина, последний переход |
| Расширяемость | Новая фича = новый набор состояний и переходов в манифесте, без изменения ядра |
| Конфликт-фри | Два действия не могут конфликтующе изменить одно устройство — автомат разрешает по приоритету |
| Миграция | Существующие фичи продолжают работать, автоматы внедряются постепенно |

## 2. Концепция

### 2.1 Что такое автомат в контексте платформы

Автомат — это **декларативное описание поведения** сущности (устройства, фичи, комнаты)
в виде:

- **Состояний** (states) — дискретные режимы, в которых может находиться сущность.
- **Переходов** (transitions) — правила: «если произошло событие X в состоянии Y,
  и условие Z выполнено, то перейти в состояние W».
- **Приоритетов** (priority) — при конфликте нескольких переходов побеждает
  переход с наивысшим приоритетом.
- **Охранников** (guards) — условия, которые должны быть истинны для перехода.
- **Действий** (actions) — побочные эффекты при входе/выходе из состояния.

### 2.2 Ключевые принципы

1. **Автомат = данные, не код.** Состояния и переходы описываются в манифесте
   (или в `schema.py` фичи), а не хардкодятся в Python. Это позволяет:
   - Менять поведение через правку манифеста без перезагрузки кода.
   - Валидировать граф переходов на этапе `./shp validate`.
   - Генерировать документацию из манифеста автоматически.

2. **Иерархия автоматов.** Автоматы организованы в три уровня:
   - **Комната/Зона** — задаёт контекст (дома/нет, день/ночь, вечеринка/сон).
   - **Фича** — принимает решения на основе контекста комнаты.
   - **Устройство** — исполняет решения с учётом ручного вмешательства.

3. **Событийно-ориентированность.** Переходы происходят по событиям (изменение
   датчика, команда пользователя, таймер), а не по тикам. Тик используется только
   для проверки таймеров переходов (раз в 60 сек).

4. **Неизменяемость истории.** Каждый переход логируется и сохраняется в кольцевом
   буфере. Историю нельзя перезаписать, только дополнить.

### 2.3 Чем автомат НЕ является

- **Не конечный автомат Мура/Мили в строгом смысле.** Мы не строим теоретическую
  модель, а используем практический паттерн «состояние + переходы».
- **Не замена реестра фич (`_FD_REGISTRY`).** Реестр остаётся для координации
  между фичами. Автоматы заменяют *внутреннюю логику* принятия решений внутри фичи.
- **Не замена манифеста.** Автоматы описываются *в манифесте*, а не вместо него.

## 3. Архитектура

### 3.1 Уровни иерархии

```
┌─────────────────────────────────────────────────────────────┐
│                    Уровень 1: Комната / Зона                │
│  Состояния: EMPTY, HOME_DAY, HOME_NIGHT, SLEEPING, PARTY   │
│  Определяет контекст для всех фич в комнате                 │
└────────────────────────┬────────────────────────────────────┘
│ контекст (текущее состояние комнаты)
▼
┌─────────────────────────────────────────────────────────────┐
│                    Уровень 2: Фича                          │
│  Освещение: OFF, ON_SCHEDULE, ON_MOTION, NIGHTLIGHT, PARTY │
│  Климат: IDLE, HEATING, COOLING, SAFETY_LOCKOUT            │
│  Вентиляция: NORMAL, BOOST, NIGHT, AWAY, WINTER_PAUSE      │
│  Шторы: OPEN, CLOSED, PARTIAL, MANUAL_LOCK                 │
│  Принимает решения на основе контекста комнаты              │
└────────────────────────┬────────────────────────────────────┘
│ желаемое действие / переход
▼
┌─────────────────────────────────────────────────────────────┐
│                    Уровень 3: Устройство                    │
│  Конкретный привод/лампа/конвектор                          │
│  Исполняет команду с учётом ручного вмешательства           │
│  Состояния: IDLE, MOVING, ERROR, MANUAL_LOCK               │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 Правила взаимодействия между уровнями

1. **Вышестоящий уровень задаёт контекст, нижестоящий реагирует.**
   Комната в состоянии `SLEEPING` → фича освещения не включает свет по датчику
   движения → устройство не получает команду «включить».

2. **Нижестоящий уровень НЕ влияет на вышестоящий.**
   Штора не может перевести комнату из `HOME_DAY` в `PARTY`. Только явные
   триггеры уровня комнаты (присутствие, время, ручная команда) меняют состояние комнаты.

3. **Ручное вмешательство — всегда приоритет.**
   На уровне устройства состояние `MANUAL_LOCK` имеет наивысший приоритет.
   Никакой автомат не может вывести устройство из `MANUAL_LOCK`, кроме:
   - Истечения таймера.
   - Явной команды сброса (через сервис или дашборд).
   - Аварийной ситуации (пожарная безопасность, протечка).

### 3.3 Компоненты платформы

| Компонент | Расположение | Назначение |
|---|---|---|
| **Движок автоматов** | `ha/pyscript/fsm_engine.py` | Универсальный движок: хранение состояний, обработка переходов, проверка guards, логирование |
| **Схема автомата** | `features/<id>/fsm.py` или `schema.py` | Описание состояний и переходов конкретной фичи |
| **Манифест** | `instances/<id>/manifest.yaml` | Инстанс-специфичные параметры автоматов (таймауты, начальные состояния, переопределения) |
| **Хранилище состояний** | `sensor.<entity>_fsm_state` | Текущее состояние автомата + атрибуты (время входа, причина, история) |
| **Дашборд** | `features/<id>/ui.py` | Визуализация текущего состояния и последних переходов |
| **Валидатор** | `cli/validate.py` | Проверка графа переходов: нет ли недостижимых состояний, зацикливаний, отсутствующих переходов |

## 4. Спецификация

### 4.1 Состояние (State)

Состояние — это именованный режим, в котором может находиться сущность.

**Атрибуты состояния:**
- `name` — уникальное имя (строка, UPPER_SNAKE_CASE).
- `initial` — является ли состояние начальным (булево).
- `on_enter` — действия при входе в состояние (список команд).
- `on_exit` — действия при выходе из состояния (список команд).
- `timeout` — опциональный таймер: если состояние активно дольше `timeout` минут,
  происходит автоматический переход по триггеру `timeout`.

**Пример:**
```
Состояние: MANUAL_LOCK
initial: false
timeout: 60  # минут
on_enter: [log("Ручное вмешательство")]
on_exit: [log("Блокировка снята")]
```

### 4.2 Переход (Transition)

Переход — это правило смены состояния.

**Атрибуты перехода:**
- `from` — исходное состояние или список состояний. Специальное значение `*`
  означает «из любого состояния».
- `to` — целевое состояние.
- `trigger` — событие, инициирующее переход (строка).
- `guard` — опциональное условие (выражение), которое должно быть истинным.
- `priority` — целое число. При конфликте нескольких переходов побеждает
  наивысший приоритет. По умолчанию 0.
- `why` — человекочитаемое описание причины перехода (для логов).

**Пример:**
```
Переход: Ручное вмешательство → Блокировка
from: [OPEN, CLOSED, PARTIAL]
to: MANUAL_LOCK
trigger: manual_change
priority: 100
why: "Пользователь изменил позицию вручную"
```

### 4.3 Триггеры (Triggers)

Триггер — это событие, которое может инициировать переход.

**Стандартные триггеры платформы:**

| Триггер | Описание | Источник |
|---|---|---|
| `manual_change` | Пользователь изменил состояние устройства | Физический выключатель, Алиса, дашборд |
| `schedule` | Сработало расписание (закат, время) | Таймер |
| `motion` | Сработал датчик движения | Сенсор |
| `presence_change` | Изменилось присутствие (дома/не дома) | `my_doma` |
| `room_state_change` | Изменилось состояние комнаты | Автомат комнаты |
| `timeout` | Истёк таймер состояния | Движок автоматов |
| `override_clear` | Явный сброс блокировки | Сервис `covers_override_clear` |
| `emergency` | Аварийная ситуация (пожар, протечка) | Датчик безопасности |
| `feature_toggle` | Включена/выключена фича | `input_boolean.feature_*` |

### 4.4 Guards (Охранники)

Guard — это условие, которое проверяется перед выполнением перехода. Если условие
ложно, переход не происходит.

**Синтаксис:** строка-выражение, вычисляемая в контексте текущего состояния платформы.

**Примеры:**
```
guard: "room_state in (HOME_NIGHT, EMPTY)"
guard: "not dogs_home"
guard: "feature_covers == 'on'"
guard: "not fire_safety or position > fire_safety_min_pct"
```

**Ограничения (из-за особенностей Pyscript):**
- Guards не должны содержать генератор-выражения.
- Guards не должны делать сетевые вызовы или читать файлы.
- Guards должны быть чистыми функциями от текущего состояния.

### 4.5 Приоритеты

Приоритеты определяют, какой переход побеждает при конфликте.

**Стандартная шкала приоритетов:**

| Приоритет | Категория | Примеры |
|---|---|---|
| 1000 | Аварийный | Пожар, протечка, угарный газ |
| 100 | Ручное вмешательство | Пользователь тронул устройство |
| 50 | Безопасность | Зимний блок кондиционера, запрет авто ночью |
| 20 | Расписание | Закат, время закрытия |
| 10 | Автоматика по датчикам | Движение, влажность, температура |
| 5 | Фоновая | Имитация присутствия, подсветка выключателей |
| 0 | По умолчанию | Всё остальное |

**Правило:** Переход с более высоким приоритетом может прервать переход с более
низким. Переход с более низким приоритетом НЕ может прервать переход с более высоким.

### 4.6 Хранение состояния

Текущее состояние автомата хранится в `sensor.<entity>_fsm_state` со следующими атрибутами:

```
Атрибуты sensor.<entity>_fsm_state:
state:        "MANUAL_LOCK"           # текущее состояние
entered_at:   "2026-09-03 14:30:00"   # время входа в состояние
entered_by:   "manual_change"          # триггер, вызвавший переход
entered_why:  "Пользователь закрыл штору"  # причина
history:      [...]                    # последние 20 переходов (кольцевой буфер)
```

**Элемент истории:**
```
{
"time": "2026-09-03 14:30:00",
"from": "OPEN",
"to": "MANUAL_LOCK",
"trigger": "manual_change",
"why": "Пользователь закрыл штору",
"src": "ручное"
}
```

### 4.7 Логирование переходов

Каждый переход логируется через `log_event()`:

```
[covers][INFO] cover.bedroom: OPEN → MANUAL_LOCK | why=Пользователь закрыл штору | src=ручное
```

Формат: `[<домен>][<УРОВЕНЬ>] <сущность>: <из> → <в> | why=<причина> | src=<источник>`

## 5. Интеграция с текущей архитектурой

### 5.1 Манифест

Автоматы описываются в манифесте инстанса. Для каждой сущности, управляемой
автоматом, добавляется секция `fsm`:

```yaml
covers:
  covers:
    - id: bedroom
      cover: cover.bedroom
      fsm:
        initial: CLOSED
        states:
          - name: OPEN
          - name: CLOSED
          - name: PARTIAL
          - name: MANUAL_LOCK
            timeout: 60
          - name: ERROR
        transitions:
          - from: [CLOSED, PARTIAL]
            to: OPEN
            trigger: schedule
            guard: "room_state == HOME_DAY"
            priority: 20
            why: "Открытие по расписанию"
          - from: [OPEN, PARTIAL]
            to: CLOSED
            trigger: schedule
            guard: "room_state in (HOME_NIGHT, EMPTY)"
            priority: 20
            why: "Закрытие по расписанию"
          - from: [OPEN, CLOSED, PARTIAL]
            to: MANUAL_LOCK
            trigger: manual_change
            priority: 100
            why: "Ручное вмешательство"
          - from: MANUAL_LOCK
            to: CLOSED
            trigger: timeout
            priority: 10
            why: "Таймер блокировки истёк"
          - from: MANUAL_LOCK
            to: OPEN
            trigger: override_clear
            priority: 50
            why: "Явный сброс блокировки"
```

### 5.2 Фичи

Фича описывает автомат в `features/<id>/fsm.py` (или в `schema.py`):

```
features/covers/
  ├── schema.py      # Pydantic-схема + описание автомата по умолчанию
  ├── helpers.py     # Генерация input_* хелперов
  ├── ui.py          # Карточки дашборда (включая визуализацию состояния)
  ├── decide.py      # ЛОГИКА ЗАМЕНЯЕТСЯ на автомат (в фазе миграции)
  ├── fsm.py         # Новый файл: описание автомата фичи
  └── runtime.py     # Runtime-контроллер (интеграция с движком автоматов)
```

**Миграция `decide.py` → `fsm.py`:**
- `decide.py` возвращал `{"action": "open", "pct": 100, "why": "..."}`.
- `fsm.py` описывает состояния и переходы. Движок автоматов принимает решение.
- В переходный период `decide.py` может работать как **адаптер**: вызывает
  движок автоматов и транслирует результат в старый формат.

### 5.3 Реестр фич

Реестр `_FD_REGISTRY` остаётся для координации между фичами. Автоматы не заменяют
реестр, а **дополняют** его:

- Реестр определяет **порядок** обработки фич.
- Автомат определяет **поведение** внутри фичи.
- При конфликте между фичами (две фичи хотят изменить одно устройство) —
  реестр разрешает конфликт по приоритету, а автомат внутри фичи определяет,
  какое действие предложить.

### 5.4 Дашборды

**На дашборде настроек** для каждой сущности с автоматом отображается:
- Текущее состояние (цветной бейдж).
- Время входа в состояние.
- Причина последнего перехода.
- Кнопка «Сбросить блокировку» (если состояние `MANUAL_LOCK`).
- История последних 5 переходов.

**На админ-дашборде:**
- Визуализация графа переходов (для отладки).
- Лог всех переходов за последний час.
- Сервисы диагностики: `fsm_debug(entity_id)`, `fsm_reset(entity_id)`.

## 6. Примеры

### 6.1 Автомат шторы (упрощённый)

```
Состояния:
  OPEN         — штора полностью открыта
  CLOSED       — штора полностью закрыта
  PARTIAL      — штора частично открыта
  MANUAL_LOCK  — ручное вмешательство, автоматика заблокирована
  ERROR        — ошибка привода

Переходы:
  OPEN ──schedule_night──→ CLOSED       [приоритет 20]
  CLOSED ──schedule_day──→ OPEN         [приоритет 20]
  * ──manual_change──→ MANUAL_LOCK      [приоритет 100]
  MANUAL_LOCK ──timeout──→ CLOSED       [приоритет 10]
  MANUAL_LOCK ──override_clear──→ OPEN  [приоритет 50]
  * ──emergency──→ OPEN                 [приоритет 1000]
```

### 6.2 Автомат группы освещения

```
Состояния:
  OFF            — свет выключен
  ON_SCHEDULE    — включён по расписанию (закат/время)
  ON_MOTION      — включён по датчику движения
  ON_MANUAL      — включён вручную
  NIGHTLIGHT     — ночник (минимальная яркость, тёплый свет)
  PARTY          — режим вечеринки (держать включённым)
  OVERRIDE       — ручное вмешательство, автоматика заблокирована

Переходы:
  OFF ──sunset──→ ON_SCHEDULE           [приоритет 20]
  OFF ──motion──→ ON_MOTION             [приоритет 10, guard: feature_motion]
  OFF ──manual──→ ON_MANUAL             [приоритет 100]
  * ──manual_change──→ OVERRIDE         [приоритет 100]
  ON_MOTION ──motion_timeout──→ OFF     [приоритет 5]
  ON_SCHEDULE ──off_time──→ OFF         [приоритет 20]
  * ──nightlight──→ NIGHTLIGHT          [приоритет 50]
  NIGHTLIGHT ──motion──→ OFF            [приоритет 10]
  * ──party_mode──→ PARTY               [приоритет 30]
  PARTY ──sunrise──→ OFF                [приоритет 20]
  OVERRIDE ──timeout──→ OFF             [приоритет 10]
```

## 8. Риски и митигация

### 8.1 Взрыв состояний
**Риск:** Комбинаторный рост числа состояний при взаимодействии нескольких автоматов.
**Митигация:** Иерархия автоматов. Автоматы независимы друг от друга. Комната
задаёт контекст, фича реагирует на контекст, устройство исполняет. Не нужно
описывать все комбинации.

### 8.2 Производительность на RPi4
**Риск:** Движок автоматов добавляет накладные расходы на каждый тик.
**Митигация:**
- Переходы событийно-ориентированы (не на каждый тик).
- Тик используется только для проверки таймеров (раз в 60 сек).
- Хранение состояний в `sensor.*` — дешёвая операция.
- Никаких файловых операций в рантайме (всё в памяти).

### 8.3 Сложность миграции
**Риск:** Переключение с текущей логики на автоматы может сломать работающие сценарии.
**Митигация:**
- Миграция по одной фиче за раз.
- Переходный период: `decide.py` работает как адаптер, вызывая движок автоматов.
- Флаг `fsm_enabled` в манифесте: можно включить/выключить автоматы для конкретной фичи.
- Теневой режим: автомат логирует переходы, но не исполняет действия (аналог `shadow_mode`).

### 8.4 Отладка
**Риск:** Если автомат «застрял» в состоянии — сложно понять почему.
**Митигация:**
- Каждый переход логируется через `log_event()`.
- `sensor.<entity>_fsm_state` всегда показывает текущее состояние и причину.
- Сервис `fsm_debug(entity_id)` выводит граф + историю переходов.
- Админ-дашборд: визуализация графа и лога переходов.

### 8.5 Обратная совместимость
**Риск:** Существующие сервисы и хелперы могут перестать работать.
**Митигация:**
- Все существующие сервисы (`covers_override_clear`, `light_debug`, и т.д.)
  продолжают работать. Они транслируются в триггеры автоматов.
- Хелперы (`input_boolean.*`, `input_select.*`) остаются. Автоматы читают их
  как источники триггеров.

## 9. Тестирование

### 9.1 Юнит-тесты движка
- Переход по триггеру: из состояния A по триггеру T переходим в состояние B.
- Guard не выполнен: переход не происходит.
- Приоритет: при конфликте побеждает переход с высшим приоритетом.
- Таймаут: состояние автоматически меняется после истечения таймера.
- История: кольцевой буфер корректно сохраняет последние 20 переходов.

### 9.2 Интеграционные тесты фич
- Шторы: день → ночь → закрытие; ручное → блокировка → таймаут → авто.
- Свет: закат → включение; датчик движения → включение → таймаут → выключение.
- Комната: уход → EMPTY → закрытие штор + выключение света.

### 9.3 Регрессионные тесты
- Все существующие сценарии (из `HANDOFF.md`) должны продолжать работать.
- Теневой режим: автомат логирует, но не исполняет. Сравнение с текущей логикой.

## 10. Миграционный план

### 10.1 Принципы миграции
1. **Не ломать работающее.** Каждая фаза миграции должна быть обратимой.
2. **По одной фиче за раз.** Сначала шторы (простая), потом свет (сложная).
3. **Флаг включения.** Автоматы включаются через `fsm_enabled: true` в манифесте.
4. **Теневой режим.** Перед включением автоматов в реальном режиме — прогнать
   в теневом режиме (автомат логирует, но не исполняет).

### 10.2 Этапы миграции для одной фичи

```
Этап 1: Описание автомата
  - Написать схему автомата (состояния, переходы, приоритеты).
  - Добавить в манифест секцию `fsm` для сущностей фичи.
  - Валидация: `./shp validate`.

Этап 2: Теневой режим
  - Включить `fsm_enabled: true` + `fsm_shadow: true` в манифесте.
  - Автомат логирует переходы, но не исполняет действия.
  - Сравнить решения автомата с текущей логикой `decide.py`.
  - Исправить расхождения.

Этап 3: Реальный режим
  - Выключить `fsm_shadow`.
  - Автомат управляет устройствами.
  - Мониторинг логов первые 24 часа.

Этап 4: Удаление старой логики
  - Удалить `decide.py` (или оставить как адаптер).
  - Обновить документацию.
```

### 10.3 Откат
Если автомат работает некорректно:
```
# В манифесте:
fsm_enabled: false
fsm_shadow: false
```
Система возвращается к текущей логике `decide.py`.

## 11. Открытые вопросы

1. **Формат описания автоматов в манифесте.** YAML-секция `fsm` или отдельный файл
   `features/<id>/fsm.yaml`? Склоняемся к секции в манифесте для единообразия.

2. **Где хранить определения автоматов по умолчанию?** В `features/<id>/fsm.py`
   (код) или в `features/<id>/schema.py` (данные)? Склоняемся к `fsm.py` для
   разделения ответственности.

3. **Как обрабатывать параллельные автоматы?** Если два автомата хотят изменить
   одно устройство одновременно — кто побеждает? Решение: реестр фич определяет
   порядок, автомат устройства разрешает конфликт по приоритету.

4. **Нужен ли визуальный редактор графа переходов?** На этапе внедрения — нет.
   В будущем — возможно, как часть админ-дашборда.

5. **Как интегрировать с Яндекс Диалогами?** Голосовые команды = триггеры
   `manual_change` или специфические триггеры (`voice_command`).

## 12. Терминология

| Термин | Определение |
|---|---|
| **Автомат (FSM)** | Декларативное описание поведения сущности в виде состояний и переходов |
| **Состояние (State)** | Дискретный режим, в котором может находиться сущность |
| **Переход (Transition)** | Правило смены состояния: из → в, по триггеру, с условием |
| **Триггер (Trigger)** | Событие, инициирующее переход |
| **Guard** | Условие, которое должно быть истинным для перехода |
| **Приоритет (Priority)** | Числовое значение, определяющее порядок разрешения конфликтов |
| **Движок автоматов** | Универсальный код, обрабатывающий переходы для всех автоматов |
| **Контекст комнаты** | Текущее состояние автомата комнаты, доступное всем фичам |
| **MANUAL_LOCK** | Состояние блокировки автоматики после ручного вмешательства |
| **Теневой режим** | Автомат логирует переходы, но не исполняет действия |
