# Architecture

## Обзор

Платформа построена по принципу **Event-Driven FSM (Finite State Machine)** с композицией поведений.

```
┌─────────────────┐     ┌──────────────┐     ┌─────────────┐
│  Home Assistant │────▶│   HAAdapter  │────▶│  EventRouter │
│  (Pyscript/WS)  │     │              │     │              │
└─────────────────┘     └──────────────┘     └──────┬───────┘
                                                     │
                                                     ▼
┌─────────────────┐     ┌──────────────┐     ┌─────────────┐
│  HA Services    │◀────│ Command      │◀────│  FSM Engine │
│  (light, fan)   │     │ Dispatcher   │     │             │
└─────────────────┘     └──────┬───────┘     └─────────────┘
                               │
                               ▼
                        ┌──────────────┐
                        │  Middleware  │
                        │  Chain       │
                        └──────────────┘
```

## Ключевые компоненты

### 1. FSM Engine (`core/fsm.py`)

**Решение:** Использовать immutable state machines с async-first подходом.

**Почему:**
- Иммутабельность защищает от гонок состояний в асинхронном коде
- Async-first позволяет обрабатывать тысячи событий без блокировок
- Dataclasses дают производительность и типобезопасность

**Не изменять без обсуждения:**
- Структуру `FSMDefinition` (frozen dataclass)
- Логику debounce
- Механизм таймаутов

### 2. Command Dispatcher (`core/command_dispatcher.py`)

**Решение:** Все команды проходят через единый арбитр с приоритетами.

**Почему:**
- Решает проблему "кто главный", когда несколько поведений хотят управлять одним устройством
- Приоритет `20` (ночник) блокирует приоритет `10` (движение)
- Метод `release()` позволяет поведению освободить устройство

**Правило:**
- Приоритет 100+ — ручное управление
- Приоритет 20+ — критические сценарии
- Приоритет 10 — стандартные автоматизации
- Приоритет 1-9 — фоновые сценарии

### 3. Event Router (`core/event_router.py`)

**Решение:** Маппинг датчик → FSM строится из манифеста.

**Почему:**
- Отделяет сенсоры от логики (сенсор не знает, какие FSM его слушают)
- Позволяет одному сенсору триггерить несколько поведений
- Маппинг строится один раз при старте, а не на каждое событие

**Схема именования FSM:**
```
{device_id}_{template}_{priority}
light.kitchen_lighting_10
light.kitchen_night_light_20
```

### 4. Middleware System (`core/middleware.py`)

**Решение:** Глобальные правила применяются через цепочку обработчиков.

**Почему:**
- Не засоряет логику отдельных поведений
- Легко добавлять новые правила без изменения кода
- Работает по принципу Chain of Responsibility

**Текущие middleware:**
- `ManualLockoutMiddleware` — блокирует автоматизацию после ручного управления

### 5. Composition Pattern

**Решение:** Устройство имеет массив `behaviors`, каждое поведение — отдельная FSM.

**Почему:**
- Избегает "комбинаторного взрыва" шаблонов
- Каждое поведение независимо и переиспользуемо
- Конфликты решаются приоритетами в Dispatcher

**Пример в манифесте:**
```yaml
devices:
  - type: light_motion
    id: light.kitchen
    behaviors:
      - template: night_light
        priority: 20
        params:
          brightness: 10
          schedule: "23:00-07:00"
      - template: lighting
        priority: 10
        params:
          motion_sensor: binary_sensor.kitchen_motion
```

### 6. Правила домовладения: решение по глобальным флагам, а не по датчикам

**Решение:** часть поведений (шторы, спека 015) решается **не датчиками и не
часами, а глобальными флагами дома** — `my_doma`, `sleep_mode`, `sobaki_doma`,
фиче-флаги, аварийные флаги. Датчики в таком поведении не участвуют: устройство
получает только «открыть» или «закрыть».

**Почему:**
- Флаги дома описывают состояние людей, а не обстановку в комнате; отдельный
  датчик на каждое правило дал бы противоречивые решения.
- Единственный вход — событие: пересмотр приходит `settings_changed`. Ранее
  `EventRouter.route_settings_change` рассылал событие только вентиляции (по
  подстроке имени автомата); теперь адресаты берутся из
  `engine.entities_with_trigger("settings_changed")`, поэтому флаг дома будит
  любое поведение, объявившее этот триггер, а не только вентиляцию.
- Первый пересмотр выполняется **один раз при подключении адаптера**: события
  приходит только на изменение, и без стартового пересмотра поведение ждало бы
  первого переключения флага (часами). Тот же принцип, что и сверка датчиков при
  подключении (B40).
- Неизвестное значение флага трактуется в **безопасную** сторону (шторы: «люди
  дома», «собак нет»), чтобы сбой чтения не запирал дом.
- **Изменение состояния самого прибора** — тоже вход пересмотра вентиляции
  (`EventRouter.route_device_change`): рекуператор сам снимает «Приток MAX»
  примерно через пять минут, и событие об откате приходит в момент отказа.
  Пересматриваются только автоматы вентиляции (`_ventilation_modes_`); эхо
  собственной команды пропускается, чтобы не порождать вторую команду (B95).
  Сторож остаётся запасным путём на случай потерянного события.

**Правило:** новое поведение, зависящее от флагов дома, обязано (1) объявить
триггер `settings_changed`, (2) сделать пересмотр при подключении, (3) записать
причину решения в журнал, (4) попасть в `DIAGNOSTIC_TEMPLATES` /
`DIAGNOSTIC_CONTEXT_KEYS` для утреннего разбора.

### 6a. Глобальная цветовая температура — служба, а не состояние автомата

Температура света — непрерывная величина: автомат включается по движению или
кнопке и между событиями молчит. Поэтому общую температуру считает отдельная
служба `LightColorTemperatureService`: днём — дневная граница, от заката
(`sun.sun.next_setting`) до `color_temp_warm_at` — линейно к ночной, после —
ночная. Значения дня/ночи и текущее живут в `input_number` Home Assistant;
служба пишет текущее и обновляет горящие лампы через диспетчер, поэтому ручная
блокировка и приоритеты действуют как у остальной автоматики. Включение света
читает текущее значение из helper-а; явный `color_temp_kelvin` устройства
сильнее общего. `warm_at` (21:00) задаётся **по часам дома**: HA отдаёт
`sun.sun.next_setting` в UTC, поэтому служба приводит закат к поясу дома — иначе
кривая заканчивается в 21:00 UTC, то есть в 02:00 по дому (B107).

Перед выключением лампа с параметром `prepare_for_night` получает ночной режим
(3 % красного), затем гаснет: прибор запоминает последнее состояние, и иначе
ночник при следующем включении сначала вспыхивал бы прошлой яркой яркостью.
У `light.svet_nad_stolom` этот параметр убран: вечером лампа не выключается, а
уходит в `DIM`, а утренний таймаут гасит её без красной подготовки; ночник
прогревается при отбое отдельным шаблоном (B99).

### 6b. Вечерняя яркость и декоративный свет

`lighting` знает состояние `DIM`: это не ночник, а тусклый вечерний свет (по
умолчанию 3 %) с общей температурой дома. Переход в `DIM` разрешает guard
`dims_when_idle` только у лампы с параметром `dim_when_idle` и только вечером —
после полудня и при солнце под горизонтом. Так одно и то же состояние не
включается предрассветной темнотой: до полудня таймаут по-прежнему гасит свет.
Движение из `DIM` возвращает полную яркость; сон, рассвет и утро гасят.
Ночник (`night_light`) остаётся отдельным поведением с красным 3 %.

В 23:00 лампа с `dim_when_idle` **не меняется**: `quiet_hours_started` для неё —
пустой self-переход. Иначе человек, только что вошедший и включивший полный
свет, получал бы 3 % через секунды после движения. Вечерняя яркость наступает
только по `timeout` — после `motion_timeout_sec` без движения. Остальные лампы
`lighting` в 23:00 по-прежнему гаснут.

`deco_light` — вечерний свет без движения: закат включает, `off_by: sleep`
гасит по «мы спим», рассвет/утро тоже гасят. В доме так работают Кусь,
настольная лампа, торшер, свет над кроватью и подсветка зеркала; торшер и
свет над кроватью сохраняют общую температуру через параметр
`use_global_color_temp`.

`scheduled_light` — плановый свет, а не декор: основное уличное
освещение. Закат включает его только при включённом флаге
`automation_rules.scheduled_light_feature_entity`; флаг — разрешение
автоматике, поэтому ручное включение работает всегда. «Мы спим» гасит свет,
рассвет и `day_started` — запасные выключатели. Выключение флага гасит
горящую группу, включение после заката зажигает сразу, если дом не спит.
Ручное выключение живёт в `OFF_MANUAL` до следующего цикла. Шаблон
реагирует на `settings_changed` только при
`_changed_role == "scheduled_feature"`: иначе смена любого флага дома гасила
бы свет, включённый вручную при выключенном флажке. Сверка вечернего света
знает список автоматов `scheduled_light` и при выключенном флаге пропускает
их: «темно, а света нет» — здесь штатное решение, а не расхождение, а ручное
включение при выключенном флажке не должно гаситься каждые 15 минут. В доме
так управляется только группа `light.vse_fonari`; отдельные фонари остаются
вне платформы.

Ручное выключение декоративного света — отдельное решение, а не «прибор
пропал»: и распознанное действие, и внешнее/физическое выключение
(`device_state_diverged` + `device_is_off` из `ON_DECO`/`ON_MANUAL`) ведут в
`OFF_MANUAL`. Вечерняя сверка это состояние пропускает, утром оно снимается, и
следующий закат снова включает автоматику. Так свет не возвращается через
15 минут после того, как человек его погасил. Действия света выбирают
домен по префиксу `switch.*`: подсветка зеркала в HA — выключатель, а не лампа,
и получает только `turn_on`/`turn_off` без яркости и цвета.

### 6c. Поля дома — на уровне `automation_rules`, а не внутри домена

Вещи, которые не принадлежат одному домену, лежат на уровне дома (аудит B76,
A2–A12):

- `automation_rules.sleep_modifier` — общий флаг «мы спим» для света, штор и
  вентиляции; адаптер читает его отсюда.
- `automation_rules.scheduled_light_feature_entity` — разрешение автоматике
  включать плановый свет (основное уличное освещение) по закату. Флаг
  принадлежит дому: одно решение владельца не дублируется в каждой группе
  фонарей. Контекст — `scheduled_light_enabled`, роль адаптера —
  `scheduled_feature`.
- `automation_rules.season_entity` — сезон (`is_winter`) для климата и
  вентиляции; контейнер отдаёт его адаптеру общей ролью `season`.
- `automation_rules.schedule` (`night_off_at`, `morning_at`) — суточный цикл
  дома. События `quiet_hours_started` и `day_started` получают все автоматы,
  поэтому расписание читают `Container._start_day_cycle()` и `_day_range()`.
  Если расписание не задано, `_day_range()` по-прежнему берёт окно тишины
  `lighting.quiet_from/quiet_to`.
- `automation_rules.sensor_health.battery_watch_entities` — батарейки датчиков
  вне манифеста; наблюдение за зарядом не перебирает домены.

Часовой пояс — `InstanceConfig.time_zone`; его читают контейнер, служба
цветовой температуры и фабрика автоматов (B76/A9).

Термостат — свойство комнаты: `RoomConfig.thermostat_entity`. Уставка дома одна,
поэтому контейнер берёт первый объявленный термостат и предупреждает, если
термостатов несколько.

Диапазон уставки в манифесте не дублируется: единственный источник — схема
шаблона (`target_temp`, 5–35) и условие `_setpoint_value`. Поля
`climate.setpoint_min/max` удалены (B76/A7).

Фиче-флаги намеренно остаются по доменам (B76/A12): `climate.feature_entity`,
`ventilation.feature_entity`, `cover.feature_entity`. У каждого свой контекст
(`climate_enabled`, `ventilation_enabled`, `covers_enabled`) и своя роль
адаптера; общий раздел «фичи дома» только добавил бы слой отображения, не
убирая у владельца возможности выключить домен отдельно.

В `lighting` остаются его собственные правила: окно тишины, ночные комнаты,
`always_on_motion_rooms` и параметры цветовой температуры.

### 7. Состояние устройства объяснимо, возвратно и не зависит от смены правил

**Концепция владельца (2026-10-14, основная — сохраняется, чтобы не переспрашивать).**

**Система про каждое устройство знает: почему оно сейчас в этом состоянии и что
будет дальше — и при этом адекватно реагирует на действия пользователя и сбои
оборудования.**

Следствия, обязательные для кода и шаблонов:

1. **Состояние — это решение автоматики, а не отсутствие решения.** Выключенный
   основной свет — решение «сейчас так», а не «автоматика молчит». Поэтому смена
   правил **не должна превращаться в команду выключения**: новое правило
   применяется (пересчитывается), а не «гасит» устройство. Если позже правило
   станет «гореть до утра», уже выключенное устройство включается по новому
   правилу, а не остаётся выключенным «потому что так было».
2. **Ручное действие пользователя имеет приоритет на срок оверрайда** —
   стандартно 60 минут, и срок считается **от более позднего события**: ручного
   действия или включения модификатора (`sleep_mode`). После истечения срока
   система **возвращает устройство к автоматике** — пересчитывает решение, — а не
   «выключает» его. Возврат к автоматике — это не команда «выключить», а
   «спросить автоматику заново».
3. **Конкретика по свету** (требование владельца 2026-10-14):
   - **гирлянды, включая уличную, гаснут при `sleep_mode = true`**;
   - **ночное освещение горит до утра** по правилам автоматики (не гасится
     оверрайдом);
   - **основной свет**, который автоматика сейчас не включает, после оверрайда
     возвращается в **выключенное (автоматическое)** состояние.
4. **Сбои оборудования не считаются согласием.** Недоступность, молчание датчика
   и расхождение «автомат ↔ прибор» — отдельные наблюдаемые состояния; система
   реагирует (сторож, тревоги), а не трактует молчание как «всё в порядке».

   *Реализация (2026-10-14).* Сторож платформы сверяет решение автомата с
   фактическим состоянием прибора (чтение у Home Assistant раз в цикл) и называет
   расхождение видами `device_on_decision_off` («горит, хотя решение —
   выключено»), `device_off_decision_on` и `device_unavailable`. Расхождение
   попадает в журнал, в `problem_count` готовности и тревогой `device_mismatch`
   в интерфейс. Осталось (BACKLOG B64): реакция «повторить команду» — сейчас
   расхождение видно, но прибор не возвращается сам.
5. **Объяснимость для человека.** У каждого решения — причина и время (журнал),
   у устройства — «почему сейчас так» и «что дальше» (интерфейс). Утренний
   разбор обязан отличать «не хотел», «не мог», «ждал» и «сломалось».

**Физический выключатель света (B89).** Событие `light.*` без `parent_id` и без
нашей команды считается ручным действием, даже если Home Assistant подставил
пользователя интеграции. Адаптер пишет локкаут и отправляет
`manual_switch_on`/`manual_switch_off`; автоматизация с `parent_id` — тоже
действие человека, а своя команда платформы исключена. Обратное расхождение
(автомат `OFF`, прибор горит) при наличии события закрывается тем же ручным
состоянием; без события остаётся наблюдение сторожа — платформа не выключает
свет силой.

**Правило для реализации:** любой таймер оверрайда живёт в автомате (состояние с
`timeout`) или в трекере ручного управления; по его истечении автомат
пересчитывает решение, а не получает готовую команду «выключить». Новое поведение
обязано записать причину решения и попасть в диагностику.

## Архитектурные ограничения (ADR)

### ADR-001: Core не зависит от Adapters
- `core/` не импортирует `adapters/`
- Связь через `CommandIntent` и протоколы
- Composition root живёт в `src/app/` (перенос из `core/container.py`), правило проверяется `tests/architecture/test_dependency_rules.py`

### ADR-002: Манифест — единственный источник конфигурации
- Никаких хардкоженных значений в коде
- Все параметры в `manifest.yaml`
- Доменная модель одна: `core.models.manifest.Manifest`; JSON Schema и проверка выводятся из неё
- Неизвестные поля отвергаются с путём до поля; явные расширения — только в `extensions`
- В WebUI нет второй модели манифеста: только DTO представления

### ADR-005: Граница управления — доверенная сеть, а не заголовок
- Пароль приложения не требуется (решение владельца 02.11.2026)
- Изменяющие операции разрешены только из `TRUSTED_MANAGEMENT_CIDRS` и ingress
- `X-User-ID`/`X-Is-Admin` от клиента не повышают права
- `/health`, `/ready`, `/metrics` — явный allowlist; остальное default deny
- Остаточный риск: любой хост доверенной сети — владелец; компенсация — сегментация и firewall

### ADR-003: FSM идентифицируются по схеме `{device}_{template}_{priority}`
- Это позволяет одному устройству иметь несколько поведений
- EventRouter использует эту схему для роутинга

### ADR-004: Все изменения манифеста версионируются
- Поле `version` в манифесте
- Миграции для обратной совместимости
```
