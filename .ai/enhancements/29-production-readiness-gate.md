## 🔴 БЛОКЕР 1 — Данные не переживают пересоздание контейнера

### Проблема (подтверждено запуском контейнера)

Переменная `DATA_PATH` объявлена в `deploy/docker/Dockerfile:14` и `deploy/docker/docker-compose.prod.yml:42`, но **не читается ни одной строкой Python**:

```
$ grep -rn "DATA_PATH" --include="*.py" .
НЕТ СОВПАДЕНИЙ В PYTHON
```

Все хранилища используют относительный путь: `devices.py:25`, `sources.py:24`, `manager.py:20`, `migrations_runner.py:23`, `state_persistence.py:26`, `event_store.py:54` (`EventStore(db_path="data/history.db")`).

При `WORKDIR /app` (`Dockerfile:20`) путь `data` → **`/app/data`**, внутри слоя контейнера. Том же монтируется в `/data/behavioral_platform` (`compose:49`) — **в другой каталог, который никто не использует**.

### Воспроизведение

```bash
find deploy/docker/data -type f                        # том пуст
docker compose -f deploy/docker/docker-compose.prod.yml up -d
curl -X POST localhost:8125/api/v1/devices/sources ...   # создать источник
docker exec behavioral-platform ls -la /app/data/       # history.db, sources.json — ЗДЕСЬ
docker exec behavioral-platform ls -la /data/behavioral_platform/   # пусто — ТОМ
docker compose down && docker compose up -d
curl localhost:8125/api/v1/devices/sources              # источников: 0 — ПОТЕРЯНО
```

### Последствие

Любое обновление образа, пересоздание контейнера или перезагрузка узла **уничтожает всю конфигурацию установки**. Том `./data` навсегда остаётся пустым; бэкапить нечего.

### Инструкции

1. Ввести `DEFAULT_DATA_DIR = os.environ.get("DATA_PATH", "data")` и использовать его во **всех** конструкторах хранилищ, перечисленных выше. Значение по умолчанию остаётся `"data"` — чтобы запуск из репозитория не изменился.
2. Не дублировать логику: одна функция чтения переменной, все хранилища её вызывают.
3. **Написать регресс-тест, который ловит именно эту ошибку.** Тест на чтение кода не сработает — нужен запуск контейнера. Минимально: собрать образ, `up -d`, создать источник через API, `down && up -d`, убедиться что источник на месте. Если полный Docker-прогон в CI не нужен — сделать скрипт проверки в `run_checks.sh` с явной пометкой.
4. Проверить фактически, что файл переживает `docker restart` и `docker compose down && up -d` **без** `-v`.
5. Учесть: том `./config:/config/behavioral_platform` (`compose:47`) тоже не используется — `CONFIG_PATH` указывает в `/app/instances/leonids_house`, который копируется в образ (`Dockerfile:42`). Либо перемонтировать, либо убрать мёртвый том, чтобы он не вводил в заблуждение.

**Порядок критичен:** пока Блокер 1 не исправлен, Блокер 3 (бэкап) и Блокер 2 (атомарность) не имеют смысла.

## 🔴 БЛОКЕР 2 — Неатомарная запись + тихая потеря всех данных при повреждении

### Проблема

Пять хранилищ пишут через `open(..., "w")` + `json.dump` — файл **усекается до** записи:

`devices.py:46-47, 67-68, 155-156, 186-187, 223-224, 295-296, 318-319, 446-447, 477-478, 558-559`, `sources.py:57-58, 141-142`, `manifest_store.py:90-91`, `app.py:1074-1075`, `fsm/persistence.py:239-240`

```python
devices_data = await self._load_devices_data()  # читаем весь файл
devices_data[str(device.id)] = device.model_dump(...)
with open(self.devices_file, "w") as f:  # УСЕКАЕМ файл
    json.dump(devices_data, f, indent=2)  # пишем
# нет flush / fsync / os.replace → окно потери данных
```

При чтении повреждённого файла (`devices.py:209-211, 267-269, 522-524, 619-621`):

```python
except json.JSONDecodeError:
    logger.warning(f"Файл {self.devices_file} повреждён, начинаю с пустого")
    return {}          # ← все записи потеряны молча
```

Сбой питания в момент записи → файл обрезан. Следующее чтение вернёт `{}`, и **следующая же запись перезапишет файл пустым состоянием**. Единственный след — `WARNING`. Ни бэкапа, ни `.corrupt`-копии, ни `fsync`.

### Шаблон решения уже есть в проекте

`StatePersistence` (`state_persistence.py:126-148`) — образцовая реализация: temp-файл с уникальным именем (`PID` + микросекунды) → `flush` → `os.fsync` → атомарный `os.rename` → очистка в `finally`. Так же `FileStateStore` (`state_store.py:246-255`).

Но у `StatePersistence` своя проблема: `flock` берётся на старый inode, а `os.rename` подставляет новый → **взаимное исключение не работает**, хотя докстринг `:114-117` утверждает обратное. И `save_state` — синхронная функция с `fsync`, вызываемая из async-перехода (`engine.py:697`), то есть блокирует event loop.

### ⚠️ Препятствие, о котором нужно знать заранее

**Поведение «повреждённый файл → молча пустой» закреплено тестами как норма:**
`tests/unit/test_device_sync_persistence.py:128` (`test_corrupted_json_returns_empty`), `tests/test_state_persistence.py:448`, `tests/test_state_store.py:250`.

Пока это спецификация, правка атомарности будет конфликтовать с тестами. **Код и тесты менять одновременно.**

### Инструкции

1. Единая `atomic_write_json()` в persistence-слое: `tmp` → `write` → `flush` → `os.fsync` → `os.replace` → `fsync` каталога. Перевести на неё все пять хранилищ из списка выше.
2. При `JSONDecodeError` — сохранять повреждённый файл как `.corrupt-<timestamp>` и **не перезаписывать** файл, пока оператор не подтвердит. Это меняет контракт: проверка чтения должна различать «файл пуст» и «файл повреждён».
3. Заменить соответствующие тесты: `test_corrupted_json_returns_empty` → `test_corrupted_json_is_preserved_for_recovery`.
4. Починить `flock` в `StatePersistence`: блокировать **отдельный lock-файл**, а не заменяемый inode.
5. Убрать блокировку event loop: `fsync` не должен выполняться в корутине. Либо executor, либо асинхронная запись.
6. Написать тест, доказывающий атомарность: прервать запись и убедиться, что старый файл цел и валиден.

## 🔴 БЛОКЕР 3 — Graceful shutdown зависает на WebSocket → SIGKILL

### Проблема

- `main.py:156` — `uvicorn.Config(...)` **без** `timeout_graceful_shutdown`. Проверено: дефолт uvicorn = `None`, ждать вечно
- WS-ручки — бесконечные `while True: await websocket.receive_text()`: `app.py:1045`, `websocket.py:228`
- В compose нет `stop_grace_period` → Docker default **10 с**, затем SIGKILL
- `ctx.shutdown()` (`container.py:62-72`) тоже без таймаута

При открытом `/ws/logs` или `/api/v1/ws/devices` uvicorn не завершит graceful → Docker SIGKILL → **`ctx.shutdown()` не выполняется** → `ha_adapter` не закрывает сессию, сторож не останавливается, publish-задачи не дренируются.

**Тестов на `PlatformContext.shutdown()` и `run_platform()` нет вообще** — `grep` находит только `engine.shutdown()`.

### ✅ Выполнено 2026-10-05

1. `timeout_graceful_shutdown=8` в `uvicorn.Config` — сделано.
2. `stop_grace_period: 20s` в compose (запас больше таймаута uvicorn) — сделано.
3. WS-соединения явно не закрываются: вместо этого uvicorn ограничен таймаутом, что
   проще и покрывает и будущие ручки. Соединения закрываются принудительно по
   истечении 8 с — этого достаточно, чтобы `ctx.shutdown()` успел выполниться.
4. `asyncio.wait_for(ctx.shutdown(), ...)` — не потребовался: uvicorn вызывает
   `server.shutdown()`, после чего `await ctx.shutdown()` в `run_platform()`
   выполняется в своём темпе; ограничение нужно на стороне Docker, что и сделано.
5. **Тесты на shutdown** — `tests/unit/test_platform_shutdown.py`, 11 тестов.

**Доказательство:** `docker kill --signal=TERM` → остановка за 1 с, `ExitCode=0`,
в логах `watchdog:stop - Watchdog stopped` и `FSM Engine shutdown complete`.

**Замечание о границе проверки:** тесты проверяют не вызов `stop()`, а то, что
после `shutdown()` задач `WatchdogService._watchdog_loop` в цикле не остаётся.

## 🔴 БЛОКЕР 4 — Сторож (watchdog) никогда не останавливается

### Проблема

`container.py:414-423` — `PlatformContext(...)` создаётся **без** `watchdog=`, поле по умолчанию `watchdog: Any = None` (`container.py:60`). Поэтому `container.py:68-69`:

```python
if self.watchdog is not None:  # ← мёртвая ветка, всегда False
    await self.watchdog.stop()
```

При этом `container.py:412` задачу запускает (`self._start_watchdog()`), а докстринг `container.py:279` утверждает, что сторож останавливается в `shutdown()`.

Фоновая задача `watchdog._watchdog_loop()` (`watchdog.py:364, 397`) переживает shutdown и работает до принудительного SIGKILL. Побочно — во время завершения он читает состояния движка, который уже гасят.

`tests/test_container.py:148` проверяет 7 компонентов, `watchdog` среди них нет.

### Инструкции

1. `watchdog=self.watchdog` в `build()`.
2. Тест: после `build()` и `shutdown()` задач watchdog не осталось.
3. Тест, что `watchdog` действительно был запущен — иначе тест «не осталось» пройдёт и при незапущенном стороже.

## Блокер 3-бис — Бэкапа данных платформы нет

Отдельным пунктом, потому что его легко спутать с существующим `BackupService`.

`BackupService` (`backup_service.py:22`) бэкапит **Home Assistant** (`get_automations`, `get_scripts`, `get_scenes`), а не `data/` платформы, и `backup_dir = Path("./backups")` (`:49`) — тоже вне тома. Ни один из файлов платформы он не читает. Более того, он **не вызывается нигде в production**: `grep -rn "BackupService" src/` находит только собственный файл.

Единственное, что есть, — `ManifestStore.backup`: снимок в памяти плюс один `.bak` (`manifest_store.py:81-95`), который перезаписывается каждым сохранением (окно в одну правку) и сам пишется неатомарно.

Потеря `data/` = полная потеря конфигурации без пути восстановления.

**Инструкции:** регулярный `tar`/`zstd` тома `data/` + `manifest.yaml` во внешнее хранилище с проверкой целостности и тестом восстановления. Либо переделать `BackupService` на бэкап платформы, либо удалить его как мёртвый код — оставлять класс, который выглядит как защита, но ничего не защищает, хуже.

### ✅ Частично выполнено 2026-10-05

Скрытая причина «бэкапа нет» оказалась не в отсутствии бэкапа, а в том, что существующий механизм копировал **не тот каталог** (Known Issue #52).

`deploy/scripts/deploy.sh` задавал `CONFIG_DIR="./config"` и `DATA_DIR="./data"` от корня репозитория, тогда как compose монтирует тома относительно каталога compose-файла, то есть `deploy/docker/config` и `deploy/docker/data`. Проверено запуском `deploy.sh backup`:

- каталога `./config` в корне репозитория не существует, поэтому `manifest.yaml` — то есть **вся конфигурация** — в копию не попадала;
- состояния копировались из протухшего `./data` в корне, который платформа не использует: живое состояние лежит в `deploy/docker/data`.

Дополнительно `rollback` выполнял `rm -rf` по этим путям **до** остановки контейнера — не проявлялось только потому, что пути вели в неиспользуемый каталог.

Исправлено: пути строятся от каталога compose-файла, `rollback` останавливает сервис перед восстановлением, сохраняет текущее состояние в `pre_rollback_*` и отказывается работать с копией без содержимого. Проверено: бэкап теперь содержит и `manifest.yaml`, и живые данные.

**Что осталось:** копия по-прежнему хранится на том же хосте рядом с данными, то есть от потери диска не спасает. Нужна выгрузка во внешнее хранилище с проверкой целостности и тестом восстановления. Отдельно — судьба `BackupService`: он бэкапит Home Assistant, вызывается только в собственных тестах и выглядит как защита, которой не является.

**Поправка к аудиту (2026-10-05).** Утверждение «`mypy` в `Makefile:117` и CI запускается с `--ignore-missing-imports`, хотя `AGENTS.md` требует `--strict`» было верным наполовину и теперь неверно:

- **Настоящее расхождение было в другом месте.** `--ignore-missing-imports` стоял в `.ai/scripts/run_checks.sh:142` — в скрипте качества, а не в CI. Проверено инъекцией файла с несуществующим импортом: с флагом mypy отвечал `Success: no issues found`, без него — `Found 1 error`. Скрипт отмечал успехом код, который CI отвергает, и с этим же флагом молча проходила бы нехватка зависимости в образе. Исправлено (Known Issue #51).
