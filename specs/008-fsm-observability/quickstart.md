# Quickstart: проверка Observability платформы

**Feature**: specs/008-fsm-observability | **Дата**: 2026-10-01

Руководство по проверке фичи после реализации. Все сценарии выполняются **без Home Assistant** (автономный режим, mock-адаптер): метрики переходов и зависаний от этого не зависят, а потеря связи с HA в автономном режиме проверяется отдельно (сценарий 6). Форматы ответов — в [contracts/metrics-api.md](./contracts/metrics-api.md), поля снимков и проблем — в [data-model.md](./data-model.md).

---

## Подготовка

```bash
# Полные проверки качества (обязательно перед коммитом)
.ai/scripts/run_checks.sh
```

Ожидание: exit code 0, покрытие не ниже 80% для новых файлов, mypy без ошибок.

**Изолированный манифест** — чтобы не менять репозиторий. `CONFIG_PATH` указывает на **каталог** с `manifest.yaml`, а не на сам файл:

```bash
mkdir -p /tmp/shp-008
cp instances/leonids_house/manifest.yaml /tmp/shp-008/manifest.yaml
```

**Запуск без Home Assistant** (автономный режим, mock-адаптер):

```bash
CONFIG_PATH=/tmp/shp-008 PYTHONPATH=src python3 -m src.main
```

Проверка готовности:

```bash
curl -s localhost:8125/health
# {"status":"ok"}
```

> ⚠️ Ошибка из предыдущих фич: `CONFIG_PATH=/tmp/shp-008-manifest.yaml` (файл вместо каталога) приводит к пути `/tmp/shp-008-manifest.yaml/manifest.yaml` и платформа не стартует. Та же ошибка была в `specs/007-fsm-live-status/quickstart.md`.

**Сброс счётчиков**: показатели живут в памяти процесса и обнуляются при перезапуске (FR-010). Перезапускайте платформу перед сценариями, где важно нулевое начальное состояние.

**Почему часть проверок выполняется через тесты, а не через внешний запрос**: в автономном режиме нет источника событий — `MockAdapter` не маршрутизирует изменения состояний (Known Issue #10), поэтому переход извне вызвать нечем. Путь «переход → шина → показатель» проверяется интеграционным тестом, который собирает настоящий контейнер, вызывает `engine.trigger()` и читает реестр: это тот же код, что работает в запущенной платформе.

## Сценарий 1. Показатели доступны сразу после старта (US1, FR-001, FR-002, SC-002, SC-004)

**Что проверяем**: `/metrics` отвечает на порту платформы, обязательные семейства присутствуют **до первого перехода** — то есть отсутствие событий не означает отсутствие метрик.

```bash
curl -si localhost:8125/metrics | head -5
```

Ожидание: `200`, тип содержимого — **текстовый** (не JSON), тело начинается с `# HELP`, а не с `{`.

```bash
# Обязательные семейства присутствуют на пустой системе
curl -s localhost:8125/metrics | grep -E '^(# TYPE )?(fsm_transitions_total|fsm_rejections_total|active_fsm_instances|fsm_stuck_current|watchdog_checks_total|ha_connection_lost)'
```

Ожидание: все перечисленные имена найдены. `active_fsm_instances` > 0 — автоматы зарегистрированы.

**Ранее**: `/metrics` не существовал вовсе (13 маршрутов, ни одного `/metrics`).

## Сценарий 2. Счётчик переходов совпадает с фактом (US1, FR-003, FR-004, SC-001)

**Что проверяем**: каждый выполненный переход увеличивает `fsm_transitions_total` ровно на 1, каждый отклонённый не увеличивает его, а увеличивает `fsm_rejections_total` с причиной.

```bash
# Тесты: успех и все виды отказов
pytest tests/unit/core/test_fsm_event_publication.py -v
pytest tests/integration/test_platform_metrics.py -v
```

Вживую: вызвать переходы автомата и сверить:

```bash
# 1. Значение счётчика до перехода
curl -s localhost:8125/metrics | grep '^fsm_transitions_total{'

# 2. Вызвать переход (любой доступный способ: событие датчика, ручная команда,
#    либо прямая проверка подписчика в тесте)

# 3. Значение после — ровно на 1 больше, с теми же метками
curl -s localhost:8125/metrics | grep '^fsm_transitions_total{'
```

Ожидание: значение выросло на 1; набор меток (`fsm_name`, `from_state`, `to_state`, `device`) соответствует состоявшемуся переходу.

Проверка отказа: вызвать событие, для которого нет подходящего перехода (например, сигнал датчика в состоянии, где он не обрабатывается) — `fsm_transitions_total` не изменится, появится `fsm_rejections_total` с `reason` из списка `debounced`, `no_transition`, `guard_failed`, `unknown_entity`, `no_state`.

## Сценарий 3. Кардинальность ограничена (US1, FR-005, SC-006)

**Что проверяем**: произвольные имена состояний не приводят к неограниченному росту памяти — значения сверх лимита попадают в серию `__other__`.

```bash
# Тест: 10 000 переходов с уникальными именами состояний
pytest tests/unit/core/test_metrics.py -v -k cardinality
```

Ожидание: число различных серий метрики переходов не превышает лимит плюс одна служебная серия `__other__`; в журнале — одно предупреждение о переполнении, а не 10 000.

## Сценарий 4. Показатели одинаковы в обоих режимах (US1, FR-009, конституция VI)

**Что проверяем**: в автономном режиме и в режиме с Home Assistant `/metrics` работает одинаково.

```bash
# Автономный режим (уже запущен)
curl -s localhost:8125/metrics | grep -c '^fsm_transitions_total'

# Режим HA: задать HA_TOKEN и перезапустить
HA_TOKEN=<token> CONFIG_PATH=/tmp/shp-008-manifest.yaml PYTHONPATH=src python3 -m src.main
curl -s localhost:8125/metrics | grep '^fsm_transitions_total{'
```

Ожидание: та же форма ответа и те же семейства в обоих режимах. Различаться может только наличие событий.

## Сценарий 5. Сторож снимает снимки состояний (US2, FR-012, SC-007)

**Что проверяем**: снимок пишется в журнал на каждом цикле, время последнего перехода взято у движка, состояния показаны реальные.

Запустить с коротким интервалом, чтобы не ждать минуту:

```bash
WATCHDOG_INTERVAL_SEC=10 CONFIG_PATH=/tmp/shp-008-manifest.yaml PYTHONPATH=src python3 -m src.main
```

Через 60 секунд в журнале — не менее 5 структурированных записей снимка; каждая содержит время снятия, число записей и по каждому автомату: идентификатор, устройство, состояние, время последнего перехода.

```bash
# Счётчик проверок сторожа
curl -s localhost:8125/metrics | grep -E '^(watchdog_checks_total|watchdog_last_snapshot_timestamp)'
```

Ожидание: `watchdog_checks_total{result="ok"}` растёт на 1 за цикл; `watchdog_last_snapshot_timestamp` — ненулевое настенное время последнего снимка.

> Замер для SC-007: за 60 минут при интервале 60 секунд должно быть 60 ± 2 снимка. Не 0 и не непрерывный поток ошибок — прежде цикл падал на `await` синхронной функции и заваливался повторяющимися `TypeError`.

## Сценарий 6. Зависание обнаруживается, а потеря связи в автономном режиме — нет (US2, FR-013, FR-014, SC-008, SC-009)

**Что проверяем**: автомат, застрявший в состоянии с таймингованным переходом, обнаруживается; состояние без таймингованных переходов зависшим **не** считается; в автономном режиме отсутствие Home Assistant проблемой не является.

```bash
# Автомат с таймингованным переходом: порог = timeout_sec перехода + запас
WATCHDOG_INTERVAL_SEC=5 WATCHDOG_STUCK_GRACE_SEC=5 CONFIG_PATH=/tmp/shp-008-manifest.yaml PYTHONPATH=src python3 -m src.main
```

Ожидание после истечения порога:

```bash
curl -s localhost:8125/metrics | grep -E '^(fsm_stuck_current|fsm_stuck_total)'
```

- `fsm_stuck_current` > 0 для зависшего автомата; `fsm_stuck_total` увеличивается один раз при обнаружении и **не** растёт при следующих проверках;
- `ha_connection_lost` = 0 (автономный режим — Home Assistant нет, и это не проблема);
- в журнале — одно событие обнаружения, а не по одному на каждую проверку.

Проверка устранения: вернуть автомат в другое состояние → `fsm_stuck_current` возвращается к 0, в журнале появляется запись об устранении с `duration_sec`.

Проверка «не зависло»: состояние, из которого нет переходов с таймаутом, не должно давать `fsm_stuck_current > 0` ни при каком времени ожидания.

**Ранее**: сторож не инстанцировался нигде, тестов на него не было вообще, а порог зависания пришлось бы задавать вручную — тогда ложные срабатывания на состояниях, живущих по часам и суткам.

## Сценарий 7. Остановка платформы не оставляет висящих задач (US2, FR-017, SC-011)

**Что проверяем**: сторож останавливается вместе с платформой.

```bash
WATCHDOG_INTERVAL_SEC=10 CONFIG_PATH=/tmp/shp-008-manifest.yaml PYTHONPATH=src python3 -m src.main &
sleep 30
# Остановить один раз — и повторить 10 раз в цикле
for i in $(seq 1 10); do
  PID=$(pgrep -f "src.main" | head -1)
  kill -TERM $PID; wait $PID 2>/dev/null
done
```

Ожидание: при каждой остановке — завершение не дольше 30 секунд, в журнале **ни одного** `Task was destroyed but it is pending`, `Traceback` и `Unclosed client session`.

## Сценарий 8. Сбой проверки не ломает платформу (US2, FR-018, SC-012)

**Что проверяем**: если чтение состояний не удаётся, сторож фиксирует ошибку и продолжает работу — автоматика обрабатывает переходы.

```bash
# Тест: подмена источника состояний на источник, бросающий исключение
pytest tests/unit/services/test_watchdog.py -v -k fail
```

Ожидание: проверка вернула признак сбоя, ошибка зафиксирована в журнале, `watchdog_checks_total{result="failed"}` увеличился, цикл продолжает выполняться.

Вживую: остановить Home Assistant (или принять, что в автономном режиме его нет) и убедиться, что переходы автоматов по-прежнему обрабатываются, а платформа не падает.

## Сценарий 9. Отсутствие библиотеки сбора не роняет платформу (US1, FR-008, SC-005)

**Что проверяем**: сбой инициализации показателей переводит сбор в режим «не собираем», платформа продолжает работать.

```bash
# Тесты класса «без prometheus» + проверка ошибки регистрации
pytest tests/unit/core/test_metrics.py -v -k "without or error"
```

Ожидание: каждый вызов записи не бросает исключение; в журнале — предупреждение; платформа полностью работоспособна; `GET /metrics` отвечает `200` с пояснением вместо пустого документа «как будто показателей нет».

## Критерии приёмки

Фича считается проверенной, если:

1. Все 10 сценариев пройдены, фактические результаты зафиксированы в этом файле.
2. `.ai/scripts/run_checks.sh` завершился с кодом 0.
3. `pytest tests/` — 0 новых падений относительно состояния до фичи (до фичи: 1725 passed / 9 skipped / 0 failed).
4. Покрытие новых файлов — не ниже 80%; для `src/core/metrics.py` и `src/services/watchdog.py` — не ниже 90% (наблюдаемость, на которую нельзя положиться, опаснее отсутствующей).
5. Ни один сценарий не потребовал обхода через заглушки вместо настоящего поведения (FR-023).
