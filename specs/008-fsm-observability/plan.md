# Implementation Plan: Observability платформы — метрики, сторож, правдивая документация

**Branch**: `008-fsm-observability` | **Date**: 2026-10-01 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/008-fsm-observability/spec.md`

## Summary

Платформа перестаёт быть «немой»: 18 объявленных метрик наконец собираются и отдаются по запросу с того же HTTP-сервера, что и панель, сторож превращается из недоделанного модуля в работающую службу (снимки состояний, обнаружение зависших автоматов и потери связи), а документация и тесты приводятся в соответствие с фактическим состоянием кода.

Технический подход: инициализация сборщика показателей первым шагом `Container.build()`; учёт переходов, отказов и восстановлений отдельным подписчиком шины `services/metrics_reporter.py` (движок не меняется — конституция I); маршрут `GET /metrics` рядом с `/health`; переписанный `WatchdogService` в жизненном цикле платформы с порогом зависания, выводимым из описания автомата; удаление неподнятого дубля метрик, параллельного зеркала и недостижимого модуля интеграции с панелью.

## Technical Context

**Language/Version**: Python 3.12 (репозиторий содержит артефакты и для 3.14; целевая версия — 3.12, см. `pyproject.toml`)

**Primary Dependencies**: FastAPI + Starlette (маршрут `/metrics`), Pydantic v2, loguru, prometheus_client ≥0.19 (`pyproject.toml:23`, установлена), aiohttp (уходит вместе с удаляемым `metrics_server.py`)

**Storage**: N/A для метрик (срез в памяти процесса); существующее хранилище не затрагивается. Снимки сторожа не сохраняются

**Testing**: pytest + pytest-asyncio (`asyncio_mode = "auto"`), `--import-mode=importlib`, `pytest-cov` (порог 80% для новых файлов), mypy `--strict`, ruff, interrogate

**Target Platform**: Linux-сервер / macOS (Docker Compose), Python 3.12; режимы: автономный (MockAdapter) и с Home Assistant (HAAdapter)

**Project Type**: web-service (FastAPI) + библиотека (ядро) + CLI

**Performance Goals**: учёт перехода добавляет к переходу < 1 мс (FR-001, SC-003); `/metrics` отвечает < 500 мс при 50 автоматах; сторож при интервале 60 с добавляет циклу < 10 мс (SC-007)

**Constraints**: длина функций ≤50 строк, type hints везде, docstrings Google style, loguru с `trace_id`, никаких bare `except`, покрытие ≥80% (критические модули 95%), Core не импортирует Adapters, число различных серий показателей ограничено (FR-005)

**Scale/Scope**: ~10–50 автоматов на объект, до 18 метрик, 3 пользовательские истории, 26 FR, 0 новых сетевых портов

| Принцип | Требование | Оценка | Обоснование |
|---|---|---|---|
| **I. Event-Driven FSM** | Структура `FSMDefinition`, логика debounce, механизм таймаутов меняются только по согласованию | **PASS** | Ни одно из трёх не меняется. Учёт переходов идёт через уже публикуемые события (R-03), движок не трогается. В движок добавляется **один** публичный read-only метод `expected_timeout_sec` (R-06) — чтение существующего `Transition.timeout_sec` (`engine.py:105`), без изменения самого механизма таймаутов и без нового синтаксиса в манифесте |
| **II. AI-first, TDD/SDD, качество** | Type hints, docstrings, ≥80% покрытия, хуки | **PASS** | Каждый новый модуль (`metrics_reporter.py`, переписанный `watchdog.py`) получает тесты; `metrics.py` — переписываются тесты с `MagicMock` на настоящую библиотеку (R-08, FR-023). Тесты первыми в каждой волне |
| **III. Контроль остаётся за пользователем** | UI — единственный источник истины; автоматика не меняет состояние сама | **PASS** | Фича только **наблюдает**. Ни одно требование не добавляет воздействия на устройства: обнаружение зависания публикует событие и инкрементит счётчик, но не переключает состояние автомата и не отправляет команду (FR-016, FR-018) |
| **IV. Многоуровневая архитектура** | Core не импортирует Adapters; Services не импортирует Core | **PASS с отклонением** | ADR-001 соблюдён: `core/metrics.py` не знает ни об адаптерах, ни о веб-слое. Второе правило уже нарушено существующим кодом (`services/fsm_state_bridge.py:27-35` импортирует `core.*`), новый сервис следует тому же образцу (R-10). Отклонение вынесено в Complexity Tracking; сторож обращается к адаптеру через протокол, без импорта класса (R-13) |
| **V. Манифест — единственный источник конфигурации** | Никаких hardcoded значений; изменения схемы версионируются | **PASS** | Схема манифеста **не меняется**. Пороги сторожа и лимит кардинальности — именованные константы модуля; настройки интервалов — переменные окружения по образцу работающего `HOT_RELOAD` (R-07). Новых правил ожидания в манифест не вводится (R-06) |
| **VI. Двухрежимное развертывание** | Автономный режим и режим HA, идентичные тесты | **PASS** | Показатели одинаковы в обоих режимах (FR-009): ключевой сценарий — переходы автоматов, они есть в обоих. Потеря связи с HA в автономном режиме **не** считается проблемой (R-13, FR-014). Тесты обоих режимов обязательны (SC-009) |
| **VII. Многоуровневый интерфейс** | CLI / Web / HA работают через общий API | **PASS** | Показатели отдаются тем же HTTP-сервером, что и панель (D-2); CLI может опрашивать тот же адрес. Нового параллельного интерфейса не появляется |
| **ADR-001** | Core не зависит от Adapters | **PASS** | Новых зависимостей Core→Adapters нет. `/metrics` живёт в веб-слое; `MetricsReporter` — в сервисах; сборщик — в core без обратных ссылок |
| **ADR-002** | Манифест — единственный источник конфигурации | **PASS** | Как в V. Удаление демо-значений и мёртвого кода (US3) убирает расхождение между описанием и кодом, а не добавляет конфигурацию |
| **ADR-003** | FSM идентифицируются по `{device}_{template}_{priority}` | **PASS** | Идентификатор используется как есть. Значение `device` для показателей берётся из полезной нагрузки события (`build_transition_payload`), а не разбирается из имени — разбор имени по `_` даёт коллизию префиксов (Known Issue #20) |
| **ADR-004** | Приоритеты в CommandDispatcher | **PASS** | Приоритеты не меняются, новые команды не создаются. Никто не отправляет интенты по команде наблюдаемости |
| **ADR-005** | Middleware для глобальных правил | **PASS** | Не затрагивается. Ручная блокировка команд (`MANUAL_SOURCES`, Known Issue #18) остаётся как есть |

**Итог гейта: PASS с одним задокументированным отклонением** (Services → Core, уже существующее в коде). Нарушений, требующих изменения принципов, нет.

**Перепроверка после проектирования (Phase 1): PASS.** Контракт `/metrics` не вводит нового состояния; порог зависания выводится из описания автомата, а не из новой конфигурации; удаляемые модули не участвуют ни в одном production-пути (проверено: `MetricsServer` — 0 импортов в `src/`, `DashboardIntegration` — только `tests/test_dashboard.py`, зеркало `src/smart_home/core/metrics.py` — только `tests/test_prometheus_metrics.py`).

## Complexity Tracking

| Отклонение | Почему нужно | Почему отвергнут более простой вариант |
|-----------|--------------|-------------------------------------|
| Сервисы импортируют `core.metrics` | `MetricsReporter` — подписчик шины, а шина и сборщик живут в ядре; другой путь потребовал бы прокидывать показатели через конструктор контейнера в каждый потребитель | Размещение сборщика в `services/` нарушило бы ADR-001 в обратную сторону (сервис стал бы ядром наблюдаемости) и не устранило бы зависимость от `core.events`, которая нужна подписчику в любом случае. Отклонение **уже существует в коде** (`services/fsm_state_bridge.py:27-35`, `services/device_service.py`), поэтому новый сервис следует принятому образцу, а не вводит вторую схему. Правило «Services не импортирует Core» в конституции не соответствует коду; исправление конституции — вне объёма фичи и вынесено в Known Issues |
