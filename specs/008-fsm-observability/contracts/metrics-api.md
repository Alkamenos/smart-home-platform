# Contract: диагностические точки HTTP (008-fsm-observability)

**Вход**: `spec.md` FR-001…FR-011, FR-019, FR-024; решения D-2 (R-02), D-3; `research.md` R-02, R-07, R-08, R-14
**Дата**: 2026-10-01
**Базовый адрес**: тот же HTTP-сервер платформы, что и панель и `/health` (порт 8125 в Docker Compose). Отдельного порта показателей нет (D-2).

---

## 1. `GET /metrics`

Отдаёт метрики платформы в текстовом формате сбора данных Prometheus.

### 1.1. Ответ

| Поле | Значение |
|------|----------|
| Код | `200` |
| Тип содержимого | текстовый (`text/plain; version=0.0.4; charset=utf-8` — точный тип задаёт библиотека сбора) |
| Тело | документ показателей: по одному блоку на метрику — `# HELP`, `# TYPE`, строки серий |

**Ответ — текст, а не JSON.** Это отличает его от `/health` (`routes/__init__.py:38`), который отвечает `application/json`. Обёртка вида `{"metrics": "..."}` недопустима (FR-002).

### 1.2. Обязательные семейства

Следующие метрики присутствуют в ответе **сразу после старта**, до первого события (FR-002, SC-004):

| Семейство | Вид | Наборы значений |
|-----------|-----|-----------------|
| `fsm_transitions_total` | счётчик | `fsm_name`, `from_state`, `to_state`, `device` |
| `fsm_rejections_total` | счётчик | `fsm_name`, `reason` |
| `fsm_states_restored_total` | счётчик | `fsm_name` |
| `active_fsm_instances` | шкала | `manifest_name` |
| `fsm_stuck_current` | шкала | `fsm_name` |
| `watchdog_checks_total` | счётчик | `result` |
| `watchdog_last_snapshot_timestamp` | шкала | — |
| `ha_connection_lost` | шкала | — |
| `metrics_collection_errors_total` | счётчик | `stage` |
| `websocket_filtered_events_total` | счётчик | — |

Существующие семейства `device_integration_*`, `websocket_disconnects_total`, `command_dispatcher_rejections_total`, `middleware_conflicts_total`, `event_processing_latency_seconds`, `ha_adapter_connection_errors_total` сохраняются и начинают отражать фактические события.

`websocket_filtered_events_total` — счётчик событий, отброшенных локальным фильтром сущностей (фильтр со стороны Home Assistant не существует, `entity_ids` в `subscribe_events` отвергается API). Счётчик обязателен, потому что сам фильтр работает молча: без него невозможно отличить «фильтр отсекает лишнее» от «события не приходят вовсе» — тот самый способ обнаружения Known Issue #83. Фильтр перечитывает манифест на каждом событии, поэтому счётчик растёт и при изменении манифеста без рестарта.

### 1.3. Соглашения об именах и значениях

1. **Формат времени** — единый ISO-8601 настенного времени, тот же, что в `specs/007-fsm-live-status` (`TIMESTAMP_FORMAT`, `fsm_events.py:48`).
2. **Причины отказов** — только значения констант `REASON_*` (`fsm_events.py:41-45`): `unknown_entity`, `no_state`, `debounced`, `no_transition`, `guard_failed`. Произвольных строк в наборе значений быть не может.
3. **Устройство в счётчике переходов** берётся из полезной нагрузки события, а не разбирается из идентификатора автомата: идентификатор строится по схеме `{устройство}_{шаблон}_{приоритет}`, а разбор по `_` даёт коллизию префиксов (Known Issue #20).
4. **Идентификатор автомата** приходит как есть, без нормализации регистра.

### 1.4. Ограничение кардинальности (FR-005)

Число различных наборов значений ограничено константой. Серии сверх лимита учитываются с меткой `__other__`. Потребитель, читающий `/metrics`, вправе рассчитывать на конечное число серий и не обязан переживать неограниченный рост (SC-006).

### 1.5. Отказ

| Случай | Код | Тело |
|--------|-----|------|
| Показатели выключены настройкой | `200` | пустой документ с пояснением, что сбор отключён |
| Сборщик не инициализирован (платформа ещё собирается) | `503` | описание причины |
| Ошибка формирования документа | `500` | описание причины |

`503` обязателен именно для случая «сервис ещё не готов»: пустой ответ `200` недопустим, иначе мониторинг примет «показателей нет» за «показатели собираются и их ноль» (аналог FR-020 из specs/007 — там этот случай был закрыт отдельно).

### 1.6. Доступ (FR-011, R-14)

Маршрут открыт так же, как `/health` — без аутентификации. Перечень открытых диагностических точек платформы:

| Точка | Открыта | Назначение |
|-------|---------|-----------|
| `/health` | да | готовность сервиса |
| `/metrics` | да | **настоящий документ** (эта фича) |

Тело ответа содержит имена устройств и автоматов, уже видимых владельцу дома в своей сети; схема разграничения доступа к устройствам (specs/004) к этому маршруту не применяется. Ввод аутентификации для диагностики — вне объёма фичи, см. Known Issues.

### 1.7. Сбой сбора не должен ломать платформу (FR-008)

| Случай | Поведение |
|--------|-----------|
| Библиотека сбора не установлена | платформа работает полностью; `/metrics` отвечает `200` с пояснением; в журнал — предупреждение при старте; `metrics_collection_errors_total{stage="initialize"}` недоступен (нет реестра), факт виден по журналу |
| Ошибка регистрации метрики | сборщик переходит в режим «не собираем» с предупреждением; платформа работает; остальные метрики не регистрируются |
| Ошибка формирования ответа | `500` с описанием; платформа работает; счётчик ошибок увеличивается |

## 2. Конфигурация через переменные окружения (FR-019, FR-024)

| Переменная | По умолчанию | Смысл | Где читается |
|-----------|--------------|-------|--------------|
| `METRICS_ENABLED` | включено | сбор показателей | `src/core/metrics.py` (настройки), инициализация — `src/core/container.py` |
| `WATCHDOG_ENABLED` | включено | сторож | `src/services/watchdog.py` |
| `WATCHDOG_INTERVAL_SEC` | `60` | интервал проверок | там же |
| `WATCHDOG_STUCK_GRACE_SEC` | `30` | запас сверх ожидаемого времени пребывания | там же |
| `WATCHDOG_HA_LOSS_SEC` | `300` | порог потери связи | там же |

**Инварианты:**

1. `METRICS_ENABLED` объявлен в `deploy/.env.example` и **обязан читаться кодом** — FR-024 прямо называет эту настройку. Сегодня он там есть и не читается.
2. `METRICS_PORT` из `deploy/.env.example` **удаляется**: отдельного порта показателей больше нет (D-2). Порт платформы конфигурируется как раньше.
3. Некорректное значение (не число, ноль, отрицательное) → значение по умолчанию + предупреждение в журнале. Сбой старта недопустим (FR-019).
4. Схема манифеста не меняется: эти настройки не имеют аналога в `manifest.yaml` (конституция V).

## 3. Событие проблемы в шине платформы

Внутренний контракт, но публичный: подписчики (внешние потребители событий платформы) обязаны знать его форму. Соглашения — общие с `specs/007-fsm-live-status/contracts/fsm-events.md`.

### 3.1. Имя события

`platform.problem` — по образцу `platform.started` (`fsm_events.py:25`). Константа объявляется рядом с существующими, а не строковым литералом (FR-025: сейчас `fsm.restored` публикуется литералом в `persistence.py:327`, и это отмечено как дефект).

### 3.2. Полезная нагрузка

| Поле | Тип | Обязательность | Описание |
|------|-----|----------------|---------|
| `kind` | `str` | да | `fsm_stuck` или `ha_disconnected` |
| `entity_id` | `str \| None` | нет | автомат; `None` для потери связи |
| `state` | `str \| None` | нет | состояние зависшего автомата |
| `resolved` | `bool` | да | `false` — обнаружено, `true` — устранено |
| `detected_at` | `str` | да | ISO-8601, настенное время |
| `resolved_at` | `str \| None` | нет | ISO-8601; при `resolved=false` — `None` |
| `duration_sec` | `float \| None` | нет | заполняется при `resolved=true` |

### 3.3. Гарантии доставки

1. Событие публикуется **только** при появлении проблемы и при её устранении. Периодические повторы запрещены (FR-016).
2. Ошибка публикации или обработки **не влияет** на работу платформы: проблема уже учтена в показателях, потеря события не должна превращаться в сбой проверки (FR-018).
3. Подписчики переходов, отказов и восстановлений событие не получают — оно фильтруется по типу.
4. Автономный режим без Home Assistant событие `ha_disconnected` **не публикует** (FR-014).

## 4. Что удаляется как часть контракта

| Объект | Основание |
|--------|-----------|
| Отдельный HTTP-сервер показателей на собственном порту (существующий неподнятый сервис) | D-2, R-02 |
| Параллельная реализация сборщика показателей и её сервер | D-2, R-09 |
| Недостижимый модуль интеграции с панелью | D-3, R-09 |

Три уровня, которые больше не являются контрактом: собственный порт показателей, независимый процесс наблюдаемости, зеркало HA-панели состояний автоматов. Зеркалирование состояний в Home Assistant остаётся и выполняется мостом состояний (specs/007) — это отдельный контракт, не затронутый фичей.
