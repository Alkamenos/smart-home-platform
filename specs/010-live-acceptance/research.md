# Исследование: Живой запуск — приёмка и пути, по которым данные не доходят

**Дата**: 2026-10-07 · **Спека**: [spec.md](../spec.md)

Все решения ниже получены чтением кода и запуском, а не предположением о
намерении. Там, где утверждение в Known Issues расходится с кодом, указано и
расхождение.

---

## R-01. Где читать указание пользователя из события Home Assistant

**Решение.** Указание пользователя лежит в конверте события, а не в его данных:
подписка `subscribe_events` присылает `{event: {event_type, data: {...},
context: {user_id, ...}}}`. Клиент отдаёт обработчику только `data`
(`ha_adapter.py:146`: `payload = event_data.get("data", event_data)`), поэтому
`context` теряется — и обработчик честно читает поля из `data`, отсюда
работоспособность маршрутизации.

Читать `context` надо в той же строке: извлечь `event_data.get("context")` и
передать обработчику вместе с `data`. Дальше контекст идёт в `on_state_change`,
который уже читает `context.get("user_id")` (`ha_adapter.py:404`) — то есть
вторая половина пути написана и ждёт данных.

**Обоснование.** Правка локальна: одна строка разбора и один параметр обработчика.
Ничего не меняется в маршрутизации и доставке состояния — там, где она работает.

**Альтернативы.**
- Читать пользователя в сервисе устройств по событию `state_change`: невозможно,
  публикуемый payload контекста не содержит — там только `entity_id`,
  `new_state`, `old_state`.
- Подписаться на события HA целиком и разбирать конверт в адаптере: дороже и
  ломает работающую подписку с фильтром по сущностям.

## R-02. Что считать ручным действием

**Решение.** Ручным считается действие, у которого есть источник «человек»:
- событие от Home Assistant с непустым `context.user_id` — человек нажал в
  приложении, на пульте или физический выключатель дошёл до Home Assistant;
- команда, отправленная из веб-интерфейса платформы.

Второй путь сейчас не проходит, потому что источник помечен `manual_command`
(`devices.py:679`), а middleware знает только `{manual, user, home_assistant,
voice, alexa, google}` (`middleware.py:103-110`).

**Обоснование.** Список источников оставлен, но пополнен и сделан
настраиваемым через манифест: набор «ручных» имён — это политика установки, а
не свойство кода. Иначе следующий интерфейс (умная колонка, CLI) снова упрётся в
тот же список.

**Альтернативы.**
- Убрать список целиком и считать ручным всё, что не автоматика: тогда
  внутренние служебные команды платформы (зеркало состояния автомата через
  диспетчер) начнут засчитываться как вмешательство человека и блокировать
  автоматику — то есть система заблокирует сама себя.
- Считать ручным только события HA: теряется команда из веб-интерфейса, а это
  самый прямой путь «человек вмешался».

## R-03. Переживает ли блокировка перезапуск

**Решение.** Да: факт последнего ручного действия по каждому устройству
сохраняется и восстанавливается при старте.

**Обоснование.** Перезапуск контейнера — это ровно тот момент, когда жилец
пробует выключить свет и убеждается, что «ничего не помогает»: автоматика
снова включает свет в первую же минуту. Срок блокировки измеряется десятками
минут, а перезапуски в бою случаются после каждой правки манифеста и каждого
обновления. Сбрасывать блокировку при старте — значит оставлять дыру именно там,
где её заметят.

**Обоснование выбора хранилища.** Небольшой отдельный файл рядом с состоянием
автоматов, атомарная запись. Добавлять состояние автоматов нельзя: оно пишется
по своему расписанию и сбрасывается при горячей перезагрузке манифеста, то есть
потеряло бы факт ручного действия в момент, когда он нужнее всего.

**Альтернативы.**
- Сбрасывать при старте: проще на одну строку, но оставляет ровно ту поломку,
  которую фича чинит, только в худший момент.
- Держать в памяти и полагаться на малый срок: недетерминированно — зависит от
  того, успел ли свет включиться до перезапуска.

## R-04. Как измеримое значение доходит до условия перехода

**Решение.** Маршрутизатор кладёт значение датчика в контекст перехода под
именем роли датчика, которую он уже знает: у него есть соответствие
«роль → событие» (`event_router.py:64`, `humidity → humidity_changed`). Для
маршрута по влажности в контекст добавляется `humidity` со значением нового
состояния датчика.

**Обоснование.** Условие уже читает `context["humidity"]` и
`context["humidity_threshold"]` (`builtin.py:118,135`) — то есть половина пути
написана и ждёт данных, как и в случае R-01. Имя роли совпадает с тем, что
условие ожидает, поэтому менять условие не нужно.

Значение добавляется как приведённое к числу, если это возможно; иначе — как
исходная строка, чтобы условие отказало по понятной причине, а не сравнило
строку с числом молча.

**Альтернативы.**
- Класть значение под одним общим именем (`sensor_value`): условие перестаёт
  знать, чей это датчик, — при двух датчиках в комнате решение станет
  неоднозначным.
- Запихивать в контекст весь словарь состояния датчика: в контекст попадает
  мусор, и любое опечатанное имя ключа больше не отлавливается проверкой.

## R-05. Как отличить «условие не прошло» от «данных не было»

**Решение.** Каждое условие объявляет, какие данные ему нужны, при регистрации.
Движок проверяет наличие этих данных до вызова условия и, если их нет,
фиксирует отказ с отдельной причиной «данных нет». Само условие вызывается
только когда данные есть, и его отказ означает ровно «значение не подходит».

**Обоснование.** Сейчас обе причины дают один и тот же `guard_failed`, и владелец
не может отличить «влажность 60, порог 65» от «влажность никогда не приходила».
Это ровно то расхождение, которое стоило понимания, почему вентиляция молчит.
Проверка наличия — до вызова условия, а не разбором его результата: условия
остаются обычными функциями «да/нет», их подпись не меняется и ни один из
десятка существующих guard'ов не правится.

**Альтернативы.**
- Возвращать из условия пару «да/нет + причина»: меняет контракт всех
  условий, то есть трогает код, который работает и покрыт проверками.
- Отличать по факту наличия ключа в контексте внутри каждого условия: правится
  каждое условие отдельно, и через полгода одно забудут — то есть расхождение
  вернётся, только тише.

## R-06. Где живёт процедура приёмки

**Решение.** Процедура — документ `quickstart.md` рядом со спекой: шаги, признак
успеха каждого шага, условие остановки и таблица для записи фактического
результата, включая «не проверено».

**Обоснование.** Проект уже проходил через это: несколько дефектов числились
закрытыми без единой живой проверки, и единственным следом была строка в
Known Issues. Процедура должна быть там же, где её читают при планировании
следующей работы, и обязана содержать графу для результатов — иначе «проверил»
и «не проверил» неразличимы.

**Альтернативы.**
- Отдельный документ в `docs/guides/`: потеряется из фичи, к которой относится,
  и перестанет обновляться вместе с ней.
- Только текст в Known Issues: там он потеряется среди тридцати записей.
