# Implementation Plan: Живой запуск — приёмка и пути, по которым данные не доходят

**Branch**: `010-live-acceptance` | **Date**: 2026-10-07 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/010-live-acceptance/spec.md`

## Summary

Три истории P1 закрывают один класс дефектов: **механизм есть, выглядит
исправным, а данных ему никто не передаёт**. Ручная блокировка не включается ни
одним путём; условие вентиляции по влажности читает значение, которого в системе
нет; доставка состояний работает впервые и в доме не проверена. Четвёртая
история приводит записи Known Issues в соответствие с измеренным состоянием,
чтобы следующая сессия не планировала по неверным основаниям.

Подход: точечное достраивание путей передачи данных, а не новые подсистемы. Все
три места ждут данных — получатель уже написан и покрыт проверками. Требуется
две правки разбора (конверт события HA, контекст перехода), объявление
требований условий и наблюдаемые признаки для приёмки.

## Technical Context

**Language/Version**: Python 3.14 · **Primary Dependencies**: FastAPI,

`/data/behavioral_platform` · **Testing**: pytest + pytest-asyncio + playwright

помеченного · **Scale/Scope**: 1 дом, 6 описанных устройств, 21 сущность в
подписке, 1502 сущности в Home Assistant

## Constitution Check

**Пройден до Phase 0.**

| Принцип | Оценка |
|---------|--------|
| I. Event-Driven FSM как фундамент | **Нарушен сейчас, фича чинит.** Переходы не исполняются при отсутствии данных условия — это не запрещённый обход FSM, а его неполное питание. Фича оставляет FSM источником истины |
| II. AI-first, TDD/SDD | Спека и план написаны до кода; FR-007 и FR-012 требуют падения проверок на прежнем коде |
| III. Контроль остаётся за пользователем | **Прямое нарушение в коде на момент написания.** Ручная блокировка не включается ни одним путём, то есть приоритет пользователя не работает. US1 — это приведение кода в соответствие принципу, а не новая функция |
| IV. Многоуровневая архитектура | Соблюдается. Чтение контекста события — дело адаптера (внешняя система); требования условий объявляются в ядре; политика источников — в манифесте |
| V. Манифест — единственный источник конфигурации | Соблюдается. Набор ручных источников и сроки берутся из манифеста, пороги — из манифеста. Новых значений в коде не появляется |
| VI. Двухрежимное развёртывание | Фича не трогает границу режимов. Приёмка начинается с режима, где команды не исполняются |
| VII. Многоуровневый интерфейс | Не затронута |
| ADR-001 Core не зависит от Adapters | Соблюдается |
| ADR-003 имена автоматов | Соблюдается: данные добавляются в контекст перехода, а не в имя |

**Вердикт**: проход. Один принцип (III) фича не нарушает, а восстанавливает.

## Фазы работы

| Волна | Содержание | Истории | Признак готовности волны |
|-------|------------|---------|--------------------------|
| 0 | Проверки, падающие на прежнем коде; фикстуры путей | US1, US2 | проверки написаны и красные по делу, а не из-за отсутствия фикстур |
| 1 | Доставка данных: конверт события, контекст перехода, путь «веб-интерфейс → движок» | US1, US2 | событие с пользователем доходит до блокировки; значение датчика доходит до условия |
| 2 | Наблюдаемость: требования условий, отдельная причина отказа, признаки блокировки | US1, US2 | отказ объясним одной причиной; блокировка видна в показателях |
| 3 | Переживание блокировкой перезапуска | US1 | факт восстановлен при старте |
| 4 | Процедура приёмки | US3 | документ написан, шаги исполняемы, есть условия остановки |
| 5 | Правка записей Known Issues | US4 | записи соответствуют коду, в каждой указан способ проверки |
| 6 | Живая приёмка по процедуре | US1–US3 | результаты записаны, включая «не проверено» |

Волны 1 и 2 разделены, хотя правки малы: сначала данные доходят, потом видно,
что они дошли и почему переход не состоялся. Иначе появился бы механизм,
которым нельзя убедиться.

## Риски

| Риск | Почему возможен | Чем снимается |
|------|----------------|---------------|
| Фикс блокировки начнёт блокировать саму автоматику | Источник команд зеркала состояния проходит через тот же диспеттер | Набор ручных источников расширяется точечно, а не заменой правила; проверка на внутренние команды обязательна |
| Разбор конверта сломает маршрутизацию, которая работает | Та же строка разбирает `data`, на которой держится доставка состояний | Правка аддитивна: `data` передаётся как раньше, контекст добавляется сверху |
| Значение датчика попадёт в контекст под чужим именем | Имя берётся из соответствия «роль → событие», а не из сущности | Проверка на сквозном пути: конкретная сущность манифеста и конкретное значение |
| Блокировка станет вечной при отсутствии событий | Отсчёт от момента ручного действия, а не от числа событий | Срок из манифеста, проверка на истечении срока без новых событий |
| Процедура приёмки станет формальностью | Её можно пройти, не заметив ничего | Каждый шаг с признаком успеха и условием остановки; «не проверено» — допустимый результат, но не «проверено» |

## Complexity Tracking

| Нарушение | Почему нужно | Почему не выбрано проще |
|-----------|--------------|--------------------------|
| Новый модуль персистентности рядом с существующим | Факт ручного действия переживает перезапуск (R-03) | Добавить в `state.json` нельзя: файл перезаписывается при горячей перезагрузке манифеста, то есть терял бы факт именно тогда, когда он нужен |
| Требования к данным объявляются условием, а не выводятся из результата | Нужна причина отказа, различимая с «значение не подходит» (R-05) | Разбор результата условия меняет контракт всех условий и трогает работающий код; проверка наличия до вызова — локальное изменение движка |
