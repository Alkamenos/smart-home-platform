# Contracts: Контроль доступа к устройствам (Access Control)

**Feature**: specs/004-device-access-control | **Date**: 2026-09-29

Форматы и семантика web-каналов доступа. Тексты/форматы следуют существующим маршрутам; contract/integration-тесты (`tests/contract/test_access_control.py`, `tests/integration/test_access_control.py`) фиксируют эти договорённости.

## 1. HTTP: идентификация и статусы

| Ситуация | Статус | Условие |
|---|---|---|
| Защищённый device-endpoint без `X-User-ID` | 401 | middleware идентификации |
| Недостаточная роль на операцию | 403 | маршрут/сервис по иерархии ролей |
| Устройство не найдено ИЛИ доступ отсутствует (детали чужого) | 404 | не раскрывать существование |
| Невалидная роль при grant | 400 | валидация значения |

Идентификация: `X-User-ID` (обязателен на защищённых device-endpoints), `X-Is-Admin` (`true` → глобальный админ). Endpoints вне устройств (healthcheck, dashboard) проверке не подлежат.

## 2. HTTP: GET /api/v1/devices (фильтрация по доступу)

- Без `X-User-ID` → пустой список (существующее поведение).
- С `X-User-ID` → только устройства с выданным доступом (по `get_user_accessible_devices`); фильтр по `source_id` применяется поверх.
- Ответ: список `DeviceResponse` (формат не меняется).

## 3. HTTP: управление доступом (admin-only)

### POST /api/v1/devices/{device_id}/access

Запрос: `{ "user_id": str, "role": "viewer"|"controller"|"admin" }` (кто выдал — из заголовков).

Ответ 200: запись доступа с реальными полями:

```json
{
  "id": "<uuid записи>",
  "device_id": "<uuid>",
  "user_id": "<str>",
  "role": "<viewer|controller|admin>",
  "granted_by": "<admin user_id>",
  "created_at": "<ISO datetime>"
}
```

- Повторное назначение той же паре (device, user) → роль обновляется, дубликата нет.
- Устройство не найдено → 404.

### DELETE /api/v1/devices/{device_id}/access/{access_id}

- 204 при удалении; **404** если запись не существует (или относится к другому устройству).

### GET /api/v1/devices/{device_id}/access

- 200: массив записей доступа устройства (тот же формат, что POST-ответ); 404 если устройство не найдено.

Все три: только админ (403 иначе). Заглушки (`UUID(int=0)`, `[]`, `None`) удаляются.

## 4. WebSocket: подписка и доставка по правам

Протокол сообщений не меняется (auth / subscribe / unsubscribe / events / error / subscribed).

### Подписка (`{"type": "subscribe", "device_id": "..."}`)

- Неаутентифицирован → `{"type": "error", "message": "Must authenticate first..."}` (существующее поведение).
- Аутентифицирован, проверка доступа не пройдена → `{"type": "error", "device_id": "...", "message": "Access denied to device ..."}`; устройство НЕ добавляется в подписки соединения.
- Проверка пройдена → `{"type": "subscribed", ...}` (существующее поведение).

### Доставка событий (state_changed broadcast)

- Событие устройства доставляется ТОЛЬКО соединениям: аутентифицированным + имеющим доступ к этому устройству (роль viewer и выше) — проверка при каждой доставке (clarify Q1).
- Отзыв доступа действует немедленно: следующее событие после отзыва не доставляется.
- Соединения, не подписанные на устройство, не получают его события (существующая семантика подписок расширяется проверкой прав).

## 5. Логи (существующие шаблоны маршрутов)

| Событие | Уровень | Содержимое |
|---|---|---|
| Отказ доступа (маршрут/WS) | WARNING | user_id, device_id, причина |
| Назначение/отзыв доступа | INFO | device_id, user_id, роль/запись |
| Запрос без X-User-ID | WARNING | метод, путь (существующий middleware-лог) |

Новых систем логирования не создаётся.

## 6. События истории операций

Каждое назначение/отзыв доступа сопровождается записью события синхронизации (DeviceAccessChangedEvent через сервис — существующее поведение публикации).
