# Research: Контроль доступа к устройствам (Access Control)

**Feature**: specs/004-device-access-control | **Date**: 2026-09-29

## R1. Где взять DeviceService в маршрутах

**Наблюдение**: маршруты устройств не получают DeviceService; сервис создаётся в `create_app` и кладётся в `app.state.device_service` (`src/webui/app.py:290-298`) вместе с `app.state.event_bus` и `app.state.persistence`.

**Decision**: в маршрутах получать сервис через `request.app.state.device_service` (для WS — через `websocket.app.state.device_service`); дополнительный DI/контейнер не вводится.

**Rationale**: переиспользуется существующая точка сборки; ServiceLocator-через-app.state уже является паттерном этого приложения (container/discovery-роуты делают так же).

**Альтернативы**: новый глобальный провайдер/dependency — отклонено (второй способ сборки в одном приложении).

## R2. Middleware: подключение и границы ответственности

**Наблюдение**: `DeviceAccessMiddleware` (`src/webui/middleware_access_control.py`) создан, но нигде не зарегистрирован; он проверяет наличие `X-User-ID` (401), извлекает device_id из пути и кладёт идентификацию в `request.state`. Ролевые проверки не выполняет.

**Decision**: зарегистрировать middleware в `create_app` ПОСЛЕ CORS и ДО включения маршрутов устройств; зона ответственности middleware — только идентификация (401 без X-User-ID на device-endpoints) и перенос идентификации в `request.state`. Ролевые проверки — в маршрутах/сервисе (403 по иерархии ролей). Список защищаемых путей сверить с фактическими маршрутами devices (`/api/v1/devices`, `/api/v1/devices/sources`, ...).

**Rationale**: единственный механизм идентификации на весь web-слой без дублирования; роли — компетенция домена, не транспортного слоя.

**Альтернативы**: ролевые проверки в middleware — отклонено (доменные знания в транспорте, дублирование сервиса).

## R3. Фильтрация GET /api/v1/devices

**Наблюдение**: фильтрация по доступу закомментирована (`routes/devices/devices.py:79-82`), комментарий ссылается на несуществующую зависимость; `get_user_accessible_devices(user_id)` в сервисе реализован.

**Decision**: разблокировать фильтрацию: список строится из `_devices_store`, фильтруется по `get_user_accessible_devices` (видимы только устройства с выданным доступом; пустой список для анонима — существующее поведение `x_user_id is None → []` сохраняется). Фильтр по `source_id` сохраняется поверх фильтра доступа.

**Rationale**: точная семантика FR-003; сервисный метод уже существует и покрывает роль admin (все устройства).

**Альтернативы**: фильтрация в middleware (перехват ответа) — отклонено (непрозрачный поток данных, сложнее тестировать).

## R4. Grant/Revoke/List: реальные данные вместо заглушек

**Наблюдение**: три эндпоинта в `routes/devices/access_control.py` отдают заглушки (`UUID(int=0)`, `[]`, `None`), сервисная логика закомментирована; сервисные методы реализованы: `grant_access(device_id, user_id, role, granted_by)` (повторное назначение обновляет роль), `revoke_access(access_id)`, `get_device_accesses(device_id)`.

**Decision**: разблокировать вызовы сервиса; заменить заглушки реальными данными: grant → сериализованная запись DeviceAccess; revoke → 404 при отсутствии записи; list → список записей устройства. Доступ к несуществующему устройству → 404 (проверка существования через сервис). Анти-дубликат — ответственность сервиса (обновление роли).

**Rationale**: один к одному соответствует серверной логике и контракту существующих contract-тестов.

**Альтернативы**: расширение сервиса под новые поля ответа — отклонено (сервис покрывает, менять его не нужно).

## R5. WebSocket: подписка и доставка с проверкой доступа

**Наблюдение**: `websocket.py` хранит `subscribed_devices` как локальную переменную socket-цикла; проверка `check_device_access` закомментирована (T071); `broadcast_state_change` → `connection_manager.broadcast` шлёт всем клиентам без понятия «пользователь соединения» и его прав. `ConnectionManager.active_connections` — просто список WebSocket.

**Decision**:
1. При подписке: разблокировать проверку `check_device_access(device_uuid, user_id, required_role="viewer")`; отказ → error-сообщение в сокет, устройство не подписывается (FR-008).
2. Для доставки по правам: ConnectionManager расширяется ассоциацией соединение → {user_id, доступные устройства}; соединение регистрирует пользователя при аутентификации/auth-сообщении; `broadcast_state_change` рассылает событие ТОЛЬКО соединениям с доступом к устройству (проверка при каждой доставке — уточнение clarify Q1). Соединения без устройства — не получают.

**Rationale**: минимальное расширение существующего менеджера (карта соединение→идентификация) без переворота протокола; требование «отзыв действует немедленно» выполняется естественно (проверка на доставке).

**Альтернативы**: форс-отписка с уведомлением — отклонено (clarify-решение A: проверка при доставке); доставка через FSM/EventBus-канал — отклонено (вне scope фичи, другой слой).

## R6. Существующие тесты как acceptance

**Наблюдение**: `tests/contract/test_access_control.py` (10 тестов: 403/404/grant/роли/список) и `tests/integration/test_access_control.py` (3 сценария полного флоу) уже написаны под целевое поведение и в baseline падают/ошибочны (contract: 6 failed / 27 errors включают этот файл; регистрация тестов запускается; конвенция `__init__.py`).

**Decision**: существующие contract/integration тесты объявляются acceptance-тестами фичи (TDD-красные сейчас); цель — сделать их зелёными без изменения ожиданий тестов. Новые тесты добавляются только для зазоров: проверка при доставке WS-события, сохранение персистентности между перезапусками, анти-дубликат grant.

**Rationale**: готовые acceptance-тесты сильнее синтетических; новые падения относительно baseline = достижение целей фичи, рост числа — сигнал поломки.

**Альтернативы**: писать новый набор с нуля — отклонено (дублирование готовых тестов).

## R7. Persistance между перезапусками

**Наблюдение**: `DeviceAccessPersistence` (`src/core/persistence/devices.py:271`) хранит доступы в JSON-файле (data-dir); `PersistenceManager(data_dir="data")` инициализируется в create_app.

**Decision**: «Переживают перезапуск» (FR-010/SC-004) = доступы сохраняются средствами существующей DeviceAccessPersistence; верификация — интеграционный кейс «save → recreate app/service → list сохранился». Специальные хранилища/кэш не вводятся (clarify-решение Q2).

**Rationale**: переиспользование готового механизма; консистентно с допущениями спеки.

**Альтернативы**: новое хранилище (SQLite/в памяти) — отклонено (clarify-решение Q2).
