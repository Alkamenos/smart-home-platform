### User Story 1 - Пользователь видит и контролирует только свои устройства (Priority: P1)

Пользователь обращается к списку устройств и деталям устройств через HTTP API и видит только те устройства, к которым ему выдан доступ. Запрос без идентификации пользователя отклоняется на защищённых endpoints. Операция, превышающая роль пользователя (команда без роли controller, настройка без роли admin), отклоняется с понятной ошибкой.

**Why this priority**: Это ядро безопасности US4 — без сегментации «кто что видит/умеет» механизм доступа не имеет смысла. Реализация одна — активация существующих механизмов (middleware + фильтрация списка + проверка ролей в сервисе).

**Independent Test**: Тестируется контрактными тестами с клиентом к web-приложению: выдача доступа → список содержит ровно выданное устройство; отзыв → исчезает; запрос без идентификатора → отклонён; роль недостаточна → отклонён.

**Acceptance Scenarios**:

1. **Given** пользователь с доступом ровно к одному устройству, **When** запрашивает список устройств, **Then** получает ровно это устройство
2. **Given** пользователь без выданных доступов, **When** запрашивает список устройств, **Then** получает пустой список
3. **Given** защищённый endpoint устройства, **When** запрос выполняется без идентификации пользователя, **Then** ответ — ошибка авторизации (401), endpoint не раскрывает данные
4. **Given** пользователь с ролью viewer, **When** выполняет команду на доступное ему устройство, **Then** получает отказ с ошибкой недостаточных прав (403)
5. **Given** пользователь с ролью controller, **When** выполняет команду на доступное ему устройство, **Then** команда исполняется

---

### User Story 2 - Администратор управляет доступом (Priority: P2)

Администратор назначает и отзывает доступ пользователей к устройствам через REST API и просматривает список текущих доступов устройства. Назначенный доступ сохраняется между перезапусками платформы.

**Why this priority**: Управляющая поверхность; имеет ценность после того, как проверки начали работать (US1). Реализация — подключение реальной логики сервиса к уже зарегистрированным маршрутам.

**Independent Test**: Тестируется контрактными тестами: POST доступа → запись с реальным идентификатором появляется в списке; DELETE → запись удаляется; несуществующая запись → 404; повторный запуск приложения → доступы сохранены.

**Acceptance Scenarios**:

1. **Given** администратор, **When** назначает доступ пользователю к устройству с ролью, **Then** получает запись с реальными данными (не заглушку) и устройство становится видимым этому пользователю
2. **Given** администратор, **When** назначает доступ повторно тому же пользователю на то же устройство, **Then** роль обновляется без дублирования записей
3. **Given** администратор, **When** отзывает несуществующую запись доступа, **Then** получает 404
4. **Given** назначенный доступ, **When** платформа перезапускается, **Then** доступ сохранён
5. **Given** не-администратор, **When** пытается назначить/отозвать доступ, **Then** получает отказ (403)

---

### User Story 3 - Проверка прав в WebSocket-подписках (Priority: P3)

Пользователь подписывается на события устройства через WebSocket и получает события только тех устройств, к которым у него есть доступ. При отказе клиент получает сообщение об ошибке в сокете, соединение сохраняется.

**Why this priority**: Замыкает консистентность HTTP и real-time каналов; работает после US1 (переиспользует ту же проверку доступа).

**Independent Test**: Тестируется интеграционным тестом WebSocket-канала: подписка с доступом → подтверждение подписки; без доступа → error-сообщение, подписки нет.

**Acceptance Scenarios**:

1. **Given** пользователь с доступом к устройству, **When** подписывается на его события, **Then** получает подтверждение подписки
2. **Given** пользователь без доступа к устройству, **When** подписывается, **Then** получает сообщение об ошибке с идентификатором устройства, подписки нет
3. **Given** неаутентифицированный сокет-клиент, **When** пытается подписаться, **Then** получает сообщение о необходимости аутентификации (существующее поведение)
4. **Given** активная подписка, **When** доступ к устройству отзывают, **When** наступает очередное событие устройства, **Then** событие не доставляется (права проверяются при каждой доставке)

---

### Edge Cases

- Что происходит при запросе деталей несуществующего устройства? Ответ 404 одинаково для отсутствующего устройства и устройства без доступа — факт существования не раскрывается
- Что происходит при дублирующем назначении доступа (тот же пользователь + устройство)? Роль обновляется, дубликатов нет
- Как система отличает пользователей? Идентификация из заголовка запроса (`X-User-ID`), признак администратора — отдельный заголовок (`X-Is-Admin`); отсутствуют → неавторизован/не-админ
- Что происходит с endpoints, не относящимися к устройствам (healthcheck, dashboard)? Проверка доступа не применяется
- Что происходит при отзыве доступа во время активной WebSocket-подписки? Права проверяются при каждой доставке — событие не доставляется сразу после отзыва (без управления временем жизни подписки)
- Что происходит при испорченном идентификаторе устройства в пути? Запрос отклоняется (некорректный идентификатор)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST применять проверку доступа ко всем endpoints операций над устройствами (детали, команда, события, настройка, управление доступом) через единый механизм (middleware)
- **FR-002**: Система MUST отклонять (401) запросы к защищённым endpoints устройств без идентификатора пользователя
- **FR-003**: Система MUST возвращать в списке устройств только те устройства, к которым у пользователя выдан доступ; без идентификатора пользователя — пустой список
- **FR-004**: Система MUST проверять роль пользователя на операции: чтение (детали, события) — viewer и выше; выполнение команд — controller и выше; настройка устройства и управление доступом — admin
- **FR-005**: Система MUST разрешать назначение доступа (роли viewer/controller/admin) только администраторам; повторное назначение обновляет роль
- **FR-006**: Система MUST разрешать отзыв доступа только администраторам; несуществующая запись → 404
- **FR-007**: Система MUST предоставлять администраторам список текущих доступов устройства
- **FR-008**: Система MUST проверять доступ при WebSocket-подписке И при каждой доставке события (роль viewer и выше); при отказе в подписке — сообщение об ошибке в сокете, устройство не подписано; при отказе во время доставки — событие не доставляется (отзыв действует немедленно)
- **FR-009**: Система MUST фиксировать каждое изменение доступа записью события синхронизации (история операций)
- **FR-010**: Система MUST сохранять выданные доступы между перезапусками платформы средствами штатной персистентности домена устройств (специальное хранилище не вводится)
- **FR-011**: Система MUST возвращать 404 для несуществующего устройства независимо от наличия доступа (не раскрывать существование)

### Key Entities *(include if feature involves data)*

- **DeviceAccess**: Связь пользователя с устройством — устройство, пользователь, роль (viewer/controller/admin), кто выдал, дата создания/изменения; хранится персистентно
- **Device**: Устройство платформы (уже существует); доступ выдаётся на устройство
- **Пользователь (User)**: Внешняя сущность, идентифицируется строковым идентификатором из заголовка запроса; роль на конкретное устройство определяется записью доступа; глобальный признак администратора приходит из заголовка
- **Событие изменения доступа (SyncEvent)**: Запись в истории операций о каждом назначении/отзыве доступа

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Корректность фильтрации 100%: пользователь видит ровно те устройства, на которые у него есть доступ (ни одним больше, ни одним меньше)
- **SC-002**: 100% защищённых endpoints устройств отклоняют запросы без идентификации пользователя
- **SC-003**: Запрос с недостаточной ролью получает отказ с корректным статусом в менее чем 1 секунду
- **SC-004**: Операции управления доступом (назначение/отзыв/список) выполняются менее чем за 2 секунды; выданные доступы переживают перезапуск платформы через штатную персистентность домена устройств
- **SC-005**: Ложные блокировки отсутствуют: легитимный запрос с выданной ролью проходит в 100% случаев

## Assumptions

- Аутентификация (пароли, токены, SSO) вне scope: идентификация пользователя и признак администратора приходят из заголовков доверенной среды (текущая семантика сохраняется); фича — авторизация (права), не аутентификация
- Серверная часть домена доступа переиспользуется: методы сервиса (назначение, отзыв, список доступов, устройства пользователя, проверка доступа), модель записи доступа и её персистентность уже реализованы — фича интегрирует их в web-каналы
- Иерархия ролей фиксирована: viewer → controller → admin; право покрывает операцию, если роль пользователя не ниже требуемой
- Администратор — глобальный: имеет доступ ко всем endpoints устройств, персональные записи доступа ему не нужны
- Форматы ответов и текстов ошибок следуют существующим маршрутам; предыдущая тестовая заглушка не сохраняется
- Персистентность — существующий файловый механизм домена устройств (файл доступов рядом с устройствами); специальные хранилища/миграции не требуются
- Проверка принадлежности/существования устройства выполняется на уровне сервиса; дубликаты записей доступа не допускаются (ключ — пара пользователь+устройство)
- Каждый акт изменения доступа сопровождается записью в истории операций (событие изменения доступа), как принято в домене устройств
- Вне scope: аудит-логирование содержимого запросов, интеграция с внешними IAM, разграничение на уровне источников (source-level ACL)
