# Implementation Plan: Verified Coverage — исполняемое покрытие и непокрытые пути

**Branch**: `009-test-coverage` | **Date**: 2026-10-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/009-test-coverage/spec.md`

## Summary

Проект заявляет покрытие, которого нет: 9 сценариев спеки 001 помечены выполненными, но никогда не выполняются; 4 теста шифрования токенов лежат в файле, который pytest не собирает; файл браузерных тестов не содержит ни одного теста; 755 строк командной строки не имеют ни одного теста через свою точку входа; локальная команда проверки молча исключает целый раздел тестов.

Технический подход: переписать 9 пропущенных тестов под текущий контракт (измерение показало — падают не из-за недоделанных TODO, а из-за рассинхрона с API и отсутствующей идентичности), вынести персистентность тестов во временный каталог, вытащить тесты шифрования в собираемый файл, добавить тесты командной строки через штатную точку входа без подпроцесса, свести локальную и автоматическую проверки к одному набору и закрыть четыре конкретных пробела.

Ключевая находка, определившая подход: **два теста «проходят» тем, что пропускают сами себя** (`pytest.skip("No devices available")` стоит до всякой проверки прав), а один (`test_sync_persistence`) тавтомологичен и не может упасть по построению. Это опаснее падения: такие тесты укрепляют иллюзию покрытия.

## Technical Context

**Language/Version**: Python 3.12 (целевая; репозиторий содержит артефакты и для 3.14)

**Primary Dependencies**: pytest + pytest-asyncio (`asyncio_mode = "auto"`), `--import-mode=importlib`, pytest-cov, pytest-playwright, httpx/`TestClient` для HTTP-уровня, playwright sync API (только для браузерных тестов)

**Storage**: временные каталоги (`tmp_path`) для всех интеграционных тестов — это и есть изменение поведения; каталог `data/` репозитория тестами больше не используется

**Testing**: pytest; baseline — 1786 собранных / 1777 выполненных / 9 пропущенных; после фичи инвариант `skipped == 0` и `passed == collected`, 25 браузерных отдельно

**Target Platform**: Linux-сервер / macOS (Docker Compose); режимы: автономный и с Home Assistant — оба без сети в тестах

**Project Type**: web-service (FastAPI) + библиотека (ядро) + CLI

**Performance Goals**: добавление проверок не увеличивает полный прогон более чем на 30 секунд; браузерные тесты сохраняют текущие ~37 секунд

**Constraints**: длина функций ≤50 строк, type hints, docstrings Google style, loguru, никаких bare `except`, покрытие ≥80% для новых файлов, тесты не пишут в рабочий каталог репозитория, тесты не ходят в сеть

**Scale/Scope**: 9 переписываемых тестов, 4 извлекаемых, ~20 новых (CLI и пробелы), 3 истории затронутых файлов конфигурации; 4 US, 26 FR, 17 SC

## Стратегия тестирования

Это фича о тестах, поэтому отдельный уровень для неё не вводится. Проверка самой фичи:

| Уровень | Что проверяет |
|---------|--------------|
| Прогон целевого набора | Число выполненных выросло ровно на число снятых пропусков; 0 самопропусков; 0 тестов без утверждений |
| Полный прогон | 0 новых падений относительно состояния до фичи; ни один tracked-файл не изменяется прогоном |
| Проверка воронки | Локальная команда и автоматическая запускают один набор; невыполненное видно с причиной |
| Вживую (quickstart) | Каждая команда интерфейса отрабатывает на временных данных; права действительно ограничивают |

## Оценка рисков

| Риск | Вероятность | Влияние | Смягчение |
|---|---|---|---|
| Переписанный тест проверяет меньше, чем прежний | Средняя | Средняя | Критерий приёмки — не «зелёный», а «проверяет то же утверждение»; ревизия в quickstart |
| Снятие пропуска вскроет настоящий дефект производственного кода | Высокая | Высокое | По условию FR-026 дефект фиксируется отдельной задачей, тест остаётся красным до исправления — но тогда задача не закрывается; такой случай явно фиксируется в отчёте |
| Перенос персистентности во временный каталог вскроет зависимость от рабочего каталога | Средняя | Средняя | Измеряется до правки: прогон в чистом окружении и сравнение состояния каталога |
| Конкурентные тесты окажутся нестабильными | Средняя | Средняя | Каждая проверка конкуренции имеет ограничение по времени; нестабильный тест помечается явно, а не ослабляется до бесконечных повторов |
| Время прогона вырастет заметно | Низкая | Низкое | Целевой бюджет +30 секунды к текущим ~87 |
