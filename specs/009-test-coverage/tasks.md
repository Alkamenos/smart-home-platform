## Path Conventions

Единый Python-проект: `src/` и `tests/` в корне репозитория. Актуальная база: **1786 собранных тестов, из них 1777 выполнено / 9 пропущено**.

**Опорная точка фичи — инвариант, а не конкретное число:** число пропусков должно стать **нулём**, а число выполненных — равным числу собранных. Формулировка «1786 выполнено» была неверной: US2 и US4 добавляют новые тесты, поэтому абсолютное число растёт. Проверяется так: `skipped == 0` и `passed == collected`, при этом ни один ранее проходивший тест не падает.

Такая проверка ничем не отличалась бы от полного отсутствия изоляции. Переписано на схему «у каждого источника своё устройство, затем исчезновение своего на фоне чужого».

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: без зависимостей — можно начинать сразу
- **Foundational (Phase 2)**: зависит от Setup — **блокирует все истории**
- **US1 (Phase 3)**: зависит от Foundational — MVP
- **US2 (Phase 4)**: зависит только от Foundational (свои фикстуры в `tests/cli/`)
- **US3 (Phase 5)**: зависит от US1–US2 по смыслу: правдивость заявлений фиксируется после того, как появляется что заявлять
- **US4 (Phase 6)**: зависит от US1 (использует переписанные фикстуры идентичности) и требует волны 0
- **Polish (Phase 7)**: зависит от всех историй

### User Story Dependencies

- **User Story 1 (P1, исполняемость)**: стартует после Foundational, зависимостей от других историй нет
- **User Story 2 (P1, интерфейс)**: стартует после Foundational, независима от US1 — свои файлы и свои фикстуры
- **User Story 3 (P2, воронка)**: стартует после US1–US2; контрактные тесты проверяют то, что обе истории создали
- **User Story 4 (P2, пробелы)**: стартует после US1 — переиспользует переписанные фикстуры идентичности и заглушку внешней системы

### Within Each User Story

- Тест проверяет результат; тест без утверждений недопустим (FR-003)
- Пропуск внутри теста недопустим: отсутствие предварительного условия либо чинится фикстурой, либо утверждается (R-06)
- Производственный код не меняется ради прохождения теста: вскрытый дефект → отдельная задача (FR-026)

## Implementation Strategy

### MVP First (User Story 1 only)

1. Phase 1: Setup
2. Phase 2: Foundational — **критично, блокирует всё остальное**
3. Phase 3: User Story 1
4. **СТОП и ПРОВЕРКА**: сценарии 1–5 из `quickstart.md`, опорная точка — выполненных ровно на 9 больше, пропусков 0
5. Развернуть/показать, если результат достаточен

Польза MVP: заявленные покрытия впервые действительно исполняются, а два теста, которые «проходили» вхолостую, начинают проверять.

### Incremental Delivery

1. Setup + Foundational → фундамент
2. US1 → проверка → демонстрация (исполняемое покрытие)
3. US2 → проверка → демонстрация (проверенный интерфейс)
4. US3 → проверка → демонстрация (единая воронка)
5. US4 → проверка → демонстрация (закрытые пробелы)
6. Каждая история добавляет ценность, не ломая предыдущие

### Parallel Team Strategy

После завершения Foundational:

- Разработчик A: US1 (интеграционные тесты) → затем US4 (пробелы, переиспользует те же фикстуры)
- Разработчик B: US2 (интерфейс, отдельный каталог `tests/cli/`) → затем US3 (воронка)
- Общая точка: `tests/integration/conftest.py` — его правки блокируют обе ветви, поэтому он меняется только в волне 0

## Notes

- `[P]` — разные файлы, отсутствие зависимостей
- `[Story]` — метка для трассируемости
- Коммит после каждой задачи или логической группы
- Останавливаться на любом checkpoint для независимой проверки истории
- Избегать: расплывчатых задач, конфликтов в одном файле, межисторийных зависимостей, ломающих независимость
- **Три дефекта вне буквального объёма спеки закрываются здесь** (см. `plan.md`): два самопропускающихся теста, тавтомологичный `test_sync_persistence`, запись прогонов в `data/` репозитория
