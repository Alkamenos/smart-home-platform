# Data Model: Verified Coverage (009-test-coverage)

**Вход**: `spec.md` (4 US, 26 FR, 17 SC) + `research.md` (измерение пропусков, 10 решений)
**Дата**: 2026-10-03

Это техническая спецификация, а не предметная область: сущности здесь — артефакты тестирования. Ни одна из них не является данными продукта и не хранится в базе.

---

## 1. Тест (Test)

Проверка, заявленная как покрытие. Ключевое свойство: **тест исполняем, только если исполняется и проверяет результат**.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `str` | Идентификатор проверки (имя теста) |
| `file` | `str` | Файл, в котором объявлен |
| `claimed` | `bool` | Отмечен ли выполненным в задачах спецификации |
| `runs` | `bool` | Исполняется ли при полном прогоне |
| `asserts` | `bool` | Содержит ли хотя бы одну проверку результата |
| `declared_state` | `enum(claimed-runs)` | Расхождение между заявленным и фактическим |

### Правила

- **R-1. Три независимых признака.** Тест может быть отмечен выполненным, не исполняться (пропуск) и при этом содержать проверки — сегодня это ровно 9 тестов спеки 001. Заявленное покрытие определяется пересечением `claimed ∧ runs ∧ asserts`.
- **R-2. Тест без проверок результата не считается покрытием**, даже если зелёный. `test_sync_persistence` сравнивает длины двух пустых списков и не может упасть по построению.
- **R-3. Тест, который пропускает сам себя до всякой проверки, не считается выполненным.** Пропуск внутри теста отличается от пропуска на отсутствующей среде: первое означает, что сценарий не был достигнут.
- **R-4. Причина пропуска допустима, только пока она верна.** Ссылка на закрытую задачу — не причина.
- **R-5. Файл без исполняемых тестов — не покрытие.** Заготовка с нулём тестов удаляется (FR-008).

### Состояния и переходы

```text
                    пропуск снят
   (пропущен) ───────────────────────► (исполняется)
                                          │      │
                    переписан под текущий │      │ содержит проверки
                    контраст, если устарел │      │
                                          ▼      ▼
                                     (исполняется, но пуст) ──► удалён или переписан
```

Переход вправо-вниз — только если тест содержит проверки; иначе возвращается в состояние «пуст» и либо дополняется, либо удаляется.

## 2. Идентичность в тестах (Test Identity)

Кто выполняет запросы в интеграционном тесте. Сущность нужна потому, что 5 из 9 падений вызваны её отсутствием.

| Поле | Тип | Описание |
|------|-----|----------|
| `user_id` | `str` | Идентификатор пользователя |
| `is_admin` | `bool` | Административные права |
| `scope` | `enum(admin, limited, none)` | Роль в конкретном сценарии |

### Правила

- **R-6. Идентичность — часть подготовки, а не украшения каждого запроса.** Заголовки идентичности поставляются фикстурой; тест описывает сценарий, а не транспорт.
- **R-7. Один сценарий — одна роль.** Смена роли внутри теста допускается, но должна быть видна в его имени.
- **R-8. Роль ограниченного пользователя обязана иметь хотя бы одно отличие в доступе**, иначе тест не различает «работает» и «устройства не существует».

## 3. Внешняя система (External System) — точка подмены

Место, где тест перехватывает обращение к Home Assistant.

| Поле | Тип | Описание |
|------|-----|----------|
| `available` | `bool` | Доступна ли внешняя система |
| `fail_mode` | `enum(none, refused, timeout)` | Как именно недоступна |
| `stubbed_at` | `str` | Шов, на котором выполнена подмена |

### Правила

- **R-9. Тест не имеет сетевых зависимостей.** Подмена выполняется на шве, где production-код обращается к внешней системе, — до подключения, а не после него: подмена перечисления устройств не мешает коду дойти до подключения (именно так устроен текущий падающий тест).
- **R-10. Недоступность — штатный сценарий, а не сбой теста.** Она задаётся явно и проверяется явно.
- **R-11. Персистентность теста изолирована во временном каталоге.** Ни один тест не пишет в рабочий каталог репозитория.

## 4. Набор проверок (Verification Suite)

Множество тестов, запускаемое одной командой. Сущность нужна для US3.

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | `str` | Имя команды |
| `includes` | `set[path]` | Что запускается |
| `excludes` | `dict[path, str]` | Что не запускается и **почему** |
| `requires` | `set[capability]` | Внешние условия (браузер, сеть) |

### Правила

- **R-12. Исключение обязано нести причину.** Запись без причины недопустима: именно молчаливые исключения позволили расхождению просуществовать.
- **R-13. Единственный источник исключений.** Перечень хранится в одном месте; и локальная команда, и автоматическая читают его.
- **R-14. Невыполненное видно.** Если часть набора не исполнена по технической причине, это отражается в результате, а не исчезает.
- **R-15. Локальный и автоматический наборы совпадают**, кроме явно объявленных исключений.

## 5. Сценарий команды (Command Scenario)

Пользовательский путь через командную строку. Сущность нужна для US2.

| Поле | Тип | Описание |
|------|-----|----------|
| `command` | `str` | Имя команды |
| `args` | `list[str]` | Аргументы |
| `data_dir` | `path` | Временный рабочий каталог |
| `expect_exit` | `int` | Ожидаемый код возврата |
| `expect_stderr_has` | `str` | Обязательный фрагмент сообщения |
| `expect_no_traceback` | `bool` | Внутренняя трассировка не показывается |

### Правила

- **R-16. Проверяется штатная точка входа**, а не внутренняя функция: иначе не проверяются разбор аргументов и код возврата — то есть ровно то, где команда ломается у пользователя.
- **R-17. Команда, меняющая конфигурацию, при сбое не оставляет её изменённой** — проверяется сравнением содержимого до и после.
- **R-18. Интерактивный ввод заменяется заранее подготовленными ответами**; ответов должно хватать на все вопросы, иначе тест падает с невнятной ошибкой.
- **R-19. Код возврата — часть контракта.** Успех — ноль, ошибка — ненулевое значение с сообщением.

## Связи сущностей

```text
Идентичность ──┐
               ├──► Тест (исполняется, проверяет)
Внешняя система┘        │
                        │ объявляет в
Набор проверок ─────────┘
        │
        │ запускает через
        ▼
Сценарий команды ──► использует Идентичность и Внешнюю систему
```

Ключевое отношение: **Набор проверок** определяет, что вообще исполняется, а **Идентичность** и **Внешняя система** определяют, каким сценарием это исполняется. Тест без обеих сущностей превращается в декоративный — ровно тот случай, который фича устраняет.
