## Сценарий 1 — Базовая интеграция и загрузка устройств (T016)

Пользователь добавляет источник HA и загружает устройства.

1. `POST /api/v1/devices/sources` (name, url, token) → ожидается **201** и наличие `id`
2. Проверка, что источник появился в `GET /api/v1/devices/sources`
3. `POST /api/v1/devices/sources/{id}/sync` → устройства загружены
4. `GET /api/v1/devices` → загруженные устройства отображаются с корректными параметрами

**Успех**: источник создан, устройства видны в списке (КУ-001/КУ-002).

## Сценарий 2 — Конфигурирование параметров устройства (T033–T034)

1. `GET /api/v1/devices/{id}` → видны название, описание, расположение, тип, команды
2. `PUT /api/v1/devices/{id}/config` (display_name, description, location, tags) → **200**
3. Повторный `GET` → изменения сохранены
4. Проверка границ валидации: пустой `display_name` (1–255), `description` ≤1000 символов → **422** на нарушении

**Успех**: параметры сохраняются и восстанавливаются при перезагрузке (КУ-003).

## Сценарий 3 — Синхронизация состояния в реальном времени

1. Подключение `ws://.../api/v1/ws/devices`
2. `{"type":"auth","user_id":...}` → `authenticated`
3. `{"type":"subscribe","device_id":...}` → `subscribed`
4. Изменение состояния устройства в HA → сообщение `state_changed` приходит **≤5 сек** (КУ-004)
5. `{"type":"ping"}` → `pong`

**Успех**: задержка обновления ≤5 сек при живом соединении.

## Сценарий 4 — Отправка команд на устройство (ТР-007)

1. `POST /api/v1/devices/{id}/command` → **202 Accepted**
2. `GET /api/v1/devices/{id}/command/{command_id}` → статус выполнения
3. Устройство в HA реагирует (свет включается)

**Успех**: команда передана в HA и выполнена (КУ-005 — 95% в нормальных условиях).

## Сценарий 5 — Обработка ошибок и сбои соединения (ТР-008)

1. Недоступный URL источника / истёкший токен → API возвращает информативную ошибку (401/403 → «перевведите токен»)
2. Потеря соединения во время операции → ошибка пользователю, платформа не применяет частичные изменения
3. Восстановление связи → `ConnectionManager` переподключается (exponential backoff 1→16 сек; требование КУ-006 — ≤30 сек)
4. Повтор операции после восстановления → успех

**Успех**: ошибки видны пользователю, восстановление автоматическое. ⚠ Автотестов reconnect пока нет (Known Issue #5).

## Сценарий 6 — История операций и логирование (ТР-010, КУ-007)

1. Выполнить изменения конфигурации и команду
2. `GET /api/v1/devices/{id}/events` → история операций
3. Loguru-логи содержат trace_id, user_id, entity_id, действие

**Успех**: любое изменение параметров отслеживается с указанием пользователя и времени. ⚠ Записи before/after как модель `DeviceSyncEvent` ещё не реализованы (бэклог RU T041/T070, H1).
