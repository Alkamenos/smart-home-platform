# Feature Specification: История операций с устройствами (ТР-010)

**Feature Branch**: `005-device-audit-log`

**Created**: 2026-09-29

**Status**: Implemented (2026-09-30)

**Input**: User description: "Модель DeviceSyncEvent + персистентность (история операций, ТР-010) — Tech Debt High Priority #2 из ROADMAP. Источники: RU T041 (запись операций конфигурации с user_id), RU T070 (запись операций прав доступа), CHK013, сценарий 6 specs/001. Текущее состояние: GET /api/v1/devices/{id}/events — заглушка возвращает [], модель DeviceSyncEvent не существует, операции конфигурации и прав доступа не сохраняются в историю."

## Clarifications

### Session 2026-09-29

- Q: Как заполнять поля «значение до / после» для типов операций, где изменяемого состояния нет (например, отправка команды)? → A: Поля опциональны и заполняются только там, где есть изменяемое состояние (конфигурация — до/после значений полей, права доступа — роль до→после как до/после); для команды фиксируется только содержимое команды, до/после остаются пустыми
- Q: Должна ли запись истории выполняться в рамках операции (до ответа клиенту) или асинхронно после завершения операции? → A: Синхронная запись в рамках операции, до ответа клиенту; ошибка записи логируется, но операция всё равно успешна
- Q: Записывать ли в историю изменения конфигурации, инициированные не через веб-API (например, hot-reload конфига, CLI-правки, config watcher)? → A: Только операции через веб-API (пользовательские) — системные источники добавятся отдельно, когда будут работать

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Просмотр истории операций устройства (Priority: P1)

Администратор или пользователь с правом просмотра открывает историю операций устройства и видит реальные записи: когда менялась конфигурация, когда выдавались или отзывались права доступа, кто выполнил действие, что было до и что стало после. История доступна сразу после перезапуска платформы — записи не теряются.

**Why this priority**: Это основная ценность ТР-010 — без реальных данных в истории требование не закрыто вовсе (сейчас endpoint отдаёт пустой список). Без этой истории невозможно аудировать действия.

**Independent Test**: Выполнить изменение конфигурации устройства, затем получить историю операций через существующий эндпоинт просмотра событий и убедиться, что в ответе есть запись с действием, пользователем, временем и парами до/после.

**Acceptance Scenarios**:

1. **Given** устройство существует, **When** пользователь обновляет его конфигурацию, **Then** история операций устройства содержит запись с типом изменения конфигурации, идентификатором пользователя, временем и значениями полей до/после
2. **Given** в истории есть записи, **When** платформа перезапускается, **Then** все ранее записанные операции остаются доступны в истории
3. **Given** пользователь с правом просмотра устройства, **When** он запрашивает историю, **Then** он получает список операций
4. **Given** история содержит записи разных типов, **When** запрашиваются события с фильтром по типу, **Then** возвращаются только записи выбранного типа

---

### User Story 2 — Автоматическая запись операций прав доступа (Priority: P2)

Каждая операция выдачи, обновления или отзыва прав доступа к устройству попадает в историю операций: видно, кто, кому и какое право выдал или отозвал, когда именно это произошло.

**Why this priority**: Права доступа — операции безопасности; их аудит критичен, но требует работающей истории (US1) как базы.

**Independent Test**: Выдать и отозвать доступ пользователю к устройству, затем проверить, что обе операции присутствуют в истории с указанием инициатора и времени.

**Acceptance Scenarios**:

1. **Given** администратор выдаёт право просмотра устройства пользователю, **When** операция завершена, **Then** история содержит запись о выдаче права с идентификаторами устройства, получателя и инициатора
2. **Given** администратор отзывает право доступа, **When** операция завершена, **Then** история содержит запись об отзыве, предшествующая запись о выдаче сохраняется

---

### User Story 3 — Автоматическая запись команд (Priority: P3)

Каждая команда, отправленная устройству, фиксируется в истории: кто отправил, что именно было отправлено и когда.

**Why this priority**: Команды — вторая часть сценария 6 ТР-010 («изменения конфигурации и команду»); важны для полноты аудита, но не блокируют US1/US2.

**Independent Test**: Отправить команду устройству и убедиться, что в истории появилась запись с пользователем и данными команды.

**Acceptance Scenarios**:

1. **Given** устройство поддерживает команды, **When** пользователь отправляет команду, **Then** история содержит запись об отправке команды с идентификатором пользователя и содержимым команды

---

### Edge Cases

- Что происходит при записи истории, если хранилище недоступно или повреждено? Операция устройства не должна падать — отказ записи истории логируется, но не блокирует основное действие.
- Как обрабатываются операции, инициированные системой без пользователя (например, автоматизация)? Запись создаётся с явным системным идентификатором вместо пользователя.
- Что если устройство удалено, а история операций по нему остаётся? Записи истории сохраняются в хранилище (по идентификатору устройства); при обращении к эндпоинту сохраняется существующее поведение — отсутствующее устройство даёт 404
- Что если история становится очень большой? Запрос истории поддерживает ограничение числа записей и смещение (пагинация) — по умолчанию не более 100 записей на запрос.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА записывать каждую операцию над устройством (изменение конфигурации, отправка команды, изменение прав доступа) с полями: время, инициатор, устройство, тип действия, значение до, значение после (ТР-010). Поля «до/после» заполняются только там, где есть изменяемое состояние (конфигурация, роль прав); для операций без изменяемого состояния (команды) они остаются пустыми — фиксируются релевантные данные операции
- **FR-002**: Записи истории ДОЛЖНЫ переживать перезапуск платформы (персистентное хранилище)
- **FR-003**: Операции изменения конфигурации через веб-API ДОЛЖНЫ фиксировать идентификатор пользователя, выполнившего изменение (RU T041); изменения конфигурации, инициированные автоматическими источниками (hot-reload, config watcher, CLI), в рамках этой фичи не записываются
- **FR-004**: Операции выдачи/отзыва/обновления прав доступа ДОЛЖНЫ фиксировать идентификаторы устройства, получателя права и инициатора операции (RU T070); роль до и после отражаются в полях «до/после»
- **FR-005**: Операции отправки команд ДОЛЖНЫ фиксировать идентификатор пользователя и содержимое команды
- **FR-006**: Система ДОЛЖНА отдавать историю операций устройства через существующий эндпоинт просмотра событий устройства (сейчас возвращает пустой список — заглушка)
- **FR-007**: История должна поддерживать фильтрацию по типу операции и пагинацию (ограничение/смещение)
- **FR-008**: Просмотр истории устройства ДОЛЖЕН требовать права просмотра этого устройства (уже обеспечено существующей проверкой доступа)
- **FR-009**: Запись истории выполняется синхронно в рамках операции (до ответа клиенту); ошибка записи НЕ ДОЛЖНА блокировать выполнение основной операции устройства — ошибка должна логироваться, операция завершается успешно
- **FR-010**: Операции без пользователя (системные) фиксируются с явным системным идентификатором
- **FR-011**: Изменения состояния устройства (state change) НЕ входят в историю операций — история фиксирует только операции (конфигурация, команды, права), чтобы не расти неограниченно

### Key Entities

- **Запись операции устройства (sync-запись / DeviceSyncEvent)**: Факт одной операции над устройством. Ключевые атрибуты: время операции, инициатор (пользователь или система), устройство, тип действия (изменение конфигурации / команда / выдача или отзыв права), состояние до, состояние после, дополнительные данные операции (роль, содержимое команды и т.п.)
- **История операций устройства**: Последовательность записей операций, отсортированная по времени, принадлежащая одному устройству; доступна с фильтрацией и пагинацией

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% изменений конфигурации устройства отражаются в истории: после каждого изменения запрос истории возвращает запись с пользователем, временем и парами до/после
- **SC-002**: 100% операций выдачи/отзыва прав доступа присутствуют в истории устройства
- **SC-003**: История переживает перезапуск: 100% записей, созданных до перезапуска, доступны после него
- **SC-004**: Пустой список больше не возвращается для устройства, по которому выполнялись операции — endpoint отдаёт реальные данные
- **SC-005**: Операции над устройством не замедляются заметно из-за записи истории: время выполнения операции вырастает не более чем на 10% (или операция завершается успешно при недоступном хранилище истории)

## Assumptions

- «Операции» = действия, изменяющие устройства: конфигурация, команды, права доступа. Изменения состояния (state change) не записываются в историю операций (FR-011) — иначе объём растёт неограниченно, а ТР-010 требует логировать именно операции
- Срок хранения истории не ограничен: по умолчанию запрос отдаёт не более 100 записей (пагинация уже заложена в существующем эндпоинте)
- Хранилище истории — файловое, в общей директории данных платформы (паттерн существующей персистентности устройств и прав доступа)
- Идентификатор инициатора берётся из уже существующей идентификации запроса (заголовок пользователя, из которого работают проверки доступа)
- Операции US2 (права доступа) публикуют существующее событие изменения доступа — новая запись истории добавляется рядом, не заменяя его
- Изменения конфигурации фиксируются только из веб-API (clarify 2026-09-29, Q3); автоматические источники (hot-reload, config watcher, CLI) — отдельная задача, когда будут подключены
- Интеграция с ЛОГАМИ (loguru, trace_id, сценарий 6) уже частично существует — спека фокусируется на модели, персистентности и отдаче истории через API; полнота loguru-строк — не предмет данной фичи
