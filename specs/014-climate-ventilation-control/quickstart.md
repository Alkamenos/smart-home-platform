## Шаг 1. Фундамент: доходит ли уставка (без включения отопления)

Самое дешёвое, что можно сломать, и самая частая причина «не работает»:
ключ `climate_setpoint` никто не пишет (`research.md` D1). Если здесь пусто,
все остальные шаги бессмысленны.

**Проверка**: поднять `input_number.temperatura` на 1 °C и посмотреть, что
решения климата перестали отказывать по `guard_data_missing`.

```bash
docker exec behavioral-platform sh -c \
  'curl -s -X POST -H "Authorization: Bearer $HA_TOKEN" \
     -H "Content-Type: application/json" \
     -d "{\"value\": 22}" "$HA_URL/api/services/input_number/set_value"'
```

Ожидание: в журнале решения появляются с числом — «холоднее цели», а не
«данных нет». Если вместо этого `guard_data_missing`, фундамент не работает.

**Проверка доменных правил**: те же записи должны ссылаться на комнату.
Если комнат в решениях нет — не работает сопоставление «шаблон → домен»
(`research.md` D3).

## Шаг 2. Обогрев одной комнаты (Story 1, P1)

Безопаснее всего начинать с комнаты, где обогрев не нужен прямо сейчас —
кабинет или гостевая спальня.

**Порядок:**

1. Убедиться, что в комнате прохладнее цели. Если тепло — конвектор не
   включится, и это правильное поведение, а не отказ.
2. Ждать показание датчика (датчики шлют сами, раз в несколько минут).
3. В журнале — переход в обогрев и команда таймеру.
4. В Home Assistant: `number.<обогреватель>_countdown` показывает заданные
   минуты, `switch.<обогреватель>` = on.

**Проверка в журнале:**

```bash
docker-compose -f docker-compose.prod.yml logs behavioral-platform | \
  grep -E "heater_timer_on|may_heat|IDLE.*HEATING"
```

**Проверка отключения:** дождаться достижения цели или истечения таймера.
Ожидание — `HEATING → IDLE` и `switch` = off.

**Проверка защиты FR-004:** выключить датчик комнаты в Home Assistant во время
работы обогревателя. Ожидание: обогреватель дорабатывает по своему таймеру и
выключается сам, а не остаётся навсегда.

**Проверка гостевой комнаты:** комнаты с `managed_by_hardware: true` платформа
не трогает. В гостиной термостат держит 24 °C — конвектор включаться не должен
ни при каких условиях (`research.md` D9).

**Проверка ручной блокировки (FR-007):** включить конвектор руками из
приложения, дождаться, когда автоматике понадобится его выключить.
Ожидание: платформа не трогает, в журнале — объяснение.

**Результат:** ☒ passed ☐ failed ☐ **not checked** — 2026-10-11

Обогрев доказан в доме: уставка поднята до 25 °C, и комнаты, холоднее порога
24.5, нагрелись сами — кабинет 23.22 → **25.15**, санузел 23.30 → **25.62**,
спальня 23.49 → **25.04**, гостиная 23.99 → **25.79**. По достижении цели
обогреватели выключились сами. Полный цикл без участия человека.

Отклонения от текста шага, зафиксированные честно:

- **Проверка защиты FR-004 при отказе датчика ждёт своей очереди.** Отдельный
  случай вскрыт в бою: датчик гостевой спальни перестал присылать показания, и
  масляный радиатор простоял включённым пять часов при истёкшем таймере. Причина
  оказалась двойной — страховочный таймер отрабатывал, но выключение прибора
  блокировалось ручным вмешательством. Починено (`heater_emergency_off`,
  спека 014, T024): по истечении таймера прибор гасится мимо блокировки.
- **Ручная блокировка (FR-007) проверена косвенно** — она сработала на живых
  данных, когда блокировала и включение, и выключение (`Blocked automated
  command … manual lockout active`). Отдельная проверка «включил руками — не
  трогаем» не проводилась.
- **Гостевая спальня не проверена:** датчик комнаты молчит (см. B36).

## Шаг 3. Отказ датчика (Story 5, P5)

Проверяется проще остального: достаточно сделать показание нечитаемым.

**Проверка отсутствия данных:**

```bash
# В Home Assistant: датчик спальни → unavailable
```

Ожидание:

- в журнале отказ с причиной `guard_data_missing`, назван датчик;
- остальные комнаты продолжают работать (FR-041);
- обогреватель спальни не включается и не выключается по догадке;
- если он был включён — дорабатывает по таймеру (FR-043).

**Проверка возврата:** вернуть датчик. Ожидание: комната возвращается в работу
без перезапуска платформы (FR-042), в журнале виден момент отказа и момент
возврата.

**Проверка заряда (FR-048):** в Home Assistant посмотреть
`sensor.datchik_temperatury_terassa_battery` — на момент написания спеки было
1 %. Ожидание: предупреждение в журнале с именем датчика и зарядом.

**Проверка частоты записей (SC-016):** оставить датчик молчащим на 15 минут и
посчитать записи. Ожидание: не больше одной в минуту.

## Шаг 4. Кондиционер (Story 2, P2)

**Сезонное ограничение проверяется первым и без риска.** Сейчас
`input_boolean.zima` = on — то есть зимой кондиционер включаться не должен ни
при каких условиях.

**Проверка запрета зимой (FR-014):** поднять показание датчика выше потолка
комфорта и включить гейт `ispolzovat_konditsioner`. Ожидание: кондиционер не
включится, в журнале — `ac_forbidden_in_winter`.

**Проверка запрета ручного включения (FR-015):** включить кондиционер из
приложения при `zima` = on. Ожидание: платформа его выключает с объяснением.

**Проверка гейта:** при `zima` = off и гейте выключенном — охлаждения нет,
причина `ac_not_allowed`.

**Проверка охлаждения — только летом.** Спецификацию можно закрыть по
запретам зимой; сама проверка охлаждения переносится на тёплый сезон.
Записать в `quickstart` дату проверки, чтобы не потерять.

## Шаг 5. Вентиляция: сначала чтение, потом управление (Story 3, P3)

> **2026-10-12 (research.md D18/D19): правила вентиляции уточнены владельцем и
> переписаны.** Проверки ниже обновлены; часть из них закрывается только после
> T060 (устройства в бою пока ведёт Home Assistant).

**Шаг 5.1 — убедиться, что платформа видит выключалку.** Включить
`input_boolean.ventiliatsiia` = off. Ожидание: в журнале решение с причиной
`turned_off_by_owner`; прибор **выключается** (`fan.turn_off`), а не крутится на
нуле — так требует T090. Флаг дома `input_boolean.feature_ventilation` = off
даёт причину `ventilation_disabled` и тот же результат. Вернуть = on.

**Шаг 5.2 — выключение при обогреве.** Включить обогрев в комнате с
рекуператором. Ожидание: в журнале причина `heating_active`, вентиляция гаснет
(T089). Проверить, что после выключения обогрева она вернулась сама.

**Шаг 5.3 — режим по модификатору «зима» и дельте (FR-019, T087).** При
`input_boolean.zima` = on ожидать `Рекуперация (зима)`, при off — `Рекуперация
(лето)`. Если комната теплее улицы не меньше `supply_delta_threshold` (5 °C по
умолчанию) — режим `Приток` (быстрое охлаждение).

**Шаг 5.4 — скорость отдельно от режима (FR-021).** Ключевая проверка:
режим и скорость — независимые оси. Ожидание: смена скорости **не** сбрасывает
режим и наоборот.

**Шаг 5.5 — ночной предел (FR-022, T088).** Включить `input_boolean.sleep_mode`.
Ожидание: скорость не выше `speed_night_max` (20). Убедиться, что ограничение
**не повышает** скорость: при расчётной 15 останется 15.

**Шаг 5.6 — проветривание с автосбросом (FR-024/025, T085).** Включить
`input_boolean.provetrivanie`. Ожидание: рекуператор в режиме `Приток MAX`;
через `airing_seconds` — возврат к обычному режиму **и** модификатор сам
становится `false` (`input_boolean.turn_off`).

**Шаг 5.7 — вытяжка по санузлу (FR-026, T086).** Нагреть или намочить санузел
(температура ≥ `exhaust_temp_threshold` = 25 °C и/или влажность ≥
`exhaust_humidity_threshold` = 65 %). Ожидание: вытяжка включается. Вернуть
санузел в норму — вытяжка гаснет. Модификатор
`input_boolean.provetrivanie_vytyazhka` даёт тот же результат с автосбросом
через `exhaust_seconds`.

**Шаг 5.8 — колебания не дёргают вентилятор (SC-008).** Наблюдать журнал
30 минут в покое. Ожидание: ни одного изменения скорости при колебаниях
меньше `delta_deadband` (0.3 °C).

## Шаг 6. Контроль владельца (Story 4, P4)

Сквозная проверка: по одному правилу на каждую историю.

| Проверка | Как | Ожидание |
|----------|-----|----------|
| Ручная блокировка вентиляции | изменить скорость рекуператора руками | платформа не перебивает 15 минут (`manual_lockout_min`) |
| Фиче-флаг климата | `input_boolean.feature_climate` = off | ни одной команды климата (SC-011) |
| Фиче-флаг вентиляции | `input_boolean.feature_ventilation` = off | ни одной команды вентиляции |
| Объяснение отказов | любое решение за сутки | у 100 % записей есть причина (SC-003, SC-009) |

**Проверка границы влияния (FR-046).** Отключить уличный датчик и убедиться,
что обогрев продолжает работать: он зависит от датчика комнаты и уставки, а не
от улицы. Обратное тоже — отключить датчик спальни и посмотреть, что вентиляция
и остальные комнаты не изменились.

## Наблюдение в течение суток

Часть критериев видна только на длинном интервале — их нельзя закрыть в первый
день, иначе проверка превратится в формальность.

| Критерий | Как проверять | Когда |
|----------|---------------|-------|
| **SC-001** температура в пределах ±1 °C | собрать показания всех комнат за сутки, посчитать долю в допуске | через сутки непрерывной работы |
| **SC-002** обогреватель не работает дольше заданного | найти в журнале самую длинную работу обогревателя | через сутки |
| **SC-004** кондиционер не включался зимой | просмотреть все решения кондиционера за сезон `zima` | после первых холодов |
| **SC-010** предупреждение о батарейке | дождаться падения заряда датчика ниже порога; если не падает — задать порог выше заряда временно | по факту или принудительно |
| **SC-012** обогреватель выключился после отказа датчика | см. шаг 3 | сразу |
| **SC-013** отказ одного датчика не тронул другие | см. шаг 3 | сразу |
| **SC-014** возврат датчика без перезапуска | см. шаг 3 | сразу |
| **SC-015** у всех отказов есть причина | разбор журнала за сутки | через сутки |
| **SC-016** не больше одной записи в минуту | подсчёт записей по молчащему датчику за 15 минут | сразу |

**Как собрать данные для SC-001 и SC-002:**

```bash
# Температуры комнат за сутки
docker exec behavioral-platform sh -c \
  'curl -s -H "Authorization: Bearer $HA_TOKEN" "$HA_URL/api/history/period/now-1d?filter_entity_id=sensor.datchik_temperatury_spalnia_temperature"'

# Самая длинная работа обогревателя: переходы HEATING → IDLE и обратно
docker-compose -f docker-compose.prod.yml logs --since 24h behavioral-platform | \
  grep -E "Transition.*(IDLE.*HEATING|HEATING.*IDLE)"
```

Результат записать в `.ai/01_PROJECT_STATE.md` рядом с историей фичи, иначе
через месяц будет нечем подтвердить, что критерий закрыт.

## Что считать провалом

| Симптом | Вероятная причина |
|---------|-------------------|
| Решения климата идут с причиной `guard_data_missing` при живом датчике | фундамент не работает: уставка не доходит (`research.md` D1) |
| Доменные правила не влияют на поведение | сопоставление «шаблон → домен» (`research.md` D3) |

| Смена режима слышна часто | режим переключается на каждое показание, а не при изменении потребности (FR-016) |
| Действие в журнале есть, а устройство не изменилось | действие не зарегистрировано и прошло молча (`research.md` D8) — загрузка теперь падает, но проверить стоит |
