# Feature Specification: Состояние локации — машиночитаемый снимок происходящего

**Feature Branch**: `016-location-state`

**Created**: 2026-10-13

**Status**: Draft

**Input**: «Хочу, чтобы у локации был какой-то state, который читается из датчиков.
Для комнаты — температура, влажность, освещённость, присутствие/последнее движение,
состояние окон и дверей, может быть что-то ещё. Для улицы — текущие климатические
параметры, датчики дождя, ветра, освещённости, температуры/влажности. Для грядок —
датчики анализа почвы. Цель — чтобы платформа имела максимально полную информацию
о том, что происходит вокруг, чтобы после анализировать происходящее. Своего рода
машинное зрение для ИИ».

## Контекст

Сегодня платформа знает о датчиках ровно столько, сколько нужно автоматике: роль
датчика («temperature», «motion», «humidity», «lux», «contact») кладётся в контекст
автомата и живёт там как последнее значение. Снимка «что сейчас в комнате / на улице
/ на грядках» нет: нет ни времени последнего показания, ни производных («человек ушёл
5 минут назад», «окно открыто», «датчик молчит»), ни единого места, откуда это можно
прочитать. `RoomManager` написан, но в рантайме не используется; `state_snapshot`
отдаёт лишь текущий `state` устройства из Home Assistant; история показаний пишется в
`EventStore` (SQLite, 30 дней) как побочный эффект доставки событий.

Фича добавляет **наблюдаемое состояние локации**: снимок по каждой локации (комната,
улица, грядки), который обновляется событиями датчиков, обогащается производными
величинами, ведёт журнал изменений и зеркалируется в Home Assistant.

Решения владельца (2026-10-13): состояние живёт **зеркалом в Home Assistant**;
нужно **текущее состояние плюс журнал изменений**; локации — **комнаты манифеста
плюс особые зоны, заданные вручную**; привязка датчиков — **вручную в манифесте**.

## User Story 1 - Машиночитаемый снимок локации (Priority: P1)

Платформа собирает по каждой локации текущее состояние: значения датчиков с единицами
и временем последнего показания, признаки доступности/молчания, а также производные
(присутствие, последнее движение, открытые окна и двери, число активных датчиков).

**Why this priority**: без единого снимка нечего ни показывать, ни зеркалировать, ни
анализировать — это фундамент остальных двух историй.

**Independent Test**: подать показания датчиков в шину и через HTTP получить снимок
локации с производными; убедиться, что значения и время обновились.

**Acceptance Scenarios**:

1. **Given** локация «Спальня» с датчиками температуры/движения/контакта, **When**
   приходят их показания, **Then** снимок содержит значения, единицы и время каждого
   показания, а также производные `occupied` и `last_motion_ago_sec`.
2. **Given** датчик не присылал показаний дольше порога, **When** читается снимок,
   **Then** этот датчик помечен `stale` с временем последнего показания.
3. **Given** локация «Улица» с датчиками дождя/ветра/освещённости, **When** приходят
   показания, **Then** снимок содержит уличные параметры наравне с комнатными.
4. **Given** локация «Грядки» с датчиками почвы, **When** приходят показания, **Then**
   снимок содержит влажность/температуру/кислотность почвы по каждому датчику.
5. **Given** контакт окна/двери в положении «открыто», **When** читается снимок,
   **Then** производная `contacts_open` перечисляет открытые сущности.

## User Story 2 - Журнал изменений локации (Priority: P2)

Каждое изменение показателя локации записывается в журнал с временем, локацией,
ролью датчика и значением — чтобы по прошествии времени восстановить, что происходило.

**Why this priority**: именно ради анализа «что было» фича и затевается; текущего
снимка для этого мало.

**Independent Test**: изменить показания датчиков, затем запросить историю локации за
интервал и увидеть эти изменения по порядку.

**Acceptance Scenarios**:

1. **Given** показание датчика изменилось, **When** запрашивается история локации за
   интервал, **Then** изменение присутствует с точным временем и значением.
2. **Given** показание не менялось, **When** запрашивается история, **Then** лишних
   записей нет (журнал — это изменения, а не поток «каждую минуту»).
3. **Given** записи старше срока хранения, **When** запрашивается история, **Then**
   старые записи удалены по тому же сроку, что и у существующего журнала событий.

## User Story 3 - Зеркало в Home Assistant (Priority: P3)

Платформа публикует снимок локации в Home Assistant, и он виден там как сущности —
для графиков, автоматизаций и анализа штатными средствами HA.

**Why this priority**: владелец живёт в HA; зеркало делает состояние доступным без
своего интерфейса. Но без снимка и журнала зеркалить нечего — потому третьим.

**Independent Test**: после обновления снимка в HA появляются сущности локации с
правильными значениями и атрибутами, без ручного создания сущностей владельцем.

**Acceptance Scenarios**:

1. **Given** локация с показаниями, **When** снимок обновляется, **Then** в HA
   появляется сущность локации со снимком (атрибуты) и сущности по ключевым
   показателям (температура, влажность, присутствие и т.п.).
2. **Given** зеркало включено, **When** Home Assistant перезапускается, **Then**
   сущности зеркала восстанавливаются (публикация с признаком хранения).
3. **Given** MQTT в HA недоступен, **When** зеркало пытается публиковать, **Then**
   отказ попадает в журнал, а снимок и история продолжают работать.

### Functional Requirements

- **FR-001**: Платформа MUST собирать по каждой локации снимок текущего состояния из
  датчиков, привязанных к локации в манифесте.
- **FR-002**: Снимок MUST содержать для каждого датчика значение, единицу измерения,
  время последнего показания и признак доступности (в т.ч. `stale` при молчании).
- **FR-003**: Снимок MUST содержать производные величины: присутствие, время с
  последнего движения, перечень открытых окон/дверей и число датчиков без показаний.
- **FR-004**: Локация MUST объединять комнаты манифеста и особые зоны (улица, грядки),
  задаваемые в манифесте вручную со своими датчиками и ролями.
- **FR-005**: Роли датчиков MUST покрывать климат (температура, влажность, давление,
  освещённость, ветер, дождь, УФ), состояние проёмов (окна/двери) и почву (влажность,
  температура, кислотность, проводимость).
- **FR-006**: Каждое изменение показателя локации MUST записываться в журнал с
  временем, локацией, ролью и значением; журнал MUST иметь срок хранения.
- **FR-007**: Платформа MUST отдавать снимок и историю локации по HTTP (JSON) для
  внешнего анализа.
- **FR-008**: Снимок MUST зеркалироваться в Home Assistant через MQTT-автообнаружение
  (платформа публикует конфигурацию и значения; сущности создаёт HA).
- **FR-009**: Недоступность MQTT MUST NOT ломать сбор снимка и журнал: отказ виден в
  журнале, состояние продолжает обновляться.
- **FR-010**: Привязка датчиков к локации MUST быть явной в манифесте; угадывание по
  именам MUST NOT применяться.
- **FR-011**: Молчащий датчик MUST быть отличим от «значение не изменилось»: в снимке
  хранится время последнего показания и порог молчания.
- **FR-012**: Набор датчиков и локаций MUST быть виден в журнале при старте (сколько
  локаций, сколько датчиков, какие молчат) — для утреннего разбора.

### Key Entities

- **Локация** — именованная область наблюдения: комната, улица, грядки. Имеет `id`,
  `name`, `kind` (комната/улица/сад/…) и привязку датчиков (роль → сущность).
- **Привязка датчика** — роль (temperature/humidity/…), сущность HA, единица.
- **Снимок локации** — значения по ролям с временем и признаками + производные.
- **Запись журнала** — время, локация, роль, значение (изменение показателя).
- **Зеркало** — сущности HA, созданные MQTT-автообнаружением из снимка.

## Edge Cases

- **Датчик молчит** (нет показаний дольше порога): значение остаётся последним
  известным, помечается `stale`, попадает в `stale_count`; «значение не изменилось»
  так не помечается.
- **Датчик исчез из HA** (`unavailable`): значение помечается недоступным, в производные
  не идёт (присутствие не считается по мёртвому датчику).
- **Локация без датчиков**: снимок пуст, но существует — она видна как «нет данных».
- **Несколько датчиков одной роли в локации** (две температуры): снимок хранит их
  списком, производная берёт агрегат (среднее/максимум) — правило задаётся явно.
- **MQTT недоступен**: снимок и история работают, отказ зеркала виден в журнале.
- **Показание «дёргается»** вокруг порога: в журнал пишется только фактическое
  изменение значения, дребезг не размножается (порог/округление — на этапе плана).

## Success Criteria

- **SC-001**: По снимку любой локации за один запрос видно всё, что известно о ней
  сейчас, включая время каждого показания и молчащие датчики.
- **SC-002**: По журналу за произвольный интервал восстанавливается, как менялись
  показатели локации, без обращения к коду и без внешней базы.
- **SC-003**: В Home Assistant сущности локации появляются сами (без создания их
  владельцем вручную) и показывают те же значения, что снимок.
- **SC-004**: Отказ зеркала (MQTT) не влияет на сбор снимка и журнал.
