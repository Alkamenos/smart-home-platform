# Контракты: Климат

Контракт шаблонов (`src/features/CONTRACT.yaml`) **генерируется из кода**
инструментом `tools/gen_template_contract.py`, поэтому ниже описаны источники
истины, а не рукописный документ. Правка шаблона, реестра условий или карты
событий без регенерации роняет `tests/contract/test_template_contract.py` —
документ не может разойтись с кодом тихо.

## 1. Карта событий (не меняется)

`EventRouter.SENSOR_EVENT_MAP` (`src/core/events/event_router.py:80-86`) уже
содержит роль `temperature` → событие `temperature_changed`. Изменений не
требуется: это единственная причина, по которой климат возможен без правок
роутера.

Роли, которых в карте нет и которые климату не нужны: охлаждение решается по
температуре комнаты, а не по отдельному событию.

## 2. Условия климата

Каждое условие — фабрика, возвращающая `(state, context) -> bool`, и
`deny_reason(state, context) -> str | None`. Все регистрируются по имени в
`REGISTERED_GUARDS` (`src/core/guards/builtin.py:604-611`); забытый в кортеже
guard движок отклонит, и переход не сработает.

| Имя условия | Разрешает, когда | Отказ, причина |
|--------------|-----------------|---------------|
| `below_setpoint` | `temperature` — число и меньше `climate_setpoint` − `hysteresis` | `guard_data_missing` при отсутствии данных; `setpoint_unavailable` при негодной уставке |
| `at_or_above_setpoint` | `temperature` ≥ `climate_setpoint` | то же |
| `climate_is_enabled` | `climate_enabled` is True | `climate_disabled` |
| `may_cool` | `is_winter` is False **и** `ac_allowed` is True **и** `temperature` > `comfort_max` | `ac_not_allowed`, `ac_forbidden_in_winter`, `guard_data_missing` |
| `managed_by_hardware_ok` | в комнате нет штатного термостата | `managed_by_hardware` |

**Инвариант**: любое условие, возвращающее False, обязано назвать причину в
`deny_reason`. Условие без причины — дефект (правило владельца о логах).

## 3. Действия климата

Каждое действие — функция `(state, context) -> CommandIntent | None`,
регистрируется в `ACTION_HANDLERS` (`src/core/action_handlers.py:381-383`
сейчас содержит `climate_heat`, `climate_cool`, `climate_off`).

| Имя действия | CommandIntent | Когда применяется |
|--------------|---------------|-------------------|
| `heater_timer_on` | `domain="number"`, `service="set_value"`, `data={"value": run_minutes}` | Основной путь: обогреватель через собственный таймер (FR-004) |
| `heater_on` | `domain="switch"`, `service="turn_on"` | Фолбэк, когда `heater_timer` не задан; в журнал пишется, что таймер недоступен (FR-004) |
| `heater_off` | `domain="switch"`, `service="turn_off"` | Достижение цели или истечение таймера |
| `ac_cool_on` | `domain="climate"`, `service="set_temperature"`, `data={"temperature": comfort_max}` | Охлаждение летом (FR-009) |
| `ac_forced_off` | `domain="climate"`, `service="turn_off"` | Защита зимой: выключить немедленно (FR-011) |

**Почему домен `number` не требует правок движка**: `CommandDispatcher`
передаёт `processed_intent.domain` в намерение как есть
(`src/core/commands/dispatcher.py:200`), домен в намерении произвольный.
Нужно только новое действие и его регистрация.

**Почему `climate_heat`/`climate_cool` не используются как есть**: они
формируют `set_temperature` — команду для `climate.*`, то есть для кондиционера
и термостатов. Обогреватель — это `switch.*`, и команду ему надо формировать
в его домене. Старое имя параметра `target_temp` сохранено (починка #71).

## 4. Параметры манифеста

`automation_rules.climate` — новый блок рядом с существующим `lighting`
и `ventilation`. Схема — `src/core/manifest_schema.py`; контракт шаблонов
регенерируется и покажет, что параметры поведения стали действующими
(`effective: true`).

Поля — по таблице «Правила дома» в [data-model.md](../data-model.md).

## 5. Контекст события

Контракт контекста — **расширение существующего**, а не новый канал. Ключи
`daylight` и `sleep_modifier_on` уже кладутся адаптером в каждое событие
(`src/adapters/ha_adapter.py:1405-1409`); климат добавляет шесть ключей рядом
с ними по тому же правилу.

| Ключ | Кто кладёт | Обязателен ли для обогрева |
|------|-----------|------------------------------|
| `temperature` | роутер (роль датчика) | да |
| `climate_setpoint` | адаптер | да |
| `is_winter` | адаптер | нет (нужен только для охлаждения) |
| `comfort_max` | адаптер | нет (только охлаждение) |
| `ac_allowed` | адаптер | нет (только охлаждение) |
| `climate_enabled` | адаптер | нет (фиче-флаг необязателен) |
| `climate_shadow` | адаптер | нет (режим тени необязателен) |

**Договорённость**: отсутствие необязательного ключа равносильно «функция не
настроена» и не должно ломать обогрев. Отсутствие `temperature` или
`climate_setpoint` — отказ с причиной, а не значение по умолчанию.

## 6. Наблюдаемость

Требования FR-012 и SC-004/005/006 опираются на существующие механизмы, новых не
требуют:

| Требование | Чем обеспечивается |
|------------|--------------------|
| Решение с причиной в журнале | `FSMEngine.trigger` пишет переход и отказ с причиной (`src/core/fsm/engine.py`) |
| Список новых причин | `GUARD_DENIAL_REASONS` (`src/core/events/fsm_events.py`) — дополняется |
| Автомат виден в интерфейсе | Регистрация через `FSMFactory` — автоматически |
| Фиче-флаги видны в `/ready` | С существующей диагностикой развёртывания |

## 7. Что контракт ловит и чего не ловит

**Ловит:**
- условие в шаблоне, которого нет в реестре (сентинел состава + генератор
  контракта);
- действие в шаблоне, которого нет в `ACTION_HANDLERS`;
- событие, которое никто не публикует (генератор помечает
  `unproduced_triggers`);
- параметр, объявленный в схеме, но не используемый (`effective: false` —
  как сейчас у `hysteresis`).

**Не ловит (проверяется тестами и живой проверкой):**
- что решение действительно выключает обогреватель, а не только пишет лог;
- что защита кондиционера зимой срабатывает до вреда технике;
- что ручная блокировка обогревателем не ломается.
