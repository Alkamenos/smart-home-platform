# План реализации: Климат — обогрев по термостату и охлаждение

**Ветка**: `011-climate-control` | **Дата**: 2026-10-09 | **Спека**: [spec.md](./spec.md)

**Вход**: спецификация из `specs/011-climate-control/spec.md`

## Краткое содержание

Платформа читает целевую температуру из Home Assistant (`input_number.temperatura`),
сравнивает её с датчиком температуры каждой комнаты и включает обогреватель через
его собственный таймер; при достижении цели выключает. Летом при превышении
потолка комфорта — охлаждение кондиционером, но только при фактической смене
решения; зимой кондиционер защищён. Расписание «день/ночь» остаётся в HA.

Технический подход: шаблон `climate_control.yaml` переписывается под единственное
событие `temperature_changed` (уже публикуется роутером), новые условия читают
уставку и флаги из контекста события, а глобальные сущности (`input_number.*`,
`input_boolean.*`) читаются адаптером по существующему пути, который уже занят
модификатором «мы спим» и солнцем — они лежат вне подписки и ловятся отдельно.

## Технический контекст

**Язык/версия**: Python 3.12 (контейнер боевого развёртывания), проект
настроен на 3.10+ (ruff target).

**Основные зависимости**: FastAPI + uvicorn (webui), pydantic v2 (модель
манифеста), loguru + stdlib logging (журнал), aiohttp (REST Home Assistant),
websockets (поток событий HA), pytest + pytest-asyncio + coverage.

**Хранилище**: JSON-файл состояний автоматов (`StatePersistence`) +
`history.db` (журнал). Новых хранилищ не требуется: климат не помнит ничего
между решениями, кроме состояния автомата, которое уже персистится.

**Тестирование**: pytest; новые файлы — не менее 80% покрытия, действия — 100%
(конституция II). Сторож покрытия `tests/` отделяет медленные проверки.

**Целевая платформа**: Linux-контейнер (боевое развёртывание), автономный режим
и режим интеграции с HA через WebSocket — оба обязаны работать (конституция VI).

**Тип проекта**: сервис с FSM-движком; фича — конфигурация поведения плюс
условия, действия и чтение состояний.

**Цели по производительности**: решение климата не позже 5 секунд после
изменения показания датчика; решение по флагам — не позже 10 секунд; никаких
опросов с периодом короче минуты.

**Ограничения**: комнат с обогревателями — 5, датчиков — 5, глобальных правил — 6.
Контекст события не должен разрастаться: в него добавляется 6 ключей, а не
состояние всего дома.

**Объём**: 5 обогревателей, 1 масляный радиатор, 2 термостата (не трогаем),
1 кондиционер, 6 глобальных сущностей правил.

## Проверка конституцией

*GATE: должен пройти до исследования; перепроверен после проектирования.*

| Принцип | Соблюдение |
|---------|-------------|
| I. Event-Driven FSM (NON-NEGOTIABLE) | Соблюдается. Единственное событие `temperature_changed` уже публикуется роутером; структура FSMDefinition, логика debounce и механизм таймаутов **не меняются** — состояние HEATING использует существующий `timeout_sec`. |
| II. TDD/SDD, ≥80% покрытия, 100% для действий | Соблюдается: спека → план → задачи → тесты первыми. Новое действие (таймер обогревателя) покрывается на 100%. |
| III. Контроль остаётся за пользователем | Соблюдается и усилено: уставка живёт в HA, фиче-флаги `feature_climate`/`climate_shadow_mode` отключают климат одной кнопкой, ручная блокировка уважается. |
| IV. Многоуровневая архитектура | Соблюдается. Чтение HA — в адаптере, условия и действия — в ядре, связь — через контекст события и CommandIntent. Ядро не импортирует адаптеры. |
| V. Манифест — единственный источник конфигурации | Соблюдается. Идентификаторы уставок, флагов, датчиков и все пороги (`hysteresis`, длительность работы обогревателя) описываются в манифесте; в коде значений нет. |
| VI. Двухрежимное развёртывание | Соблюдается: без HA данных нет — решения не принимаются, дом не трогается. Автономный режим остаётся рабочим. |
| VII. Многоуровневый интерфейс | Соблюдается: новые автоматы автоматически видны в webui (статус, история), в журнале — по правилу владельца о подробных логах. |

**Нарушений нет** — Complexity Tracking не заполняется.

### Повторная проверка после проектирования (Phase 1)

Проектные решения не изменили ни одного пункта. Две проверки отдельно, потому
что именно на них чаще всего ломается конституция проекта:

| Проверка | Результат |
|----------|-----------|
| V: значения в манифесте, а не в коде | Соблюдается. Уставка, потолок, сезон, флаги, гистерезис и длительность работы обогревателя — параметры манифеста; в коде остаются только умолчания как страховка отсутствия настройки. |
| I: FSM не трогаем | Соблюдается. Событий не добавляем (нужное уже публикуется), таймауты не меняем (используем существующий `timeout_sec`). |

Новый модуль `core/services/climate.py` сознательно **не создаётся**: решение
живёт в шаблоне и условиях, иначе конфигурация поведения перестала бы быть
источником истины, а это прямое нарушение принципа V.

```text

│   └── ha_adapter.py              # чтение глобальных сущностей климата, контекст события
├── core/
│   ├── container.py               # запуск климата, фиче-флаги
│   ├── guards/
│   │   └── builtin.py             # новые условия климата + REGISTERED_GUARDS
│   ├── action_handlers.py         # таймер обогревателя (number.set_value)
│   ├── events/
│   │   ├── fsm_events.py          # причины отказов климата
│   │   └── event_router.py        # без изменений (роль temperature есть)
│   ├── models/
│   │   ├── manifest.py            # automation_rules.climate
│   │   └── manifest_schema.py     # схема параметров климата
│   └── services/
│       └── day_cycle.py           # переиспользуется (deliver_to_automata), без правок
├── features/
│   └── climate_control.yaml       # переписан под одно событие и условия
└── bootstrap.py                   # регистрация новых условий/действий

tests/
├── contract/
│   └── test_template_contract.py  # контракт регенерируется из кода
├── integration/
│   └── climate/                   # новое: обогрев по датчику, защита кондиционера
└── unit/
    └── core/test_climate_*.py     # новые проверки условий и действий
```

**Решение по структуре**: проект уже разделён на слои (конституция IV), новых
каталогов не требуется. Климат добавляется в существующие модули: условия — в
`guards/builtin.py` по образцу `may_turn_on`, действия — в `action_handlers.py`,
шаблон — в `features/`, конфигурация дома — в манифест. Новый модуль
`core/services/climate.py` **не создаётся**: вся логика решения помещается в
шаблон и условия, а это требование конституции V (логика — в конфигурации).

## Порядок работ (для /speckit-tasks)

1. Условия климата в `guards/builtin.py` + регистрация в `REGISTERED_GUARDS`.
2. Контекст события: чтение глобальных сущностей в `ha_adapter.py`.
3. Действие таймера обогревателя в `action_handlers.py` (100% покрытие).
4. Переписанный шаблон `climate_control.yaml` (одно событие, условия, таймаут).
5. Параметры манифеста (`automation_rules.climate`) и их прокидывание в поведение.
6. Причины отказов климата в `fsm_events.py`.
7. Боевой манифест: комнаты с датчиком и обогревателем, глобальные правила.
8. Регенерация контракта шаблонов, полный прогон проверок.

## Риски и как они снимаются

| Риск | Снятие |
|------|--------|
| Обогреватель греет, а датчик молчит — перегрев | FR-004: работа через таймер обогревателя. Даже при полной потере датчика нагрев закончится сам. |
| Две правды об уставке (термостат и `input_number`) | FR-014: расхождение больше 1 °C попадает в журнал, а не выбирается молча. |
| Климат ловит ручную блокировку от своего же выключателя | Ручная блокировка отличает собственные команды по `context.id` (`ha_adapter.py:783`). Существующий механизм, покрыт тестами #18. |
| Гвард забыт в `REGISTERED_GUARDS` — переход отклонится, фича «работает молча» | Сентинел: `tests/unit/core/test_builtin_guards_actions.py` сверяет состав условий манифеста с реестром. Перегенерация контракта падает при расхождении. |
| Событий много (датчик шлёт показания часто) — дебаунс съест решение | `debounce_sec` подбирается по наблюдению; при необходимости решение принимается по каждому событию, а таймер обогревателя ограничивает реальные включения. |
