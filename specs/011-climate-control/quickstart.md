# Быстрый старт: проверка климата

Два способа проверить фичу: тестами (быстро, до дом��) и в доме (медленно, но
единственный, который доказывает пользу). Тесты обязательны до коммита, живая
проверка — до того, как фича поставлена на боевое расписание.

## Часть 1. Проверка тестами

### 1.1 Условия обогрева

```bash
make test-block unit/core/test_climate_guards.py
```

Ожидаемое поведение (проверяется содержанием, а не наличием):

- комната 20.5, цель 22, гистерезис 0.5 → **включение разрешено**;
- комната 21.8, цель 22 → **включение запрещено** (в мёртвой зоне);
- комната 22.5 → достигнута цель, обогреватель выключается;
- уставка отсутствует → отказ с причиной `setpoint_unavailable`;
- датчик недоступен (`unavailable` строкой) → отказ с причиной
  `guard_data_missing`, **не** включение;
- `climate_enabled` = false → отказ `climate_disabled`.

### 1.2 Таймер обогревателя

```bash
make test-block unit/core/test_climate_actions.py
```

Ожидаемое поведение:

- действие таймера создаёт намерение `domain="number"`, `service="set_value"`,
  `data={"value": 15}` при `run_minutes: 15`;
- без `heater_timer` в параметрах — намерение `switch.turn_on` (фолбэк);
- `heater_off` — намерение `switch.turn_off`;
- покрытие новых действий — 100% (требование конституции II).

### 1.3 Шаблон и контракт

```bash
python tools/gen_template_contract.py
make test-block contract/test_template_contract.py unit/core/test_builtin_guards_actions.py
```

Ожидаемое поведение:

- в `src/features/CONTRACT.yaml` у `climate_control` все переходы имеют
  производимые события, `unproduced_triggers` пуст, `hysteresis` помечена
  `effective: true`;
- все условия шаблона есть в реестре и в реестре реализаций.

### 1.4 Сквозная проверка на живых объектах движка

```bash
make test-block integration/climate/
```

Ожидаемое поведение: событие `temperature_changed` с числом в контексте и
уставкой в правилах дома приводит к переходу `IDLE → HEATING`, из которого
приходит намерение таймера; истечение таймера возвращает автомат в `IDLE`.

### 1.5 Полный прогон перед коммитом

```bash
bash .ai/scripts/run_checks.sh
```

Ожидаемое поведение: `✅ Можно коммитить изменения`.

## Часть 2. Проверка в доме

Порядок обязателен: сначала режим тени, потом активный режим. Причина в том,
что первая же ошибка в порогах станет заметна по деньгам и по сроку службы
обогревателя.

### 2.1 Подготовка манифеста

В `deploy/docker/config/manifest.yaml` (в git не входит):

- каждой комнате с обогревателем — датчик температуры в `sensors.temperature`
  и обогреватель в `devices` с поведением `climate_control`;
- `heater_timer` указывает на `number.obogrevatel_<комната>_countdown`
  (у масляного радиатора — `number.maslianyi_radiator_countdown`);
- для гостиной — `managed_by_hardware: true`, потому что там термостат;
- блок `automation_rules.climate` с идентификаторами правил.

Проверка синтаксиса и подписки:

```bash
docker compose -f deploy/docker/docker-compose.prod.yml restart
docker logs behavioral-platform 2>&1 | grep -E "Created FSM|subscribed|ошибк"
```

Ожидаемое поведение: число автоматов климата равно числу комнат с обогревателем;
в списке подписки появились датчики температуры; ошибок разбора манифеста нет.

### 2.2 Режим тени: решения видны, команды не уходят

Включить режим тени (`SHADOW_MODE=true`) либо
`input_boolean.climate_shadow_mode` = on. Опустить уставку в HA на 25 °C и
дождаться, пока в комнате станет холоднее.

Ожидаемое поведение в журнале:

- приход показания датчика и **решение** с причиной (`ниже цели на …` или
  `в мёртвой зоне`), без строки `calling service`;
- при включённом `feature_climate` = off — отказ с причиной `climate_disabled`.

### 2.3 Активный режим: одна комната

Снять режим тени, оставить климат активным **только для одной комнаты**
(например, спальни). Опустить уставку ниже текущей температуры комнаты.

Ожидаемое поведение:

- в журнале — переход `OFF → HEATING` с указанием причины;
- в Home Assistant обогреватель включается, **а его таймер обратного отсчёта
  начинает идти** — это главный признак, что включение идёт через таймер;
- при достижении цели обогреватель выключается, автомат возвращается в решение;
- если датчик замолчал — через `run_minutes` обогреватель выключается сам.

### 2.4 Охлаждение (лето)

Летом, при температуре выше потолка комфорта:

- с `input_boolean.ispolzovat_konditsioner` = off — отказ с причиной
  `ac_not_allowed`, кондиционер молчит;
- с ним = on — кондиционер переходит в охлаждение **один раз** и не
  переключается при дальнейших колебаниях температуры.

Зимой этот сценарий проверяется **только** через защиту: любая попытка включить
кондиционер должна привести к его немедленному выключению и уведомлению.

### 2.5 Расхождение уставок

Развести уставку термостата гостиной и `input_number.temperatura` больше чем на
1 °C.

Ожидаемое поведение: в журнале появляется запись о расхождении с обеими
величинами, а не молчаливый выбор одной из них.

### 2.6 Право владельца

Проверить три флага подряд:

1. `input_boolean.feature_climate` = off → команды обогревателя прекращаются в
   течение 60 секунд, в журнале — `climate_disabled`;
2. `input_boolean.climate_shadow_mode` = on → решения принимаются, команды не
   уходят;
3. ручной выключатель обогревателя → блокировка работает, причина отказа видна.

## Часть 3. Откат

Климат отключается без отката платформы: `input_boolean.feature_climate` = off
останавливает все решения, а удаление блока `automation_rules.climate` из
манифеста возвращает платформу к состоянию «климата нет» — обогреватели
остаются под ручным и HA-управлением, как сейчас.
