## R-01. Корень проблемы: движок не имеет ни шины, ни диспетчера, ни хранилища

**Находка.** `FSMEngine.__init__` (`src/core/fsm/engine.py:119-131`) принимает `command_dispatcher` и `persistence`, но единственное место создания движка в платформе — `src/core/container.py:130`:

```python
@property
def fsm(self) -> FSMEngine:
    if self._fsm is None:
        self._fsm = FSMEngine()  # ни диспетчера, ни хранилища, ни шины
    return self._fsm
```

Следствия, все подтверждены кодом:

| Что | Строка | Последствие |
|---|---|---|
| `self._dispatcher is None` | `engine.py:324-328` | `CommandIntent` из действий **отбрасывается** с предупреждением «No dispatcher available». Автоматика меняет состояние FSM, но **не отправляет команды устройствам** |
| `self._persistence is None` | `engine.py:145`, `:475` | `save_state` не вызывается; `register_definition(restore_state=True)` **не восстанавливает** состояние — всегда `initial_state` |
| атрибута `event_bus` нет | `engine.py:124-131` | публиковать переходы нечем (FR-001) |

Дополнительно: `ha_adapter.py:309` проверяет `hasattr(self._engine, "event_bus")` — сегодня это **всегда `False`**, ветка мёртвая (Known Issue #9 / B5).

**Решение.** Инъецировать в движок все три зависимости из контейнера. Требуется порядок сборки: `event_bus` → `fsm` (с `dispatcher=None` на первом проходе) → `dispatcher` → связать. Так как `dispatcher` создаётся лениво и зависит от `adapter`, а `adapter` — от `fsm`, нужен двухшаговый сценарий: `Container.build()` создаёт движок, затем после создания диспетчера вызывает публичную точку связывания.

**Альтернативы.**
- *Оставить диспетчер `None`.* Отклонено: FR-016 требует, чтобы команды шли через диспетчер как раньше; сегодня они не идут вообще, а фича US3 показывала бы переходы, не влияющие на устройства — недостоверно по духу спеки.
- *Передавать диспетчер конструктором.* Отклонено: создаёт циклическую зависимость `dispatcher → adapter → fsm → dispatcher`.
- *Изменить `FSMEngine.trigger` на вызов диспетчера напрямую.* Отклонено: нарушит инкапсуляцию и усложнит тесты.

**Следствие для плана.** Требуется публичный сеттер диспетчера в движке + вызов из `Container.build()`. Это минимальное аддитивное изменение, не трогающее правила переходов (конституция, принцип I).

## R-02. Где именно публиковать переход

**Находка.** `trigger()` (`engine.py:376-496`) — единственная точка перехода. Путь:

```
trigger() → 404 _cancel_timers → 406-414 отказ по определению/состоянию
 → 419-427 ДЕБАУНС (отказ) → 429-440 поиск перехода (отказ)
 → 447 цикл кандидатов → 449-455 ГАРД (отказ) → 458 действие
 → 465-467 новый State → 470 ЗАПИСЬ → 474 save_state → 477-482 log.info
 → 485-491 таймаут → 493 return True
```

Единственный сигнал о переходе — `log.info` на `engine.py:477-482`. Отказов пять видов, все `return False` с разным уровнем лога.

**Решение.** Публиковать в двух точках:
- успешный переход — сразу после записи состояния (`engine.py:470-471`), до сохранения в хранилище, чтобы подписчики видели согласованное состояние;
- отказ — в точке отказа, с указанием причины (`debounce` / `no_transition` / `guard_failed` / `unknown_entity` / `no_state`).

Все пять точек отказа сводятся к хелперу, чтобы не дублировать формат. Публикуемые поля берутся из уже доступных данных: `entity_id`, `target_device_id` (устройство, `engine.py:363-365`), имя поведения (шаблон из идентификатора), `from_state`/`to_state`, `trigger`, `trace_id`.

**Альтернативы.**
- *Публиковать из `FSMFactory`.* Отклонено: фабрика не участвует в выполнении перехода, только в создании.
- *Подписываться на логи.* Отклонено: хрупко, неструктурировано, недоступно подписчикам.
- *Хук на каждое изменение `State`.* Отклонено: `reset_state` и `_restore_state` тоже пишут в `_states` — это не переходы, а приравнивать их сломало бы FR-009/FR-016.

## R-03. Источник перехода: автоматический или ручной — в движке его нет

**Находка.** Ни `trigger()`, ни `FSMDefinition`, ни `Transition` не содержат признака источника. `trigger()` принимает только `(entity_id, event, external_ctx, trace_id)` (`engine.py:376-382`). Различия нет ни в одном поле:

| Поле | Кто читает | Реальность |
|---|---|---|
| `Transition.priority` | только `webui/routes/__init__.py:98` (разметка) | движком **не читается** при выборе перехода |
| `Transition.manual_lockout_min` | только генератор манифеста | движком **не читается** |
| `CommandIntent.source` | `core/commands/dispatcher.py:39-46` | заполняется в действии из контекста, но `engine.py:344-374` **не подставляет** `source`/`priority` в контекст → в производстве всегда `priority=50`, `source="lighting"` |

Единственный соглашённый сигнал — имя события-триггера в шаблонах: `manual_switch_on`, `manual_override`, `manual_change` (`src/features/lighting.yaml:53,66,72`, `generic_switch.yaml:42`).

**Решение.** Источник определяется по префиксу имени события: `manual_*` → ручной, иначе автоматический. Правило вынести в константу-набор префиксов (конституция V, запрет magic values), применять только при публикации события — логика переходов не меняется. Дополнительно в payload класть `event` (имя триггера), чтобы потребитель мог решить сам.

**Альтернативы.**
- *Добавить поле `source` в `FSMDefinition` и требовать его в манифесте.* Отклонено: ломает схему манифеста (принцип V требует версионирования и миграций) ради данных, которые уже выводимы.
- *Передавать `source` аргументом `trigger()`.* Отклонено: вызывающая сторона — `EventRouter`/`HAAdapter` — не знает о происхождении; ложная определённость опаснее соглашения.
- *Считать ручным всё, что пришло с приоритетом ≥ 100.* Отклонено: движок приоритетов не хранит (см. таблицу выше).

**Явный риск, фиксируется в плане.** Соглашение об именах — не изменить его нельзя, но можно проверить: тест, что все триггеры из `src/features/*.yaml`, начинающиеся с `manual`, классифицируются как ручные, а остальные — как автоматические, и что новые триггеры с префиксом `manual_` подхватываются без изменения кода.

## R-04. Время перехода: `State.entered_at` — монотонные часы цикла

**Находка.** `State.entered_at` заполняется `asyncio.get_event_loop().time()` (`engine.py:417`, `:466`) — это **монотонный** таймер цикла, а не настенное время. Он несравним с `time.time()` и бессмысленен для отображения, сериализации и записи в БД.

При этом остальной проект использует ISO-8601 строки: `datetime.utcnow().isoformat()` (`device_service.py:1367, 1390, 1425`).

**Решение.** В payload события публиковать отдельное поле `timestamp` как `datetime.utcnow().isoformat()` — в одном формате со всеми существующими событиями проекта. Значение `State.entered_at` в payload не дублировать: оно принадлежит внутренней модели движка. FR-023 (единый формат времени) выполняется введением одной константы формата, используемой и в REST-ответах US2, и в живых сообщениях US3.

**Альтернативы.**
- *Привести `State.entered_at` к настенному времени.* Отклонено: `entered_at` используется в логике (дебаунс-подобные сравнения в тестах, отображение «сколько в состоянии») и является частью структуры движка, изменение которой — правка ядра.
- *Отдавать epoch float.* Отклонено: несогласовано с остальными разделами интерфейса.

## R-05. `EventBus.publish` блокирует — нужно решить FR-013/FR-014/SC-015

**Находка.** `publish` (`event_bus.py:107-153`) — `async`, без очереди, без `create_task`. Подписчики вызываются **последовательно** (`for handler in handlers`, строка 129), не `gather`. Итого задержка публикации = сумма задержек подписчиков. Медленный подписчик задерживает вызывающего — то есть переход автомата.

FR-014 и SC-015 требуют обратного: переход не должен ждать подписчиков.

Дополнительно найдено: **синхронные подписчики не работают**. Тип объявлен как `Coroutine`, но `FSMPersistence._on_fsm_transition` (`core/fsm/persistence.py:76`) и `_on_platform_started` (`:113`), а также `ContextManager._on_platform_started` (`core/persistence/context_manager.py:86`) и `_on_ha_state_change` (`:90`) — обычные `def`. Путь их вызова: `await handler(..., trace_id=...)` → `TypeError` (`:132`) → повторный вызов `await handler(event_type, payload)` → тело выполняется (побочные эффекты есть!) → `await None` → `TypeError` → ловится `except Exception` (`:136`) → ошибка логируется. Итог: побочный эффект есть, но каждая доставка пишет ложную ошибку.

**Решение.** Три части:

1. **Публикация перехода — неблокирующая.** Движок планирует публикацию отдельной задачей и **отслеживает** её в множестве, чтобы на `shutdown()` дождаться или отменить. Это даёт FR-014/SC-015, не меняя семантику `publish` для существующих вызывающих (детерминированный порядок сохраняется там, где он важен).
2. **Поддержка синхронных подписчиков.** Исправить запасной путь в `publish`: если обработчик не `Coroutine`, вызвать без `await`; если вернул awaitable — дождаться. Заодно устранить двойной вызов при `TypeError` **из тела** обработчика (сейчас `except TypeError` на строке 132 не отличает несовпадение сигнатуры от ошибки внутри тела, из-за чего побочные эффекты могут выполниться дважды).
3. **Подписчики-классы приводятся к async** с сигнатурой `(event_type, payload, trace_id=None)`, чтобы соответствовать объявленному контракту.

**Альтернативы.**
- *Сделать `publish` всегда неблокирующим.* Отклонено: сломает детерминированный порядок и тесты `tests/test_event_bus.py` (там порядок доставки подразумевается `assert_called_once_with` сразу после `await publish`).
- *Очередь с фоновым воркером.* Отклонено: новая инфраструктура (задача, остановка, переполнение) ради требования, которое решается планированием задачи. Потеря событий при крэше уже сейчас допускается для необязательных подписчиков.
- *Путь «мягкий» — `try/except` вокруг `await publish`.* Отклонено: медленный подписчик всё равно задержит переход.

**Компромисс, фиксируется явно.** Доставка неблокирующая — значит, при аварийном завершении процесса событие может потеряться. Для FR-001 это приемлемо: событие — сигнал о состоянии, а источник истины — `engine.get_all_states()`, из которого состояние читается синхронно (FR-018, SC-004). Компенсирующая мера — FR-028/SC: при (пере)подключении клиент получает актуальное состояние запросом.

## R-06. Как сохранять состояние автоматов (FR-015, D-1)

**Находка.** Три несвязанных механизма, все частично мёртвые:

| Механизм | Состояние | Вывод |
|---|---|---|
| `StatePersistence` (`core/persistence/state_persistence.py`) | **уже встроена в движок**: `save_state` на `engine.py:475`, восстановление в `register_definition` на `engine.py:145-158` с проверкой `saved_state in definition.states` | Мёртва только из-за `persistence=None` (R-01). Работает в обоих режимах, JSON, атомарная запись |
| `FSMPersistence` (`core/fsm/persistence.py`) | подписан на непубликуемое `fsm.transition`; **никогда не создаётся в `src/`**; вызывает `self._adapter.set_entity_state(...)` (`:180`) — **метода нет ни у одного адаптера**; запасной путь — жёсткий `~/.homeassistant/.storage/fsm_persistence/` | Как источник истины непригоден без нового метода адаптера |
| `StateStore`/`FileStateStore` | в `src/` нет пользователей | Не используется |

**Решение.** Один источник истины — **`StatePersistence`, подключённая к движку**:

- `StatePersistence(data_dir/state.json)` — рядом с прочими файлами `data/`, вместо дефолта `"state.json"` в CWD;
- движок сохраняет при каждом переходе (уже есть, `engine.py:475`) и восстанавливает при регистрации определения (уже есть, `engine.py:145-158`) — **логика переходов не меняется**;
- восстановление ограничено списком допустимых состояний определения, поэтому снятый с регистрации автомат не восстановится: у него нет определения (SC-017).

Для режима с Home Assistant (вторая часть FR-015) — **зеркалирование состояния в HA через существующий диспетчер команд**: `CommandIntent(domain="input_text", service="set_value", data={"value": state}, priority=1, source="fsm_state")`. Это использует уже работающий путь `dispatcher → adapter.call_service` и **не требует** нового метода адаптера. Ошибка зеркалирования логируется и не влияет на переход. Переходы, при которых `input_text` не создан, не приводят к сбою.

`FSMPersistence` приводится к корректным подписчикам (async + сигнатура), чтобы перестать быть источником ложных ошибок, но **не инстанцируется** — дублировать источник истины нельзя.

**Альтернативы.**
- *Активировать `FSMPersistence` как есть.* Отклонено: требует нового метода адаптера, пишет вне `data/`, хранит ключ вида `{entity}_mode` отдельно от состояния движка — два источника истины.
- *Только HA-зеркало, без JSON.* Отклонено: автономный режим (принцип VI) остался бы без сохранения.
- *Хранить состояние в `EventStore` (SQLite).* Отклонено: там уже есть таблица `fsm_transitions` для **журнала**, а не для текущего состояния; смешивать две ответственности.

**Риск для пользователя.** `input_text.*` может не существовать в его Home Assistant. Поэтому зеркалирование — «лучшее усилие»: ошибка в журнале, переход и сохранение в JSON не страдают. Основное требование FR-015 (переживание перезапуска) обеспечивается JSON независимо от HA.

## R-07. Единая шина событий: мост WebUI ↔ Container

**Находка.** Две шины в одном процессе:
- `Container.event_bus` (`core/container.py:123`) — каноническая; её получают `FSMFactory` (`container.py:198-200`) и `PlatformContext` (`container.py:241`);
- **новая пустая** `EventBus()` в `webui/app.py:357` — отдаётся `DeviceService` и кладётся в `app.state.event_bus` (`:408`). Подписчиков на неё нет нигде (`app.state.event_bus` читается только в строке 408), поэтому все пять событий `device.*` уходят в пустоту.

**Решение.** `app.state.event_bus = _container.event_bus`; удалить создание второй шины. Дополнительно:
- подписать `DeviceService.handle_state_change` (`device_service.py:1067`) на актуальный HA-канал — он не подписан нигде;
- опубликовать `platform.started` при старте платформы — на него подписаны `FSMPersistence` и `ContextManager`, и он тоже не публикуется никогда.

**Альтернативы.**
- *Оставить две шины и пересылать.* Отклонено: ровно та конструкция, которую фича устраняет; две подписчики-источника расходятся во времени.
- *Шина на `app.state`, контейнер берёт из неё.* Отклонено: нарушает направление зависимостей — ядро не должно зависеть от веб-слоя.

**Побочный эффект, требующий проверки.** После появления `event_bus` у движка оживает мёртвая ветка `ha_adapter.py:309-315` (`hasattr(self._engine, "event_bus")` станет `True`): вместо `engine.trigger(f"{entity_id}_changed")` адаптер начнёт публиковать `state_change`, на который подписан `FSMFactory` с фильтром по `motion_sensor` (`factory.py:399-403`). Это **исправление** Known Issue #9 / B5, но оно меняет маршрутизацию состояний — обязательно проверяется тестом и вживую (сценарий quickstart).

## R-08. Канал реального времени: строить на существующем, а не на мёртвом

**Находка.** Три WebSocket-эндпоинта, ни один не доставляет:

| Эндпоинт | Состояние | Пригодность |
|---|---|---|
| `/ws/live` (`app.py:456`) | принимает, читает текст, `manager.broadcast` **не вызывается нигде**; `broadcast_event` (`app.py:472`) — мёртвый код; **нет идентичности и проверки доступа** | Негоден: FR-025 требует разграничения по правам |
| `/ws/logs` (`app.py:1067`) | принимает, `receive_text` в цикле, отправки нет | Не относится к фиче |
| `/api/v1/ws/devices` (`routes/devices/websocket.py:203`) | **полностью готов**: идентичность через `auth`, подписки по устройствам, проверка доступа при **каждой** доставке (`_has_access_now`, `:115`), чистые JSON-формы | Годится |

`broadcast_state_change` (`websocket.py:368`) — единственный раздатчик, вызывается **только из теста** (`tests/integration/test_access_control.py:318`).

Шаблоны: `index.html:838` подключается к `/ws/live` с обработчиком, который только пишет в консоль и ищет типы `fsm_transition`/`sensor_event` (`:846-853`) — ни один сервер такие типы не производит. `dashboard.html` — WebSocket не использует вовсе.

**Решение.** Базой берётся `/api/v1/ws/devices` — он единственный удовлетворяет FR-025/FR-038/FR-039. `/ws/live` выводится из эксплуатации, шаблоны переводятся на канал устройств. Источник переходов в сокет — подписка на шину событий, а не опрос.

Опасность, найденная в тесте (`tests/integration/test_access_control.py:303-305`): `src/main.py` импортирует пакет `webui` верхнего уровня, поэтому `webui.routes.devices.websocket` и `src.webui.routes.devices.websocket` — **разные модули с разными синглтонами `connection_manager`**. Ошибка импорта молча доставляет «в никуда». Требуется единый путь импорта, и это отдельный пункт задач.

**Альтернативы.**
- *Оживить `/ws/live` и добавить в него проверку прав.* Отклонено: дублирование существующей логики доступа, два канала на одну задачу.
- *Опрос REST вместо сокета.* Отклонено: SC-003 требует ≤2 с, FR-024 — доставку по событию; опрос нагружает и не соответствует FR-024.

## R-09. Диаграмма: JSON попадает в страницу как текст (FR-029, FR-030)

**Находка.** Эндпоинт отдаёт конверт (`webui/routes/__init__.py:155-158`):

```python
return Response(
    content=json.dumps({"diagram": _build_mermaid_state_diagram(definitions)}),
    media_type="application/json",
)
```

`dashboard.html:242-248` читает его как текст и вставляет через `innerHTML`:

```javascript
fetch(`/api/fsm/${deviceId}/diagram`).then(r => r.text())
    .then(diagramText => { container.innerHTML = diagramText; mermaid.contentLoaded(); })
```

Итог: на страницу попадает строка `{"diagram": "stateDiagram-v2\n    [*] --> OFF\n..."}`. При этом `index.html:783-818` делает **правильно**: `r.json()`, распаковка `.diagram`, установка через `textContent`. То есть два места в одном проекте делают одно и то же по-разному, и одно из них сломано.

Подсветка текущего состояния (`generate_with_highlight` из enhancement 26) в проекте **отсутствует полностью** — поиск по `src/` и `tests/` даёт 0 совпадений.

**Решение.** Разделить формат по назначению:
- `GET /api/fsm/{entity_id}/diagram` остаётся источником **чистой** Mermaid-строки для рендера (`text/plain`) — так его уже потребляет `index.html`;
- **состояние** приходит отдельным полем в ответе состояний US2 и живым сообщением US3, а подсветка делается на клиенте: помечать текущий узел классом и перерисовывать диаграмму при смене состояния (без перезагрузки страницы и без обращения к серверу).

**Альтернативы.**
- *Оставить JSON и починить только `dashboard.html`.* Отклонено: FR-029 говорит о формате вообще; смешение двух форматов в одном эндпоинте — источник этого дефекта.
- *Реализовать `generate_with_highlight` на сервере.* Отклонено: перерисовка диаграммы на каждое живое событие означает перезагрузку текста диаграммы по сети; подсветка на клиенте дешевле и мгновеннее.

## R-10. Честные данные (US4): чем заменить выдуманные

**Находка.** Три раздела, два из которых выдумывают данные:

| Эндпоинт | Источник | Реальность |
|---|---|---|
| `/api/history/activity-heatmap` (`routes/__init__.py:215-258`) | `random.seed(42)`, 7×24 значения | Полностью выдумано; комментарий в коде сам называет замену — агрегация `EventStore` |
| `/api/events/history` (`:261-301`) | `event_store.get_events(limit=100)` | Запрос настоящий, но **таблица `events` пуста**: писателей `save_sensor_event` в `src/` нет вообще → плоская нулевая линия. Плюс оси перепутаны: корзина считается «часов назад», а подписи идут от `00:00` — график отображается задом наперёд |
| `/api/ai/suggestions` (`:373-422`) | при пустом ответе — `random.seed(42)`, 3 объекта | Выдумано; форма ключей не совпадает с формой настоящих строк, поэтому интерфейс видит только вымышленную форму |

`EventStore` (`core/persistence/event_store.py`, SQLite `data/history.db`) имеет **все четыре таблицы** (`events`, `fsm_transitions`, `manual_overrides`, `ai_suggestions`) и методы `save_fsm_transition` (`:134`), `save_sensor_event` (`:185`), но **писателей в `src/` нет ни одного**. Заполнена только `manual_overrides` — единственный раздел с настоящими данными.

Отдельно: `POST /api/ai/suggestion/{id}/respond` (`routes/__init__.py:446-450`) передаёт `responded_at=` в `update_suggestion_status`, который такого параметра не принимает (`event_store.py:341`) → `TypeError` → 500. Тест этого не ловит, проверяя `status_code in [200, 404]` (`tests/test_webui.py:123-127`).

**Решение.** Данные появляются из публикации переходов, которую делает US1:

| Раздел | Источник после фичи | При пустоте |
|---|---|---|
| активность | агрегация `fsm_transitions` + `events` по дням и часам | `{"days": [...], "hours": [...], "data": [], "has_data": false}` + сообщение в интерфейсе |
| история событий | `events` (записи по событиям устройств) с **исправленной** осью времени | пустой ряд + признак отсутствия |
| подсказки | строки `ai_suggestions` | пустой список + признак отсутствия; выдуманные три записи удаляются |

Плюс: писателей для `save_fsm_transition` и `save_sensor_event` появляются как подписчики шины (тот же механизм, что US1/US3), поэтому «честность» достигается вместе с доставкой, а не отдельной работой.

**Альтернативы.**
- *Оставить выдумку, но помечать.* Отклонено: решение D-2 — удалить полностью.
- *Считать активность по `data/device_sync_events.json` (968 записей).* Отклонено: это административные операции над устройствами (выдача прав, конфиг), а не активность автоматики; подмена одного вымысла другим.
- *Хранить историю переходов в JSON рядом с состоянием.* Отклонено: `EventStore` уже содержит нужную таблицу и метод — дублировать схему незачем.

## R-11. Что сознательно не трогаем

| Элемент | Почему |
|---|---|
| `State`, `Transition`, `FSMDefinition`, дебаунс, таймауты, выбор перехода по порядку | конституция, принцип I: «изменяются только по явному согласованию». План их не касается; в R-02 добавление публикации — побочный эффект, не меняющий решения |
| Реестр гвардов и действий движка (`engine._guards`/`_actions`) | в производстве не используются — фабрика резолвит имена через `Registry` напрямую (`factory.py:186-195`). Мёртвый код, не в объёме фичи |
| `MANUAL_SOURCES` в `ManualLockoutMiddleware` (`core/commands/middleware.py:93-111`) | набор значений недостижим: движок не подставляет `source` в контекст (R-03). Смежный дефект, но трогать его — значит менять приоритеты команд, что выходит за FR-016 |
| Шина HA (`ha_adapter`) и реконнект | закрыты ранее (Known Issue #5, `tests/test_ha_adapter_reconnect.py`) |
| Метрики платромы `/metrics`, сторож | вне объёма по спецификации (F3). `record_fsm_transition` станет вызываемым из того же подписчика — фактическая польза появится автоматически |
| `ContextManager` | подписан на непубликуемые `ha.state_changed`/`platform.started`. Публикация `platform.started` (R-07) оживит его; `ha.state_changed` остаётся мёртвым — вне объёма, фиксируется как Known Issue |
