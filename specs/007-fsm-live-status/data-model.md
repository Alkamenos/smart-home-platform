# Data Model: Live FSM Statuses

**Feature**: specs/007-fsm-live-status | **Дата**: 2026-10-01

Сущности описаны в терминах предметной области. Схема манифеста и формат существующих хранилищ **не меняются** — миграции не требуются (конституция V). Новые сущности добавляются как события (передаются по шине и в REST) и как записи в уже существующие таблицы `EventStore`.

---

## 1. Переход автомата (FSM Transition) — новое событие

Главная сущность фичи: факт смены состояния автомата. Раньше существовал только как строка в журнале (`log.info`), теперь передаётся подписчикам, отдаётся по REST и пишется в журнал переходов.

| Атрибут | Тип | Правила |
|---|---|---|
| `fsm_id` | строка | идентификатор автомата по схеме `{устройство}_{шаблон}_{приоритет}` (ADR-003). Обязателен |
| `device_id` | строка | `target_device_id` из описания автомата — фактическое устройство (например, `light.kitchen`). Обязателен |
| `behavior` | строка | имя шаблона поведения, извлекается из идентификатора. Обязателен |
| `from_state` | строка \| null | предыдущее состояние; `null` при первом входе |
| `to_state` | строка | новое состояние. Обязателен |
| `event` | строка | имя события-триггера, вызвавшего переход (например, `motion_detected`, `manual_switch_on`) |
| `source` | перечисление | `manual` — имя события начинается с `manual_`; `automatic` — иначе (R-03) |
| `timestamp` | строка (ISO-8601) | настенное время в момент перехода. Единый формат для всех разделов интерфейса (R-04) |
| `outcome` | перечисление | `transitioned` (выполнен) \| `rejected` (отказ). Обязателен |
| `reason` | строка \| null | причина отказа: `unknown_entity`, `no_state`, `debounced`, `no_transition`, `guard_failed` |
| `trace_id` | строка | сквозной идентификатор для корреляции по журналу; совпадает с журналом движка |

**Правила валидации** (нарушение → событие не формируется, предупреждение в журнале — FR-008):
1. `fsm_id` непустой.
2. Для `outcome = "transitioned"` обязательны `to_state` и `event`.
3. Для `outcome = "rejected"` обязателен `reason`.
4. `from_state`/`to_state` берутся только из описания автомата; значение вне списка допустимых состояний — признак повреждения, фиксируется в журнале, но не блокирует публикацию.

**Связи**: принадлежит автомату; потребляется хранилищем состояний, журналом переходов, веб-мостом, зеркалом в HA.

**Транспорт**: плоский словарь `dict[str, Any]` — формат, уже принятый шиной событий (`device.*` события используют тот же стиль с ISO-8601 временем).

## 2. Состояние автомата (FSM State) — новое представление в ответах

В движке состояние — dataclass с `current_state`, `entered_at` (монотонные часы цикла, R-04) и `context`. Для интерфейса нужен отдельный, безопасный для показа вид.

| Атрибут | Тип | Правила |
|---|---|---|
| `fsm_id` | строка | идентификатор автомата |
| `device_id` | строка | фактическое устройство |
| `behavior` | строка | имя шаблона поведения |
| `state` | строка | текущее состояние автомата |
| `since` | строка (ISO-8601) \| null | время последнего перехода; `null`, если переходов не было |
| `automated` | логическое | есть ли у устройства автоматика вообще (`false` → состояние не показывается, вместо него «автоматика не настроена») |

**Отличие от внутреннего состояния движка**: `since` — настенное время, а не монотонные часы цикла; внутренний `context` **не** отдаётся наружу (может содержать внутренние параметры шаблона, а FR не требует их раскрытия).

## 3. Устройство в списке (Device) — расширение существующего ответа

Существующий ответ устройства уже содержит `state` (FR-019 требует, чтобы там было реальное состояние автоматики, а не пустое значение).

| Атрибут | Тип | Правила |
|---|---|---|
| `fsm` | список состояний (§2) | по одному элементу на каждый автомат устройства; **пустой список**, если автоматики нет |
| `state.automation` | объект \| null | `{ "configured": false, "reason": "no_automation" }`, когда автоматики нет; иначе `{ "configured": true, "fsm_ids": [...] }` |

**Правило различения** (FR-019, FR-021): пустой результат по автоматике — это не то же, что «сервис недоступен». Недоступность сигнализуется отдельно (код ответа 503 с причиной), а не пустым списком.

**Связи**: устройство → автоматы (0…N) через префикс `{device_id}_` в идентификаторе автомата.

## 4. Живое обновление (Live Update) — сообщение канала устройств

| Атрибут | Тип | Правила |
|---|---|---|
| `type` | строка | `fsm_transition` (совпадает с ожиданием клиента, `index.html:849`) |
| `device_id` | строка (UUID) | устройство-получатель; доставка только подписчикам этого устройства |
| `fsm_id` | строка | автомат, чьё состояние изменилось |
| `from_state` | строка \| null | прежнее состояние |
| `state` | строка | новое состояние |
| `source` | перечисление | `manual` \| `automatic` |
| `timestamp` | строка (ISO-8601) | время перехода |

**Правила доставки** (FR-025, FR-038): сообщение формируется один раз и рассылается только тем соединениям, которые (а) подписаны на это устройство и (б) проходят проверку доступа **в момент отправки**, а не только при подписке.

**Обратная совместимость**: `broadcast_state_change` (используется в `tests/integration/test_access_control.py`) сохраняется и продолжает работать — новое сообщение строится поверх существующего раздатчика.

## 5. Запись журнала переходов (FsmTransition) — существующая таблица, новый писатель

Таблица `fsm_transitions` в `data/history.db` существует (`core/persistence/event_store.py:74`) вместе с методом `save_fsm_transition` (`:134`), но **писателя в `src/` нет**. Фича добавляет подписчика, который сохраняет туда каждый переход.

| Атрибут | Правила |
|---|---|
| `entity_id` | идентификатор устройства, для которого сохранён переход |
| `from_state`, `to_state` | состояния |
| `timestamp` | время перехода |
| `trigger` | событие-триггер |
| `success` | логическое; для отказа — `false` |

**Назначение после фичи**: реальный источник данных для карты активности и истории (FR-033), вместо выдуманных значений.

## 6. Запись события (SensorEvent) — существующая таблица, новый писатель

Таблица `events` (`event_store.py:61`) и метод `save_sensor_event` (`:185`) существуют без писателей. Фича подключает запись событий устройств, приходящих из Home Assistant, через уже существующий обработчик `DeviceService.handle_state_change`.

**Назначение**: график событий за 24 часа получает настоящие данные (FR-033).

## 7. Отсутствие данных (Empty Section) — явное состояние раздела

Вместо выдуманных значений разделы возвращают признак отсутствия данных.

| Раздел | Форма при отсутствии данных |
|---|---|
| карта активности | `{ "days": [...7], "hours": [...24], "data": [], "has_data": false }` |
| история событий | `{ "labels": [...24], "datasets": [], "has_data": false }` |
| подсказки | `{ "suggestions": [], "has_data": false }` |

**Правило** (FR-032, FR-036): ключ `has_data` присутствует **всегда** — и при наличии данных (`true`), и при отсутствии (`false`), чтобы клиент не определял наличие данных по длине массива.

**Различение состояний** (краевой случай спеки): «нет записей» (`has_data: false`) ≠ «сбой чтения данных» (ошибка с описанием) — интерфейс показывает их по-разному.

## Диаграмма состояний (обновление §9 контракта)

Схема остаётся статической структурой; **текущее** состояние приходит отдельным каналом и подсвечивается на клиенте (R-09).

| Атрибут | Правила |
|---|---|
| `diagram` | Mermaid-строка (текст) без конверта JSON; соответствует состояниям описания автомата |
| текущее состояние | передаётся в §2 и §4; диаграмма сама его не содержит |

**Почему так**: перерисовка диаграммы на каждое живое событие означала бы передачу текста схемы по сети при каждом переходе; подсветка на клиенте локальна и мгновенна (FR-030).

## Инварианты

1. **Состояние движка — источник истины.** Всё, что отдаётся наружу (REST, живое сообщение, журнал), выводится из состояния движка на момент запроса (FR-018). Источник события — доставка; источник состояния — `get_all_states()`.
2. **Событие без состояния невозможно**: успешный переход публикуется только после записи нового состояния (R-02), поэтому подписчик, прочитавший состояние после события, всегда увидит новое.
3. **Повтор в то же состояние не порождает событие** (FR-009) — движок не выполняет переход, публиковать нечего.
4. **Устройство без автоматики не порождает пустых состояний**: `fsm: []` и `automation.configured = false` (FR-019).
5. **Запись состояния не зависит от Home Assistant** (FR-015, R-06): персистентность JSON — обязательный путь, зеркалирование в HA — дополнительный.
