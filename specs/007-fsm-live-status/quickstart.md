**Feature**: specs/007-fsm-live-status | **Дата**: 2026-10-01

Руководство по проверке фичи после реализации. Сценарии 1–5 и 9 выполняются **без Home Assistant** (автономный режим). Форматы ответов — в [contracts/fsm-live-api.md](./contracts/fsm-live-api.md), поля событий — в [contracts/fsm-events.md](./contracts/fsm-events.md).

## Сценарий 1. Переход публикуется в шину (US1, FR-001, FR-002) — без HA

**Что проверяем**: успешный переход автомата порождает событие с полным набором полей.

**Как**: unit-тест публикации; вживую — через журнал (публикация логируется).

```bash
# Тест: успешный переход публикует fsm.transitioned с обязательными полями
pytest tests/unit/core/test_fsm_event_publication.py -v
```

Вживую: в журнале запущенной платформы при переходе должна появиться строка публикации события с `fsm.transitioned` и `trace_id`, совпадающим со строкой перехода движка.

**Ожидаемый результат**: событие содержит `fsm_id`, `device_id`, `behavior`, `from_state`, `to_state`, `event`, `source`, `timestamp`, `outcome`, `trace_id`; `trace_id` совпадает с журналом перехода.

## Сценарий 2. Отказ публикуется как отказ, а не как переход (US1, FR-004) — без HA

**Что проверяем**: пять видов отказа дают `outcome: "rejected"` с причиной и не порождают события успешного перехода.

```bash
pytest tests/unit/core/test_fsm_event_publication.py -v -k rejected
```

**Ожидаемый результат**: для каждой причины (`unknown_entity`, `no_state`, `debounced`, `no_transition`, `guard_failed`) — событие с `outcome: "rejected"`, `reason` заполнен, `to_state` пуст; событий `fsm.transitioned` нет.

## Сценарий 3. Медленный подписчик не задерживает переход (US1, FR-013, FR-014, SC-015)

**Что проверяем**: доставка событий неблокирующая.

```bash
pytest tests/unit/core/test_event_bus_handlers.py -v -k slow
```

**Ожидаемый результат**: переход завершается за время, не зависящее от длительности подписчика; событие подписчику приходит позже. Время перехода измеряется отдельно от времени доставки.

## Сценарий 4. Состояние автомата переживает перезапуск (US1, FR-015, SC-016, SC-017) — без HA

**Что проверяем**: FR-015 целиком — сохранение состояния в обоих режимах.

```bash
pytest tests/unit/core/test_fsm_state_persistence.py -v
```

Вживую (автономный режим):

1. Запустить платформу, дождаться готовности.
2. Перевести автомат в не-начальное состояние (через событие или тестовый сценарий).
3. Проверить `GET /api/fsm/state` — состояние отличается от начального.
4. Остановить платформу, запустить заново с тем же `CONFIG_PATH`.
5. Проверить `GET /api/fsm/state` — состояние **то же**, а не начальное.

**Ожидаемый результат**: после перезапуска состояние восстановлено; файл состояний создан рядом с прочими файлами данных (`data/state.json`), не в домашнем каталоге.

**Отдельно (SC-017)**: автомат, снятый с регистрации до перезапуска, не восстанавливается — тест на отсутствие восстановления снятого автомата.

## Сценарий 5. Одна шина событий на процесс (US1, FR-006) — без HA

**Что проверяем**: веб-слой и ядро используют одну шину.

```bash
pytest tests/contract/test_fsm_live_contract.py -v -k event_bus
```

Вживую: в журнале не должно быть предупреждения о недоступности хранилища, а переход должен доходить до веб-слоя (проверяется сценарием 7).

**Ожидаемый результат**: `app.state.event_bus` — тот же объект, что шина контейнера; второго создания шины в веб-слое нет.

## Сценарий 6. Состояния по запросу (US2, FR-017…FR-023)

**Что проверяем**: форма ответа и различение пустого результата с недоступностью сервиса.

```bash
curl -s localhost:8000/api/fsm/state -H "X-User-ID: admin_user" | python3 -m json.tool
```

**Ожидаемый результат**:
```json
{ "count": 3, "states": [ { "fsm_id": "...", "device_id": "...", "behavior": "...",
                          "state": "ON_MOTION", "since": "2026-10-01T14:23:11.482913",
                          "automated": true } ] }
```

| Проверка | Ожидание |
|---|---|
| состояния соответствуют действительности | после перехода в состояние — оно в ответе (SC-004) |
| `since` — настенное время ISO-8601 | не монотонное значение внутренних часов (R-04) |
| нет автоматов | `{"count": 0, "states": []}`, **не** 500 (FR-021) |
| сервис недоступен | `503` с описанием, **не** пустой список (FR-020) |
| время устройства без автоматики | явный признак, не пустое значение (FR-019) |
| автономный режим | ответ работает так же (FR-022) |

## Сценарий 7. Живое обновление в браузере (US3, FR-024…FR-031, SC-003)

**Что проверяем**: обновление без перезагрузки, права доступа, восстановление соединения, диаграмма.

Отдельный прогон Playwright (файл исключён из общего прогона):

```bash
pytest tests/test_webui_playwright.py -v
```

Вручную:

1. Открыть главную страницу. Убедиться, что соединение установлено (признак «есть обновления»).
2. Вызвать переход автомата (событием или командой через диспетчер).
3. **Не перезагружая страницу**, убедиться, что состояние изменилось в течение 2 секунд (SC-003).

| Проверка | Ожидание |
|---|---|
| обновление без перезагрузки | новое состояние видно за ≤2 с |
| состояние при загрузке | видно сразу, без ожидания первого события (FR-028) |
| диаграмма устройства | отображается **схемой**, не JSON-текстом (FR-029) |
| текущее состояние на диаграмме | выделено (FR-030) |
| несколько автоматов одного устройства | видны состояния всех (FR-031) |
| обрыв соединения | виден признак «нет обновлений» за ≤10 с (FR-027) |
| восстановление соединения | пауза растёт; после переподключения состояния актуальны (FR-026) |

## Сценарий 8. Права доступа на живых обновлениях (US3, FR-025, FR-038, SC-009)

**Что проверяем**: события устройств, к которым у пользователя нет доступа, не доставляются.

```bash
pytest tests/integration/test_fsm_live_updates.py -v -k access
```

**Ожидаемый результат**: два пользователя с разными правами подключены к каналу; переход автомата недоступного устройства **не приходит** пользователю без прав; при выдаче права и повторном переходе — приходит. Ни по одному каналу утечек нет.

## Сценарий 9. Честные данные визуализаций (US4, FR-032…FR-037, SC-011…SC-013) — без HA

**Что проверяем**: вместо выдуманных значений — сообщение об отсутствии данных.

```bash
# До перехода: раздел без данных
curl -s localhost:8000/api/history/activity-heatmap | python3 -m json.tool
curl -s localhost:8000/api/events/history | python3 -m json.tool
curl -s localhost:8000/api/ai/suggestions | python3 -m json.tool
```

**Ожидаемый результат** на пустой системе: `has_data: false`, пустые массивы данных. Значения, повторяющиеся при каждом запросе, отсутствуют.

| Проверка | Ожидание |
|---|---|
| два повторных запроса | одинаковый результат (SC-013) |
| после переходов появились данные | `has_data: true`, графики отражают именно эти переходы (SC-012) |
| счётчик на графике равен числу записей | совпадение с тем же разделом по данным (FR-034) |
| подсказки | пустой список, выдуманные записи отсутствуют (FR-035) |
| ось времени графика событий | «00:00» соответствует полуночи, а не 24 часам назад (R-10) |
| интерфейс | вместо пустого графика — сообщение «данных пока нет» |
