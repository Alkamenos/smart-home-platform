# Data Model: Архитектурная гигиена и чистые границы

**Feature**: `018-architecture-hardening` | **Date**: 2026-11-02

Модель описывает понятия, которыми оперирует программа работ. Это не схема
таблиц: у большинства сущностей физическое представление уже есть (манифест,
сессии, артефакты, журнал), а здесь зафиксированы **инварианты**, которые
проверяются тестами.

## 1. HomeDescription — каноническое описание дома

**Что это**: единственный документ, описывающий дом: экземпляр, комнаты,
локации, датчики, приборы, поведения, правила дома, панель.

**Ключевые атрибуты**:

| Атрибут | Смысл | Правило |
|---|---|---|
| `version` | версия формата | целое ≥ 1; неизвестная версия — отказ |
| `instance` | дом и владелец | обязателен; имя непустое |
| `rooms` / `locations` | места | уникальные `id` в пределах дома |
| `devices` | приборы | уникальные `id`; ссылки на датчики существуют |
| `behaviors` | поведения | шаблон существует; приоритет уникален в приборе |
| `automation_rules` | правила дома | ссылки на сущности непустые |
| `dashboard` | панель | только известные поля |
| `extensions` | явные расширения | только с префиксом, если включены |

**Инварианты**:

- `INV-HD-1`: любое чтение и запись описания проходит через одну модель и один
  набор правил.
- `INV-HD-2`: неизвестное поле отклоняется с путём до поля; молчаливого
  игнорирования нет.
- `INV-HD-3`: сохранение атомарно: при ошибке старое описание остаётся
  действующим.
- `INV-HD-4`: все ссылки между местами, датчиками и приборами разрешаются до
  сохранения.
- `INV-HD-5`: описание прежней версии загружается без потери данных; умолчания
  задокументированы.

**Связи**: `HomeDescription` → `Room`/`Location` → `Device` → `Behavior`;
`AutomationRules` ссылается на внешние сущности по идентификаторам.

## 2. ActorIdentity — участник

**Что это**: подтверждённый субъект, от имени которого выполняется операция.

| Атрибут | Смысл | Правило |
|---|---|---|
| `subject` | идентификатор | непустой; выдаётся сервером |
| `roles` | роли | owner / guest / automation / monitor |
| `source` | откуда идентичность | ingress / session / token |
| `trusted` | подтверждена ли | только серверное решение |

**Инварианты**:

- `INV-AI-1`: идентичность и роли не выводятся из заголовков, присланных
  клиентом.
- `INV-AI-2`: ingress-идентичность принимается только от доверенного прокси.
- `INV-AI-3`: отсутствие идентичности — не «пользователь по умолчанию», а отказ
  для изменяющих операций.
- `INV-AI-4`: роли неизменяемы в рамках запроса; повышение прав — отдельная
  операция с аудитом.

## 3. ManagementOperation — операция управления

**Что это**: изменение описания, команда прибору, публикация панели, выдача
доступа.

| Атрибут | Смысл |
|---|---|
| `kind` | manifest.write / device.command / dashboard.publish / access.grant |
| `target` | что именно меняется |
| `actor` | `ActorIdentity` |
| `decision` | allow / deny |
| `reason` | названная причина отказа |
| `trace_id` | сквозная корреляция |

**Состояния**:

```text
requested → authenticated → authorized → applied → audited
     │             │              │
     └─────────────┴──────────────┴──→ rejected (reason, trace_id)
```

**Инварианты**:

- `INV-MO-1`: default deny; allowlist только для операций состояния.
- `INV-MO-2`: каждый отказ попадает в журнал с источником, операцией и
  причиной.
- `INV-MO-3`: успешная изменяющая операция оставляет след, связанный с
  `trace_id`.
- `INV-MO-4`: операция не считается успешной, если изменение не применилось к
  работающей системе.

## 4. BuildArtifact — артефакт поставки

**Что это**: результат сборки, который можно воспроизвести и проверить.

| Атрибут | Смысл |
|---|---|
| `commit` | исходный коммит |
| `dependency_lock_hash` | хэш зафиксированного набора зависимостей |
| `image_digest` | digest образа |
| `vulnerabilities` | найденные уязвимости по уровням |
| `sbom` | состав компонентов |
| `runtime_user` | пользователь процесса |

**Инварианты**:

- `INV-BA-1`: одинаковый `commit` + lock дают одинаковый набор зависимостей.
- `INV-BA-2`: критическая или высокая уязвимость блокирует выпуск.
- `INV-BA-3`: runtime-образ не содержит сборочного инструментария и работает не
  от root.
- `INV-BA-4`: отсутствие проверки не трактуется как «чисто»; выпуск не
  подменяется догадкой.

## 5. ModuleBoundary — граница модуля

**Что это**: набор ответственностей с одной причиной изменения.

| Атрибут | Смысл |
|---|---|
| `name` | модуль/пакет |
| `responsibility` | одна причина изменения |
| `public_contract` | что видно снаружи |
| `allowed_dependencies` | куда можно импортировать |
| `size_budget` | порог размера |

**Инварианты**:

- `INV-MB-1`: `core` не импортирует `adapters`, `webui`, `services`.
- `INV-MB-2`: доменная модель существует в одном экземпляре; на границах —
  только DTO.
- `INV-MB-3`: новый модуль не превышает согласованный порог; существующие
  крупные сокращаются по плану.
- `INV-MB-4`: публичный контракт модуля не меняется при внутреннем разделении
  без явного решения.

## 6. FailureEvent — событие отказа

**Что это**: запись о том, что пошло не так, с классификацией.

| Атрибут | Смысл |
|---|---|
| `class` | expected / defect / safety |
| `source` | модуль, сущность, операция |
| `reason` | названная причина |
| `trace_id` | корреляция |
| `action` | что сделано или почему ничего |

**Инварианты**:

- `INV-FE-1`: ожидаемый отказ не маскируется под дефект и наоборот.
- `INV-FE-2`: авария всегда имеет отдельный канал и приоритет.
- `INV-FE-3`: каждый отказ связан с решением и командой по `trace_id`.
- `INV-FE-4`: широкий перехват допустим только на границе, где продолжение
  работы безопаснее падения, и обязан классифицировать причину.

## Связи между сущностями

```text
ActorIdentity ──выполняет──→ ManagementOperation ──меняет──→ HomeDescription
                                     │
                                     ├──порождает──→ FailureEvent
                                     └──фиксируется в──→ журнал (trace_id)

BuildArtifact ──поставляет──→ работающая система
ModuleBoundary ──ограничивает──→ код, который исполняет операции
```

## Правила проверки (сводка)

| Правило | Где проверяется |
|---|---|
| Одно описание, одна проверка | unit + contract: round-trip всех полей |
| Нет параллельных доменных моделей | `tests/architecture` |
| Default deny | матрица ролей × маршруты |
| Подделанный админ не работает | contract: spoofed headers |
| Воспроизводимость | CI: две чистые сборки, сравнение lock |
| Уязвимости блокируют выпуск | CI: подложенная зависимость |
| Ядро без адаптеров | `tests/architecture` (AST) |
| Различимость отказов | три сценария: нет данных / дефект / авария |
| Контракт ошибки един | contract: все маршруты |
| Мёртвый код отсутствует | инвентаризация + тест на список исключений |
