# Implementation Plan: Архитектурная гигиена и чистые границы

**Branch**: `018-architecture-hardening` | **Date**: 2026-11-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/018-architecture-hardening/spec.md`

## Summary

Программа из шести независимых срезов, которая приводит архитектуру к
собственной конституции проекта (принцип IV: Core не зависит от Adapters) и
убирает классы дефектов, найденные аудитом 02.11.2026:

1. одно каноническое описание дома;
2. подтверждённая граница управления;
3. воспроизводимая и проверяемая поставка;
4. локальность изменения и разделение крупных модулей;
5. различимые отказы и явные контракты;
6. удаление мёртвого кода и синхронизация документации.

Поведение автоматики дома не меняется. Каждый срез можно выпускать отдельно;
порядок выбран так, чтобы более поздние срезы опирались на уже стабилизированные
контракты, а не наоборот.

## Technical Context

**Language/Version**: Python 3.12 (backend, CLI), TypeScript / React 19 (frontend)

**Primary Dependencies**: Pydantic v2, FastAPI, uvicorn, loguru, aiohttp,
websockets, prometheus-client, SQLite (stdlib), Next.js 16, pytest, vitest,
Playwright

**Storage**: JSON-файлы (манифест, состояния, доступы) + SQLite (`history.db`);
переход на другую СУБД не требуется

**Testing**: pytest (unit / contract / integration / architecture), vitest,
Playwright; текущий baseline — 3418 passed / 19 skipped, покрытие 84 %

**Target Platform**: Linux-контейнер в домашней сети; разработка допускается на
Windows, эксплуатация — Linux

**Project Type**: модульный монолит: доменное ядро + адаптеры + прикладные
сервисы + Web UI + CLI

**Performance Goals**: домашний масштаб — 27 автоматов, ~1600 сущностей HA,
один дом. Целевые показатели — не пропускная способность, а предсказуемость:
готовность после старта не хуже текущей, синхронизация источника — в пределах
измеренного baseline (~2.6 с), отсутствие деградации времени отклика UI

**Constraints**: поведение автоматики — эталон; один дом и один владелец;
доверенная сеть / ingress HA; без новых пользовательских функций; без перехода
на другую СУБД или брокер; постепенный рефакторинг с откатом

**Scale/Scope**: ~41 тыс. строк `src`, ~65 тыс. строк тестов, 47 внешних
маршрутов, 6 срезов, 22 функциональных требования

размеров модулей.

## Implementation Waves

Срезы независимы по приёмке, но имеют естественный порядок: A стабилизирует
описание дома, B — границу доступа, C не зависит ни от чего, D опирается на A,
E — на B и D, F завершает.

### Wave A — Одно описание дома (P1)

- Каноническая модель: `core/models/manifest.py` — единственный источник.
- JSON Schema и валидация — из модели; политика неизвестных полей
  зафиксирована контрактом.
- Удаление параллельных схем и дублирующей модели WebUI после перевода
  сохранения на каноническую модель.
- WebUI получает DTO только для представления, не для доменной проверки.
- Приёмка: round-trip каждого поля, ошибки по полям, совместимость старых
  манифестов.

### Wave B — Граница управления (P1)

- Глобальная проверка идентичности с явным allowlist для состояния
  (`/health`, `/ready`, `/metrics`).
- Идентичность и права — только серверные; заголовки клиента не повышают права.
- Защита изменяющих операций: манифест, публикация панели, команды, доступы.
- Журнал отказов с источником, операцией и причиной.
- Приёмка: матрица «аноним / гость / владелец / ingress» для всех маршрутов.

### Wave C — Воспроизводимая поставка (P2)

- Зафиксированный набор Python-зависимостей; сборка из lock-файла.
- Закрепление базовых образов; runtime без сборочных пакетов; non-root.
- Проверки уязвимостей и SBOM в конвейере; блокировка выпуска при
  критической/высокой уязвимости.
- Приёмка: две чистые сборки дают один набор; подложенная уязвимость
  блокируется; образ запускается без root.

### Wave D — Локальность изменения (P2)

- Composition root вынесен из `core` в `src/app/`.
- Поэтапное разделение `HAAdapter`, `FSMEngine`, `Container`, `Watchdog`,
  `DeviceService` за стабильными фасадами; публичное поведение сохраняется.
- Автоматические проверки: запрет `core → adapters`, порог размера модуля,
  отсутствие параллельных доменных моделей.
- Приёмка: тесты зелёные после каждого шага; откат возможен.

### Wave E — Видимые отказы и контракты (P2)

- Классификация: ожидаемый отказ, дефект, авария; разные каналы и причины.
- Контракты ответов и единый формат ошибки для внешних операций.
- Структурированный журнал (опционально JSON) и сквозная корреляция
  `trace_id` от события до команды и результата.
- Приёмка: три класса событий различимы без чтения кода; контракт ошибки
  совпадает у всех маршрутов.

### Wave F — Чистота и документация (P3)

- Инвентаризация: мёртвые сервисы, параллельные схемы, выключенные
  возможности.
- Удаление или явная пометка «экспериментально» с условиями и рисками.
- Синхронизация Known Issues, Roadmap, BACKLOG с кодом.
- Приёмка: у каждого production-модуля есть вызов или пометка; статусы
  документации совпадают.

## Complexity Tracking

Нарушений конституции, требующих оправдания, нет. Существующее нарушение
принципа IV не оправдывается, а устраняется в Wave D. Новые абстракции
вводятся только там, где они убирают дублирование или делают проверку
автоматической; «слои ради слоёв» не добавляются.
