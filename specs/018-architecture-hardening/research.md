# Research: Архитектурная гигиена и чистые границы

**Feature**: `018-architecture-hardening` | **Date**: 2026-11-02

Шесть решений Phase 0. Каждое фиксирует выбор, причину и отвергнутые
альтернативы; реализация и порядок — в `plan.md`, задачи — в `tasks.md`.

## D1. Одно каноническое описание дома

**Decision**: единственный источник — Pydantic-модель `core/models/manifest.py`.
JSON Schema для интерфейса и документации генерируется из неё
(`Manifest.model_json_schema()`). Политика неизвестных полей — `extra="forbid"`:
опечатка в имени поля должна быть ошибкой, а не молчаливым игнором. Для
расширений, если понадобятся, вводится явное пространство `extensions`, а не
«что угодно рядом».

**Rationale**: сейчас описание дома определено четырьмя способами
(`core/models`, `webui/models`, `manifest_schema`, `manifest_validator`).
Сохранение через WebUI идёт через вторую модель, а исполнение — через первую;
это класс дефектов, который проявляется через недели. Генерация схемы из модели
делает расхождение физически невозможным.

**Alternatives considered**:
- `extra="allow"` с сохранением неизвестных полей — удобно для отката версий,
  но скрывает опечатки и оставляет мусор в боевом манифесте. Для одного дома
  откат версий не является рабочим сценарием.
- `extra="ignore"` — худший вариант: данные теряются молча.
- Оставить `ManifestModel` в WebUI как «форму» — отклонено: это и есть второй
  источник истины. DTO допустимы только для ответа, не для проверки.

## D2. Граница управления

**Decision**: глобальная проверка идентичности с явным allowlist. Идентичность
и роли определяются сервером:

- запрос от ingress Home Assistant принимается только из доверенного
  прокси-диапазона; имя пользователя берётся из ingress-заголовков, потому что
  аутентификацию выполнил HA;
- прямой доступ в локальной сети требует сессии: вход по паролю владельца
  (секрет из окружения) выдаёт подписанную HttpOnly-cookie; API и CLI используют
  bearer-токен;
- `X-User-ID` и `X-Is-Admin` от клиента не повышают права и не являются
  идентичностью;
- allowlist без идентичности: `/health`, `/ready`, `/metrics`, статика и вход.

**Rationale**: сейчас защита точечная (только `/api/v1/devices/**`), а признак
администратора приходит от клиента; манифест и публикация панели вне защиты.
Для домашней сети это допустимо только пока порт доступен исключительно
доверенному хосту — то есть «безопасно по случайности». Серверная сессия и
default deny убирают эту случайность.

**Alternatives considered**:
- OAuth2/OIDC — избыточно для одного владельца и добавляет внешнюю зависимость.
- Basic Auth на reverse proxy — добавляет компонент и не решает авторизацию по
  ролям внутри приложения.
- Оставить заголовки, но «доверять только с localhost» — ломается при доступе с
  телефона и не покрывает ingress.
- Полноценная база пользователей — не нужна: владелец один, гости не управляют.

**CSRF**: cookie-сессия для UI требует `SameSite=Strict` и проверки `Origin`
для изменяющих запросов. Bearer-токен CSRF не подвержен.

## D3. Воспроизводимая поставка

**Decision**: `uv` + `uv.lock` как единственный зафиксированный набор
Python-зависимостей; сборка и CI используют `uv sync --frozen`. Базовые образы
закрепляются по digest. В конвейер добавляются `pip-audit` (Python-зависимости),
Trivy (образ), SBOM (Syft), Dependabot для Docker. Runtime-образ — multi-stage,
без компиляторов, non-root, read-only FS с tmpfs, `cap_drop: [ALL]`,
`no-new-privileges`, лимиты памяти/CPU.

**Rationale**: сейчас зависимости объявлены как `>=` без lock-файла, базовые
образы плавающие, проверок уязвимостей нет. «Собралось вчера» и «собралось
сегодня» — разные системы; для дома это означает невоспроизводимое
восстановление после сбоя.

**Alternatives considered**:
- `pip freeze` — фиксирует и транзитивные, но не обновляется осознанно и не
  даёт разрешения конфликтов.
- Poetry/PDM — рабочие варианты, но `uv` быстрее и уже совместим с PEP 621;
  принципиальной разницы нет, выбран один инструмент.
- Не сканировать, «доверять Dependabot» — Dependabot предлагает обновления, но
  не блокирует выпуск с известной уязвимостью.

## D4. Локальность изменения и границы

**Decision**: composition root выносится из `core` в `src/app/`; `core` не
импортирует `adapters`, `webui`, `services`. Крупные модули делятся
**фасадами**: публичный API сохраняется, внутренние обязанности выносятся в
пакеты. Правила проверяются тестами в `tests/architecture/`:

1. запрет импортов `core → adapters/webui/services`;
2. отсутствие параллельных доменных моделей;
3. порог размера: новые файлы ≤ 800 строк, существующие крупные — в
   allowlist с целью сокращения ≥ 50 %;
4. `core` не импортирует FastAPI/Next-специфику.

**Rationale**: цель — не «красивые папки», а локальность правки. Сейчас
`HAAdapter` (2206 строк), `FSMEngine` (1695), `Container` (1439), `Watchdog`
(1200), `DeviceService` (1204) требуют держать в голове слишком много
контекста, а `core/container.py` нарушает конституцию IV.

**Alternatives considered**:
- Полный редизайн слоёв «с нуля» — высокий риск регрессии поведения дома.
- `import-linter` — хороший инструмент, но добавляет зависимость; на первом
  этапе достаточно AST-теста, позже можно заменить.
- Деление по «техническим» слоям (все репозитории, все сервисы) — не совпадает
  с причинами изменения в этом домене.

## D5. Отказы, контракты и наблюдаемость

**Decision**: три класса отказов, различаемых явно:

- **ожидаемое состояние** — нет данных, прибор недоступен, ручной оверрайд:
  возвращается причиной и не считается дефектом;
- **дефект** — непредвиденное исключение: журнал уровня error, корреляция,
  отсутствие маскировки под «нет данных»;
- **авария** — нарушение правила безопасности: отдельный канал/тревога,
  команда обходит обычные ограничения.

Внешние операции получают DTO ответа (`response_model`) без изменения текущих
форм успеха; ошибки — единый конверт `{error: {code, message, fields?,
trace_id}}`. Журнал остаётся человекочитаемым по умолчанию, но получает
опциональный JSON-режим и обязательные поля корреляции (`trace_id`, `fsm_id`,
`device_id`, `reason`).

**Rationale**: широкий `except Exception` (277 мест) делает систему устойчивой,
но стирает разницу между «датчик молчит» и «в коде ошибка». Контракт ответа
сейчас не описан: 47 маршрутов, один `response_model`.

**Alternatives considered**:
- OpenTelemetry сразу — полезно, но добавляет инфраструктуру и объём; достаточно
  корреляции и структурного журнала, OTel — следующий шаг.
- Полный редизайн ошибок в домене — слишком крупно; классификация вводится на
  границах и постепенно проникает в домен.
- Универсальная обёртка успеха `{data: ...}` — ломает существующих клиентов без
  пользы для дома.

## D6. Чистота и мёртвый код

**Decision**: инвентаризация и правило:

- production-код без вызова → удалить;
- возможность, которая может понадобиться → явный флаг, документация условий,
  риск и тест; по умолчанию выключена;
- решение владельца требуется только там, где есть продуктовая ценность
  (например, судьба `BackupService` — B13/B14).

Кандидаты, известные на 02.11: `BackupService`, `manifest_schema.py`,
`manifest_validator.py`, `bootstrap.py`, неиспользуемые guard'ы
(`is_day_time`, `has_usable_reading`, `at_or_above_setpoint`, `below_setpoint`,
`climate_is_enabled`, `managed_by_hardware_ok`), два CLI-дерева
(`src/cli` и `src/smart_home/cli`), `ConfigWatcher` по умолчанию выключен.

**Rationale**: мёртвый код не ломает дом, но создаёт ложное ощущение
возможностей и замедляет каждую следующую правку. Правило «удалить или
пометить» делает состояние однозначным.

**Alternatives considered**:
- Оставить «на всякий случай» — именно так появились параллельные схемы.
- Удалить всё сразу, включая спорное — риск потерять нужную владельцу
  возможность (backup). Поэтому для продуктовых решений — явный запрос.

## Открытые решения владельца

Не блокируют Waves A–E, нужны к Wave F:

- судьба резервного копирования: `BackupService` и `BACKUP_DEST_DIR`
  (B13/B14);
- нужен ли вход по паролю для прямого LAN-доступа или достаточно ingress HA
  (влияет на объём Wave B, но не на принцип default deny).

Если ответа не будет, применяются умолчания из Assumptions спецификации:
резервное копирование остаётся на том же хосте с предупреждением, прямой
доступ требует сессии.
