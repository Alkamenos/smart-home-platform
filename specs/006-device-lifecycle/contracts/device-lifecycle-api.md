# Contract: REST API жизненного цикла устройств

**Feature**: specs/006-device-lifecycle | **Дата**: 2026-09-30

Область контракта: `/api/v1/devices/**` и мастер (`/api/v1/devices/sources/**`). Существующие контракты сохраняются, кроме явно отмеченных изменений. Транспорт: HTTP/1.1 + JSON, аутентификация — заголовки `X-User-ID` и `X-Is-Admin` (см. «Идентификация»).

## Идентификация

| Заголовок | Обязательность | Значение |
|---|---|---|
| `X-User-ID` | обязателен для `/api/v1/devices/**`, кроме `GET /api/v1/devices` и `POST /api/v1/devices/sources` | идентификатор пользователя |
| `X-Is-Admin` | необязателен | `true` — права администратора (снимает проверку роли) |

Интерфейс передаёт заголовки автоматически для всех своих запросов (D-008); сервер задаёт значения по умолчанию из окружения (`WEBUI_DEFAULT_USER_ID`, `WEBUI_DEFAULT_USER_ADMIN`).

## Формат ответа устройства

`GET /api/v1/devices` и `GET /api/v1/devices/{id}` возвращают список/объект устройства:

```json
{
  "id": "3f7bcdb0-3dfd-4940-b10e-8625a8772e1d",
  "name": "Кухонный свет",
  "display_name": "Кухонный свет",
  "device_type": "light",
  "status": "available",
  "state": { "state": "on", "brightness": 200 },
  "source_id": "29a65033-2c48-4d1e-8a5f-9e0a1b2c3d4e",
  "ha_entity_id": "light.kitchen",
  "ha_area_id": null,
  "description": "Основное освещение кухни",
  "location": "Кухня",
  "tags": ["lighting", "kitchen"],
  "created_at": "2026-09-30T10:00:00",
  "updated_at": "2026-09-30T18:27:32"
}
```

Изменение по сравнению с текущим поведением: список формируется из единого источника (сервис устройств), а не из временного словаря роутов. Форма ответа совместима с текущей (тесты `test_devices_api`, `test_sources_api` проверяют поля `id`, `name`, `device_type`, `status`, `ha_entity_id`).

**Изменение поведения**: после перезапуска сервера и после синхронизации список содержит сохранённые устройства (сейчас всегда пуст).

---

## 1. `GET /api/v1/devices` — список устройств

**Назначение**: список устройств, доступных пользователю (FR-003, FR-019).

| Параметр | Тип | Обязательность | Описание |
|---|---|---|---|
| `source_id` | UUID (query) | нет | фильтр по источнику; применяется **после** фильтра по правам |

**Ответ**: `200` + массив объектов устройства.

**Правила**:
- без `X-User-ID` — `[]` (текущее поведение сохранено);
- устройства, к которым у пользователя нет прав, не попадают в список;
- устройства в статусе `removed_from_ha` остаются в списке (их видно с пометкой статуса) — чтобы пользователь мог вернуть устройство вручную.

**Ошибки**: `500` — внутренняя ошибка (с понятным `detail`).

---

## 2. `GET /api/v1/devices/{device_id}` — устройство

**Ответ**: `200` + объект устройства.

**Ошибки**: `404` — устройство не найдено; `403` — недостаточно прав (роль зрителя); `401` — нет идентификации; `503` — сервис устройств не инициализирован.

---

## 3. `PUT /api/v1/devices/{device_id}/config` — конфигурация устройства

**Тело запроса** (все поля необязательные):

| Поле | Тип | Ограничения |
|---|---|---|
| `display_name` | строка \| null | 1…255 символов; пустая строка — отказ |
| `description` | строка \| null | ≤1000 символов |
| `location` | строка \| null | ≤255 символов |
| `tags` | массив строк \| null | ≤10 тегов, каждый ≤50 символов |

**Ответ**: `200` + объект устройства с обновлённой конфигурацией.

**Правила**: обновление конфигурации **не требует** перезапуска и не влияет на машины состояний; результат переживает перезапуск; операция пишет аудит-событие `config_changed` с изменёнными полями.

**Ошибки**: `400`/`422` — нарушение ограничений с указанием поля и причины; `404` — устройство не найдено; `403` — требуется роль администратора; `401` — нет идентификации.

---

## 4. `POST /api/v1/devices/apply` — применение устройств (канонический путь)

**Назначение**: единственная точка применения набора устройств (мастер и форма комнаты). Заменяет текущее состояние, при котором обработчик этого адреса — чтение списка (FR-005).

**Тело запроса**:

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `source_id` | UUID | да | источник, из которого берутся устройства |
| `selections` | массив объектов | да | список применяемых устройств (пустой массив допустим) |
| `dry_run` | булево | нет (по умолчанию `false`) | предпросмотр без применения |

**Элемент `selections`**:

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `ha_entity_id` | строка | да | идентификатор устройства в Home Assistant |
| `device_type` | строка | да | тип устройства |
| `name` | строка | да | имя устройства (по умолчанию — идентификатор) |
| `behaviors` | массив объектов | нет | поведения: `{ "template": "...", "priority": 10, "params": {} }` |
| `target_room` | строка | нет | идентификатор комнаты; не задан — создаётся новая по имени области/устройства |
| `ha_area_id` | строка \| null | нет | область Home Assistant |

**Ответ `200`** (успех):

```json
{
  "success": true,
  "devices_added": 3,
  "devices_updated": 1,
  "failed": 0,
  "failed_devices": [],
  "backup_path": "instances/leonids_house/manifest.yaml.bak"
}
```

**Ответ при `dry_run: true`**: `200` + `{ "dry_run": true, "would_add": 3, "devices": [ ... ] }` — манифест и устройства не изменяются.

**Правила**:
- **идемпотентность**: повторное применение тех же данных не создаёт дублей — устройство с тем же `ha_entity_id` и тем же источником обновляется (FR-008);
- применяются **только** переданные устройства (FR-012);
- каждое применённое устройство: появляется в манифесте, в постоянном хранилище, в списке, получает машины состояний, **без перезапуска** (FR-014);
- интерфейс, читающий ответ, может полагаться на поле `success` (текущий мастер этого не мог делать);
- результат переживает перезапуск (FR-004).

**Ошибки**: `400` — невалидные данные с указанием устройства и причины; `401` — нет идентификации; `403` — требуется роль администратора; `404` — источник не найден; `503` — сервис недоступен.

---

## 5. `DELETE /api/v1/devices/{device_id}` — удаление устройства

**Назначение**: полное снятие устройства (FR-024…027).

**Ответ**: `204` без тела.

**Побочные эффекты** (все выполняются до ответа): снятие машин состояний → отзыв всех записей о доступе → удаление из постоянного хранилища, кэша и индексов → удаление из манифеста → перестроение маршрутизации → аудит `device_deleted`.

**Правила**:
- идемпотентно: удаление отсутствующего устройства — `204` (а не `404`), чтобы повторные нажатия не ломали сценарий;
- после удаления события от связанных датчиков не вызывают команд этому устройству (FR-017);
- устройство не возвращается в списках после перезапуска (в том числе через записи о доступе — они отозваны).

**Ошибки**: `401`, `403` (требуется администратор), `503`.

---

## 6. `GET /api/v1/devices/{device_id}/events` — история устройства

Существующий контракт сохраняется: `200` + список записей жизненного цикла, `404` — устройство не найдено, `403`/`401` — права/идентификация. Дополняется новыми типами событий из раздела «Запись жизненного цикла» (data-model).

---

## 7. `POST /api/v1/devices/{device_id}/command` и `GET /api/v1/devices/{device_id}/command/{command_id}`

Контракты сохраняются. Изменение: команды исполняются через сервис устройств, связанный с Home Assistant (FR-016) — в автономном режиме команда завершается понятной ошибкой, а не «503 адаптер не настроен» из-за неподключённого адаптера.

---

## 8. `GET /api/v1/devices/sources/{source_id}/discovery-data` — данные мастера

**Назначение**: реальные устройства и области источника (FR-010). Текущая реализация — заглушка с нулями; заменяется.

**Ответ `200`**:

```json
{
  "source_id": "29a65033-2c48-4d1e-8a5f-9e0a1b2c3d4e",
  "areas": [ { "id": "kitchen", "name": "Кухня", "icon": null, "picture": null } ],
  "available_devices": [
    {
      "entity_id": "light.kitchen",
      "friendly_name": "Кухонный свет",
      "device_type": "light",
      "area_id": "kitchen",
      "area_name": "Кухня",
      "state": "on",
      "icon": null
    }
  ],
  "available_device_count": 1
}
```

**Правила**:
- данные берутся из источника по его адресу и учётным данным; глобальное соединение не используется (работоспособно в автономном режиме);
- при недоступном источнике — `200` с пустым списком **и** заполненным сообщением об ошибке в теле ответа (см. ниже), либо `502`/`503`; интерфейс обязан показать причину, а не «устройств нет» (FR-013);
- `404` — источник не найден; `401`/`403` — идентификация/права.

**Форма сообщения об ошибке источника** (дополнение, обратно совместимо):

```json
{
  "source_id": "…",
  "areas": [],
  "available_devices": [],
  "available_device_count": 0,
  "error": "Не удалось подключиться к источнику: таймаут соединения"
}
```

---

## 9. `POST /api/v1/devices/sources` — создание источника

Существующий контракт: `201` + объект источника; `422` — невалидные имя/адрес/токен. Мастер использует его для формы создания источника (FR-011). Ответ содержит `url` в том виде, в котором его задал пользователь (без нормализующего завершающего слэша).

## 10. `POST /api/v1/devices/sources/{source_id}/sync` — синхронизация

Существующий контракт: `200` + `{ "status": "success", "message": "…", "device_count": N }`; при ошибке подключения — `500` с `detail` (это поведение закреплено тестами, FR-023: ранее загруженные устройства не теряются).

**Изменение**: после успешной синхронизации устройства появляются в `GET /api/v1/devices` без перезапуска (FR-019); повторная синхронизация обновляет существующие записи (FR-020); устройства, исчезнувшие из источника, получают статус `removed_from_ha` и теряют активную автоматику (FR-022).

---

## Формат ошибок

Единый для всех операций:

```json
{ "detail": "<человекочитаемое сообщение на русском, с указанием причины отказа>" }
```

Для `POST /api/v1/devices/apply` дополнительно используются поля `failed` и `failed_devices` (список `{ "ha_entity_id": "...", "reason": "..." }`), чтобы интерфейс мог показать частичный успех.
