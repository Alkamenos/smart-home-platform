# Contract: мастер поиска устройств (взаимодействие с интерфейсом)

**Feature**: specs/006-device-lifecycle | **Дата**: 2026-09-30

Описывает поведение мастера со стороны пользователя и правила его связи с API. Транспортные детали — в [device-lifecycle-api.md](./device-lifecycle-api.md).

## Роли в мастере

| Роль | Что делает |
|---|---|
| **Администратор** | создаёт источник, запускает поиск, выбирает устройства, применяет |
| Зритель | мастер доступен только для чтения: поиск работает, кнопки изменения недоступны |

## Сценарий 1. Первый запуск: источника нет

1. Пользователь открывает мастер → видит карточку выбора источника со **списком источников** и **формой создания источника** (имя, адрес, токен).
2. При пустом списке форма — основной элемент карточки (сейчас вместо неё текстовая подсказка с командой `curl`).
3. Отправка формы создаёт источник и **сразу** переходит к поиску — без ручного обновления страницы.

**Условия приёмки**:
- форма содержит понятные подписи и подсказку о формате адреса;
- ошибка создания (невалидный адрес, короткий токен) показывается рядом с формой, с указанием поля;
- после успешного создания источник появляется в списке и выбирается.

## Сценарий 2. Поиск устройств

1. Пользователь выбирает источник → нажимает «Сканировать».
2. Интерфейс запрашивает данные источника и **отрисовывает реальные устройства**: имя, идентификатор, тип, область/комната, состояние, признак «применить автоматически».
3. Показываются фильтры (домен, категория, область, поиск по имени) и счётчики: всего найдено, требует внимания (без автоприменения), выбрано.
4. Есть постраничная навигация при большом числе устройств.

**Условия приёмки**:
- при источнике, содержащем хотя бы одно устройство, список **не пуст** (SC-003);
- признак «применить автоматически» берётся из ответа источника, а не выставляется всем подряд (сейчас всегда `true`);
- категории в фильтрах соответствуют категориям платформы (значения из ответа, а не отдельный список в интерфейсе);
- **при недоступном источнике** показывается причина («не удалось подключиться…»), а не «устройств нет» (FR-013); счётчик «всего найдено» при этом не показывается как 0 успеха;
- при пустом результате (источник доступен, устройств нет) — отдельный понятный текст «устройств не найдено»;
- все запросы интерфейса передают идентификацию (FR-009), поэтому мастер не получает отказов доступа (SC-004).

## Сценарий 3. Применение выбранных устройств

1. Пользователь отмечает устройства (флажками или массово: «выбрать все», «только с автоприменением», «очистить»), при необходимости назначает комнату (по области Home Assistant либо своей).
2. Нажимает «Тестовый запуск» → интерфейс показывает предпросмотр: что будет добавлено, в какие комнаты, с какими поведениями; **ничего не меняется**.
3. Нажимает «Применить» → интерфейс показывает результат: сколько добавлено, сколько обновлено, какие не удались и почему.
4. После применения список устройств **на главной странице и в мастере** содержит новые устройства, а они **сразу работают** (реагируют на события датчиков) — без перезапуска (SC-001, SC-002).

**Условия приёмки**:
- применяются только выбранные устройства; невыбранные не появляются;
- предпросмотр не меняет данные (проверяется отсутствием изменений в манифесте и списке);
- повторное применение тех же данных не создаёт дублей (SC-005 на трёх прогонах);
- сообщение об успехе **не исчезает** само через несколько секунд;
- частичный успех показывается честно: «3 добавлено, 1 не удалось: <причина>»;
- для устройства без корректного шаблона поведения применяется только то, что можно применить, и это видно в результате.

## Сценарий 4. Удаление устройства

1. На странице устройства (или в списке) доступно действие «Удалить» для администратора.
2. Пользователь подтверждает действие.
3. Устройство исчезает из списка; его автоматика прекращает работу; в истории устройства остаётся запись об удалении.

**Условия приёмки**:
- повторное удаление не приводит к ошибке (идемпотентно);
- после удаления события от датчиков не вызывают команд этому устройству (SC-006);
- устройство не возвращается после перезапуска.

## Правила интерфейса

| Правило | Требование |
|---|---|
| Идентификация | Все запросы интерфейса к `/api/v1/**` несут `X-User-ID`/`X-Is-Admin`; значения приходят из серверной разметки (D-008) |
| Экранирование | Значения из источника (имена, идентификаторы) вставляются в разметку только с экранированием |
| Ошибки | Сообщение об ошибке показывается в зоне статуса; тексты на русском; «успех при нуле устройств» недопустим |
| Пустые состояния | Отдельные состояния: «нет источников», «нет устройств», «источник недоступен» |
| Отзывчивость | Индикатор занятости на время запросов; кнопки блокируются на время применения (защита от двойной отправки) |
| Мёртвый код | В странице мастера не остаётся неисполняемых блоков скриптов и неиспользуемых подключений |

## Что мастер не делает

- Не применяет устройства автоматически без явного выбора пользователя (принцип «контроль за пользователем»).
- Не создаёт источники «по умолчанию» — источник либо создан пользователем, либо его нет.
- Не обходит защиту доступа: если прав недостаточно, интерфейс показывает отказ, а не пытается обойти его.
