# Implementation Plan: Device Lifecycle (жизненный цикл устройства)

**Branch**: `main` (разработка в `main` — `.ai/CONTEXT.md`) | **Date**: 2026-09-30 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/006-device-lifecycle/spec.md`

## Summary

Делаем добавление устройства сквозным рабочим путём: единый источник устройств (сервис устройств + постоянное хранилище вместо временного словаря в роутах), одна транзакция жизненного цикла (манифест → хранилище → машины состояний → маршрутизация событий → аудит), починенный мастер поиска (реальные данные источника, рабочее применение, идентификация запросов) и удаление устройства с полным каскадом. Устройство начинает работать сразу после добавления, без перезапуска.

**Технический подход** (решения и обоснования — в [research.md](./research.md)): новый сервис жизненного цикла в слое `services/`, точечное создание/снятие машин состояний через существующие публичные API движка, публичный `rebuild()` у маршрутизатора событий, реализация данных мастера через уже работающий `HARestClient`, серверная идентичность интерфейса по умолчанию.

## Technical Context

**Language/Version**: Python 3.14 (проект на 3.11+; CI — ubuntu-latest, локально 3.14)

**Primary Dependencies**: FastAPI, Jinja2 + htmx 1.9 (WebUI), Pydantic v2, loguru, aiohttp, watchdog, uvicorn

**Storage**: JSON-файлы в каталоге данных (`data/devices.json`, `data/device_access.json`, `data/device_sync_events.json`, `data/state.json`) + YAML-манифест экземпляра; миграции в `src/core/persistence/migrations/`

**Testing**: pytest (+ pytest-asyncio в режиме auto), pytest-cov, mypy --strict, ruff, interrogate; Playwright — отдельно (Known Issue #13)

**Target Platform**: Linux-сервер (Docker), автономный режим и режим Home Assistant; локальный запуск без Home Assistant тоже поддерживается

**Project Type**: web-service (WebUI + REST API) с event-driven ядром

**Performance Goals**: добавленное устройство реагирует на событие датчика не позднее 10 секунд без перезапуска; список устройств отдаётся за <200 мс при 100 устройствах; перестроение маршрутизации событий <50 мс

**Constraints**: неприкосновенны `FSMDefinition`, логика дебаунса и механизм таймаутов (конституция, принцип I); слои: `core` не знает об `adapters`, `services` не знает о `adapters`; все публичные функции — type hints + docstring Google-style; функции ≤50 строк; покрытие нового кода ≥80%, критических модулей ≥95%; запрещены bare `except`, правила констант

**Scale/Scope**: один дом (десятки-сотни устройств), один пользователь-администратор WebUI (модель ролей — «зритель/контролёр/администратор»), 1 экземпляр, 1–2 источника Home Assistant; затрагиваемые модули: webui-роуты устройств/источников, мастер discovery, сервис устройств, фабрика/движок FSM, маршрутизатор событий, шина событий, шаблоны WebUI

## Комплексность (волны реализации)

Волны упорядочены так, чтобы каждая давала работающий результат и могла быть задеплоена отдельно; каждая волна закрывает соответствующую пользовательскую историю.

| Волна | Содержание | Истории | Требования |
|---|---|---|---|
| **Волна 1. Единое хранилище и полный CRUD** | Гидратация при старте; публичные операции со списком/добавлением/удалением в сервисе устройств; роуты читают и пишут через сервис; удаление временного словаря; удаление дубля `/apply`; прокси в менеджере хранения; обновление 4 тестовых фикстур | US1, US4 | FR-001…008, FR-024…027, FR-003, FR-004 |
| **Волна 2. Сервис жизненного цикла и мгновенное оживление** | Новый `DeviceLifecycleService` (транзакция + компенсация); точечное создание/снятие машин состояний; `EventRouter.rebuild()`; отписка от подписок с фильтром; подключение адаптера к сервису устройств; UI-форма и `/apply` через сервис; удаление `_hot_reload_fsm` | US1, US2 | FR-014…018, FR-028, FR-029, FR-005…007 |
| **Волна 3. Мастер поиска** | Реальные данные через `HARestClient`; форма создания источника; переключение мастера на рабочие данные; применение выбранного; идентификация запросов; чистка мёртвого JS; соответствие категорий и шаблонов бэкенду; корректные сообщения об ошибках | US2 | FR-009…013, FR-030 |
| **Волна 4. Согласованность синхронизации** | Список после синка; дедупликация; политика исчезнувших устройств; фиксация ошибок без потери данных; проверка сценария автономного режима | US3 | FR-019…023 |

Критический путь: Волна 1 → Волна 2. Волны 3 и 4 могут идти параллельно после Волны 2 (разные файлы: `routes/sources.py` + шаблоны против `device_service.py`/sync-политики), но в текущей сессии выполняются последовательно из-за пересечения по `routes/ddevices/sources.py` в тестах.
