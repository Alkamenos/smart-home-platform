# Research: Device Lifecycle (жизненный цикл устройства)

**Feature**: specs/006-device-lifecycle
**Дата**: 2026-09-30
**Источники фактов**: код репозитория (три параллельных исследования: хранилища устройств, механизм FSM, мастер discovery + UI), конституция v3.0.0, ответы пользователя на три вопроса.

---

## Установленные факты (сжато)

**Три несвязанных мира устройств:**

| Мир | Где | Кто пишет | Кто читает |
|---|---|---|---|
| In-memory словарь | `src/webui/routes/devices/devices.py:27-28` | только `apply_devices` (недостижим) и тестовые фикстуры (4 файла) | `GET /api/v1/devices`, `GET/PUT /{id}*` (`:125,162,216,373,441,531`) |
| `DeviceService` + `data/devices.json` | `src/webui/app.py:300-304`, `src/core/persistence/devices.py:33` | только `sync_devices_from_source` (`device_service.py:126-132`) | ничего в webui, кроме `get_user_accessible_devices` (`:129` для фильтрации) |
| YAML-манифест | `instances/leonids_house/manifest.yaml` | `/devices/save` (`app.py:713-826`), discovery (`discovery_service.py:241,339`) | `Container.build()` → фабрика FSM; `GET /` |

**Ключевые блокеры (подтверждены):**
- `POST /api/v1/devices/apply` обрабатывается функцией `get_devices` (первый зарегистрированный дубль `:99`), настоящий `apply_devices` (`:585`) недостижим; UI читает `.success` у списка → всегда «Ошибка при применении» (`discovery.html:1161,1169`).
- `GET .../discovery-data` (`sources.py:329-375`) — вечная заглушка: TODO на месте, HA не опрашивается, всегда `available_device_count: 0`.
- Ни один запрос UI к `/api/v1/**` не несёт `X-User-ID` (`discovery.html:432,661,1118,1152`) → 401 на трёх из четырёх (`middleware_access_control.py:71-79`).
- Гидратации устройств при старте нет: `DeviceService._devices` пуст до первого синка; `load_all_devices` из `src/` не вызывается.
- `DeviceService` не умеет ни добавить одно устройство, ни удалить; `persistence.devices.delete_device` (`:140`) и `delete_accesses_for_device` (`:458`) существуют, но не вызываются и не имеют тестов.
- FSM создаются только в `Container.build()` (`container.py:221`); точечные примитивы есть (`factory.create_from_behavior` `:278`, `engine.unregister` `:515`, `register_definition` `:133`), но оркестратора нет; ни один роут webui не упоминает FSM.
- `EventRouter`: маппинг строится один раз в конструкторе (`event_router.py:43-65`), публичного `rebuild()`/`remove_mapping()` нет, удалить маппинг нельзя.
- `EventBus.unsubscribe` (`:29-35`) не трогает `_filtered_subscribers` (`:54`) → подписки фабрики по `motion_sensor` неудаляемы, повторное создание даёт дубли обработчиков.
- `_hot_reload_fsm` (`discovery_service.py:357-393`) падает на несуществующем `event_router.add_mapping` (`:389`), исключение проглочено → `success: true` при незавершённом reload.
- `discovery.html` содержит 540 строк мёртвого JS вне `<script>` (`:1216-1755`) — дубли всех 19 функций.
- `MockAdapter` не имеет `is_connected` → `scan_devices` через WS-адаптер падает в mock/standalone-режиме (`discovery_service.py:68`).
- `Container.build()` — **синхронный** (`container.py:203`), вопреки одному из пунктов исследования; расхождение отброшено.

## Решения

### D-001. Единый источник устройств — `DeviceService` + persistence
**Решение**: in-memory словарь роутов удаляется; все операции чтения/записи устройств идут через `DeviceService`, который работает поверх постоянного хранилища.
**Обоснование**: решение пользователя; подтверждено исследованием — список пуст после каждого рестарта, а два других мира не видны интерфейсу.
**Альтернативы**: (а) манифест как единственный источник — отклонено: манифест хранит конфигурацию, а не runtime-состояние (состояние/доступность/время обновления); (б) оставить in-memory словарь и писать в него из всех путей — отклонено: данные теряются при рестарте, дублируются два хранилища.
**Следствие**: 4 тестовые фикстуры (`tests/contract/test_devices_api.py:114`, `tests/contract/test_device_events_api.py:40`, `tests/integration/test_device_config.py:44`, `tests/integration/test_device_audit_log.py:32`) переводятся на посев через `DeviceService`/persistence.

### D-002. Гидратация при старте — явный вызов
**Решение**: `DeviceService.hydrate_from_persistence()` вызывается один раз при создании приложения (там же, где создаются persistence и сам сервис, `src/webui/app.py:294-308`), до первого запроса.
**Обоснование**: `load_all_devices` уже есть (`persistence/devices.py:98`), но никем не вызывается; без гидратации FR-001/FR-019 не выполняются.
**Альтернативы**: ленивая загрузка при первом чтении — отклонено: неявное поведение, трудно диагностировать и тестировать.

### D-003. Один путь добавления/изменения/удаления — сервис жизненного цикла
**Решение**: новый `DeviceLifecycleService` (слой `services/`) — единственная точка, которая выполняет транзакцию: манифест → постоянное хранилище → `DeviceService` (кэш/индекс) → машины состояний → перестроение маршрутизации событий → событие аудита. И UI-форма (`/devices/save`), и REST-применение (`/api/v1/devices/apply`) вызывают только его.
**Обоснование**: сейчас логика расползлась по трём местам (роут манифеста, discovery-сервис, apply роут); без единой точки идемпотентность (FR-008) и атомарность (FR-004) недостижимы.
**Альтернативы**: (а) логика в роутах — отклонено: дублирование между формой и мастером; (б) через файловый наблюдатель манифеста — отклонено: наблюдатель реагирует на файл асинхронно, не даёт ответа и транзакции; в проекте он по умолчанию выключен.

### D-004. Мгновенное оживление — только публичный API движка
**Решение**: при добавлении/изменении устройства для каждого поведения вызывается `FSMFactory.create_from_behavior()`, затем `engine.unregister(entity_id)` (если FSM уже был) и `engine.register_definition(def, restore_state=False)`. При удалении — `engine.unregister` для всех сущностей устройства.
**Обоснование**: эти методы уже покрыты тестами (`tests/test_fsm_factory.py:276-290`, `tests/test_hot_reload_memory.py:56-239`) и работают вне event loop; структура `FSMDefinition`, дебаунс и механизм таймаутов не затрагиваются (конституция, принцип I).
**Альтернативы**: (а) `restore_state=True` из потока UI — отклонено: ветка восстановления состояния вызывает `get_event_loop()` без защиты (`engine.py:153`) и падает вне основного цикла; (б) правка дебаунса/таймеров в `register_definition` — отклонено: запрещено конституцией без отдельного согласования; (в) пересоздать весь `Container` — отклонено: рвёт ссылки адаптера и шины.

### D-005. Перестроение маршрутизации — новый публичный `EventRouter.rebuild()`
**Решение**: добавить публичный `rebuild(manifest)`, который очищает маппинг и строит его заново из переданного актуального манифеста; вызывается сервисом жизненного цикла после любого изменения состава устройств.
**Обоснование**: сейчас маппинг строится один раз из ссылки на объект манифеста (`event_router.py:38,43-65`), удалить его нечем — осиротевшие записи остаются навсегда. Полный пересчёт дешёв (манифест мал) и устраняет все классы рассинхрона.
**Альтернативы**: (а) точечные `add_mapping`/`remove_mapping` — отклонено: больше кода, риск частичного рассинхрона; (б) создавать новый `EventRouter` — отклонено: адаптер уже держит ссылку, метода переприсвашения у `HAAdapter` нет.

### D-006. Источник данных для мастера — `HARestClient` конкретного источника
**Решение**: реализовать заглушку `discovery-data` через уже рабочий путь `HARestClient` (`connect_to_ha` → `fetch_devices` → `fetch_areas`), тем же кодом, что использует `sync_devices_from_source` (`device_service.py:103-116`). Мастер ходит в `/api/v1/devices/sources/{id}/discovery-data`.
**Обоснование**: работает в автономном режиме и с источниками, созданными в интерфейсе; не требует WebSocket-соединения и `HA_TOKEN`; переиспользует покрытый код. Вариант через WS-адаптер (`POST /discovery/scan`) падал бы в mock/standalone-режиме (`is_connected` отсутствует у `MockAdapter`).
**Альтернативы**: (а) чинить `scan_devices` и перевести мастер на него — отклонено: нужен живой WS, глобальный, привязанный к env, а не к выбранному источнику; (б) поддерживать оба пути — отклонено: двойная логика и два контракта.

### D-007. Каноническая точка применения — `POST /api/v1/devices/apply`
**Решение**: удалить дублирующийся декоратор, оставить одну реализацию; она принимает выбранные устройства, дедуплицирует по `ha_entity_id`, пишет манифест через `ManifestStore` (а не сырым YAML) и вызывает сервис жизненного цикла. Роут `/discovery/apply-selective` остаётся для CLI, но перестаёт быть отдельным источником правды: его запись манифеста переводится на `ManifestStore`.
**Обоснование**: это уже адресуемый мастером адрес, и он же обслуживает UI-форму.
**Альтернативы**: перевести мастер на `/discovery/apply-selective` — отклонено: этот путь пишет YAML в обход `ManifestStore` (UI-состояние устаревает, «Reload» откатывает результат) и не интегрирован с FSM и правами.

### D-008. Идентификация пользователя в интерфейсе — серверная по умолчанию
**Решение**: сервер передаёт в шаблоны идентичность по умолчанию (источник: переменные окружения `WEBUI_DEFAULT_USER_ID` / `WEBUI_DEFAULT_USER_ADMIN`, значения по умолчанию — `admin_user` / `true`), а общий скрипт в базовых шаблонах добавляет `X-User-ID` и `X-Is-Admin` ко всем запросам (перехват `fetch` + обработчик `htmx:configRequest`).
**Обоснование**: в проекте нет ни аутентификации, ни сессий; требование FR-009 — чтобы запросы интерфейса не отклонялись, а не чтобы появилась полноценная система прав. Идентичность должна быть настраиваемой, а не зашитой в шаблон.
**Альтернативы**: (а) хардкод в шаблоне — отклонено: не настраивается и дублируется в каждом шаблоне; (б) полноценная аутентификация — вне объёма (не заявлена в спеке).

### D-009. Источник для устройства, добавленного вручную — обязательный выбор
**Решение**: форма добавления требует выбора источника (список из `GET /api/v1/devices/sources`); пустой выбор → отказ с понятным сообщением.
**Обоснование**: у модели устройства `source_id` обязателен, а источник нужен для команд, синхронизации и прав.
**Альтернативы**: создавать скрытый «ручной» источник — отклонено: искусственные записи в данных и двусмысленность при синхронизации.

### D-010. Устройство, исчезнувшее из источника — пометка, не удаление
**Решение**: при синхронизации устройство, отсутствующее в источнике, получает статус `removed_from_ha` (значение уже заложено в модель и миграции), исключается из активной автоматики (машины состояний снимаются), но его конфигурация и права сохраняются; при повторном появлении статус возвращается в `available`.
**Обоснование**: FR-022 требует явного поведения; удаление потеряло бы настройки пользователя.
**Альтернативы**: (а) молча оставлять — отклонено: нарушает FR-022 и оставляет активную автоматику; (б) удалять — отклонено: потеря конфигурации.

### D-011. Удаление устройства — каскад с отзывом прав
**Решение**: удаление выполняется сервисом жизненного цикла: снятие машин состояний, отзыв всех записей о доступе (`delete_accesses_for_device`), удаление из постоянного хранилища, из кэша и индекса, запись в манифест, событие аудита. Отсутствие устройства → идемпотентный успех.
**Обоснование**: FR-025/FR-026; API персистентности уже есть, но не вызывается.
**Альтернативы**: оставить «зомби»-права — отклонено: удалённое устройство возвращалось бы в списки через записи о доступе.

### D-012. Порядок операций и компенсация
**Решение**: порядок «манифест → постоянное хранилище → runtime (кэш/индекс) → машины состояний → маршрутизация → аудит». При сбое на шаге хранилища манифест откатывается (в памяти, через резервную копию `ManifestStore`); сбой на шаге машин состояний не откатывает данные, а фиксируется событием с признаком частичного успеха — устройство остаётся в списке и не должно молча пропасть.
**Обоснование**: FR-004, FR-007, SC-002; принцип «контроль за пользователем» — данные пользователя не теряются.
**Альтернативы**: сначала runtime, потом манифест — отклонено: при сбое записи манифеста устройство «ожило» бы, но исчезло бы после рестарта.

### D-013. Идемпотентность подписок на шине
**Решение**: дополнить `EventBus` отпиской для подписок с фильтром (`unsubscribe_with_filter`) и научить `unsubscribe` обслуживать отфильтрованные подписки; сервис жизненного цикла отписывается перед повторной подпиской.
**Обоснование**: FR-008 (идемпотентность повторного применения) иначе нарушается: каждое повторное создание добавляет обработчик, и один и тот же датчик вызывает несколько триггеров.
**Альтернативы**: не трогать шину и не пересоздавать FSM при неизменных параметрах — отклонено: расхождение состояний манифеста и машин состояний не отслеживается, риск тихих ошибок.

### D-014. Порядок регистрации FSM-подписок в фабрике
**Решение**: не менять `factory._subscribe_to_sensor_events`; отписку выполняет вызывающий код (сервис жизненного цикла) по сохранённому дескриптору подписки.
**Обоснование**: фабрика не владеет жизненным циклом подписок и не знает, что устройство удалено.
**Альтернативы**: добавить в фабрику `unsubscribe_device(device_id)` — отклонено: потребует хранить дескрипторы подписок в фабрике, что усложняет её без выигрыша (подписка всегда одна на пару устройство+датчик).

### D-015. Что остаётся за рамками фичи
- `POST /discovery/scan` и `GET /discovery/stats` остаются как есть (CLI/совместимость), но UI их не использует.
- `ManifestAutomationGenerator`/`_hot_reload_fsm` перестаёт быть рабочим путём: функция удаляется, её роль переходит к сервису жизненного цикла (иначе остаётся мёртвый код, который вводит в заблуждение).
- Аудит: используется существующий журнал синхронизации устройств, добавляются типы событий жизненного цикла.
- `config_watcher` (горячая перезагрузка файла манифеста) не меняется: он остаётся отдельным механизмом для правки файла вручную; устройства, добавленные через интерфейс, обрабатываются сервисом жизненного цикла.

## Открытые технические моменты реализации (для tasks)

1. `Device` → `DeviceResponse`: у ответа есть поля `display_name`, `description`, `location`, `tags`, которых нет в модели устройства — они берутся из `device.config` (сейчас это делается вручную в роуте, `devices.py:171-178`).
2. `DeviceService` не имеет «получить все устройства» — нужен публичный метод списка; существующий `get_devices_by_source` кэширует выборку источника (`device_service.py:205`), новый список должен читать актуальное состояние индекса/кэша.
3. Запись в манифест: `ManifestStore` уже умеет откат (`app.py:76-161`), нужно использовать его API вместо прямой работы с YAML в `discovery_service`.
4. Тесты доступа: `_require_access_or_403` проверяет роль; для новых операций (добавление, удаление, применение) роль — администратор.
5. Аудит-события: `record_sync_event` уже используется в роутах (`devices.py:269`); переносится в сервис, чтобы все пути писали одинаково.
6. Покрытие: для новых файлов — не менее 80%, для критических модулей (движок, роутер) — не менее 95%; E2E мастера попадает в карантин playwright-файла, поэтому E2E-сценарии верифицируются через quickstart-ручной прогон, а автотесты — контрактные и интеграционные.
