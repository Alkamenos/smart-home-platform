# Quickstart — проверка веб-интерфейса «Дом»

Руководство для проверки результата. Не содержит реализации; ссылается на контракты и
модель данных. Сценарии упорядочены от автотестов к живой приёмке.

## Предусловия

- Python-окружение проекта установлено (`.venv`), зависимости — по `pyproject.toml`.
- Node 22+ и `pnpm` доступны (в проде не нужны — только для сборки и тестов фронта).
- Для сценариев без боевого дома: `MockAdapter` (не требуется HA).
- Для живой приёмки: доступ к платформе в LAN и боевой манифест.

## Сборка и запуск (dev)

```bash
# фронтенд: установка и сборка статики
make frontend-install
make frontend-build          # кладёт результат в frontend/out

# платформа (раздаёт собранный фронт и API на одном порту)
make run-webui               # http://localhost:8000
```

Ожидание: `/` открывает раздел «Дом», API доступно под `/api/**`, страницы живут без
обращения к внешней сети (проверяется отключением интернета).

## Сценарий 1 — «Дом» показывает состояние (US1, FR-007…FR-012)

1. Открыть `/`. Убедиться, что видны локации с показаниями и единицами, устройства с
   фактическим состоянием и состояниями автоматов, и блок тревог.
2. Изменить состояние датчика/света (в HA или через mock) и убедиться, что значение
   обновилось **без перезагрузки** страницы.
3. Сделать датчик недоступным (`unavailable`) — он показан как недоступный, а не пустым.
4. Проверить локацию с мёртвым датчиком движения: производное «присутствие» не выводится из
   недоступного датчика.

Критерий: SC-001 (состояние понятно за 10 с), SC-010 (нет выдуманных данных).

## Сценарий 2 — управление с откликом (US2, FR-013…FR-017)

1. На карточке устройства нажать включить/выключить: состояние отражается **немедленно**,
   затем подтверждается.
2. Повторить на недоступном приборе: показана причина ошибки, состояние не «залипает».
3. Отправить команду через автомат и напрямую: интерфейс явно сообщает, учла ли автоматика.
4. Быстро нажать кнопку несколько раз: лишние команды не уходят, интерфейс не зависает.

Критерий: SC-002 (отклик мгновенный), SC-003 (100% неудач с причиной).

## Сценарий 3 — причина и блокировки (US3, FR-018, FR-019)

1. Открыть устройство «не включилось»: видна причина человеческим языком и относительное
   время.
2. Включить ручную блокировку: видно, что автоматика не трогает прибор, и до какого времени.

## Сценарий 4 — журнал и диаграмма (US4, FR-020…FR-023)

1. Открыть `/journal`, дать прийти новым событиям: лента дописывается, список не
   перерисовывается целиком, прокрутка плавная при 1000+ записях.
2. Отфильтровать по устройству и по trace: показаны только подходящие записи, цепочка
   «событие → решение → команда → результат» прослеживается.
3. Открыть диаграмму автомата: текущее состояние подсвечено и меняется живьём.

Критерий: SC-004.

## Сценарий 5 — настройка (US5, FR-024…FR-027)

1. `/settings/sources`: подключить источник, увидеть сущности, импортировать одну, выполнить
   синхронизацию. Устройство появляется на `/` без перезапуска платформы.
2. `/settings/devices`: задать поведение и параметры; ошибка указывает конкретное поле.
3. **Регресс диалогов**: открыть и закрыть каждый диалог редактирования несколько раз —
   открывается всегда (проверка текущего дефекта «модалки не открываются»).

Критерий: SC-008.

## Сценарий 6 — диагностика (US6, FR-028, FR-029)

1. `/system`: видно готовность платформы, состояние источников, метрики, технические логи.
2. Отключить источник: в `/system` это отражено; состояние отличается от «в доме ничего не
   произошло».

## Сценарий 7 — интерфейс в целом (оболочка)

1. Пройти по всем пяти разделам: единая навигация и стиль, всё на русском (FR-002, FR-003).
2. Отключить внешнюю сеть: интерфейс полностью работоспособен (FR-005, SC-005).
3. Открыть на телефоне (ширина 360 px): ключевые сценарии выполнимы (SC-009).
4. Проверить, что старые страницы (`/dashboard`, `/discovery`, `/logs`) удалены, а вход ведёт
   в новый интерфейс (FR-030).

## Автотесты

```bash
# бэкенд: контрактные и модульные тесты новых маршрутов
pytest tests/unit/webui -q

# фронтенд: компоненты и клиенты
make frontend-test           # vitest + покрытие ≥ 80%

# E2E: сквозные сценарии на собранном фронте
pnpm --dir frontend test:e2e # playwright (frontend/tests/e2e)
```

Ожидание: все прогоны зелёные; старый `tests/test_webui_playwright.py` удалён.

## Живая приёмка (по завершении)

Повторить сценарии 1–6 на боевом доме: убедиться, что показания совпадают с HA, тревоги
соответствуют реальным молчащим/недоступным датчикам, команды доходят и подтверждаются,
журнал восстанавливает ночные события по trace. Результат зафиксировать в
`.ai/01_PROJECT_STATE.md` (правило владельца: логика в документацию).
