# Phase 0 — Research: Веб-интерфейс инженера «Дом»

Дата: 2026-10-13. Все неизвестные из Technical Context разрешены; маркеров
`NEEDS CLARIFICATION` не осталось.

## R-01. Фронтенд-фреймворк

**Решение**: Next.js 15 (App Router) + React 19 + TypeScript, сборка в статику
(`output: 'export'`).

**Обоснование**: нужен современный, поддерживаемый интерфейс с роутингом и экосистемой
готовых компонентов; владелец склонялся к Next.js. Режим статического экспорта убирает
потребность в Node-рантайме в проде и в SSR, который для LAN-инструмента не даёт ничего.

**Альтернативы**: Vite + React SPA (то же по сути, но без App Router — отклонено в пользу
единообразия с выбором владельца); Next.js в режиме SSR/standalone (лишний Node в проде);
остаться на Jinja+HTMX (отклонено в Complexity Tracking плана).

## R-02. Способ раздачи фронтенда

**Решение**: FastAPI раздаёт `frontend/out` через `StaticFiles(html=True)` на `/`; все
API- и служебные маршруты (`/api/**`, `/health`, `/metrics`, `/ready`, `/api/v1/ws/**`)
регистрируются **раньше** монтирования статики и потому имеют приоритет. Неизвестные пути
не под API отдают SPA-оболочку (`index.html`) — SPA-фолбэк для глубоких ссылок.

**Обоснование**: один origin → нет CORS, cookie/заголовки передаются штатно, один контейнер,
сохраняется текущая топология compose.

**Альтернативы**: отдельный контейнер nginx (правка compose, два origin); отдельный порт
(усложняет доступ из LAN). Отклонены.

## R-03. Идентичность и доступ

**Решение**: модель доступа не меняется — заголовки `X-User-ID`/`X-Is-Admin`, заполняемые
прокси-слоем/клиентом. Добавляется `GET /api/v1/session`, возвращающий идентичность и права
текущего запроса; фронтенд читает её один раз при загрузке и прикладывает заголовки ко всем
запросам и к WS-авторизации.

**Обоснование**: сейчас идентичность зашивается серверным рендером в атрибуты `<body>`; в
SPA этого нет, нужен явный bootstrap. Значения по-прежнему приходят из запроса — доверие к
клиенту сохраняется как принятое проектное решение (B5, развёртывание в LAN).

**Альтернативы**: вводить настоящую аутентификацию — вне объёма по решению владельца.

## R-04. Получение данных и кэш

**Решение**: TanStack Query на клиенте: ключи по ресурсам (`['overview']`,
`['locations']`, `['devices']`, `['device', id]`, `['events', filters]`), разумные
`staleTime`, инвалидация после мутаций. Никакого собственного глобального стора, кроме
Query-кэша и лёгкого React-контекста для темы/идентичности.

**Обоснование**: даёт отмену запросов, повтор, оптимистичные мутации (нужны для FR-014) и
единообразную обработку загрузки/ошибки без ручного кода.

**Альтернативы**: SWR (близко, но слабее по оптимистичным мутациям и инвалидации); ручной
fetch-менеджер (отклонено — больше кода и ошибок).

## R-05. Живые обновления (локации, устройства, автоматы)

**Решение**: вводится унифицированный канал `WS /api/v1/ws/events` с типами сообщений
`auth`, `subscribe` (по темам: `locations`, `devices`, `fsm`), `revoke` и серверными
`state_change` (показания датчиков/сущностей), `fsm_transition`, `device_state`. Права
проверяются при **каждой** доставке (как в существующем `/api/v1/ws/devices`). Существующий
`/api/v1/ws/devices` сохраняется на время перехода и затем удаляется.

**Обоснование**: FR-012 требует живых показаний локаций, а сегодня их источник
(`state_change` шины) наружу не отдаётся вовсе; device-канал покрывает только автоматы и
подписку по устройствам. Один канал проще и дешевле для клиента.

**Альтернативы**: второй отдельный канал для датчиков (два соединения, дублирование кода);
периодический опрос (противоречит «без перезагрузки и без ручного обновления» и создаёт
нагрузку). Отклонены.

**Риск**: широковещательная шина `state_change` может быть шумной (поток показаний). Мерило:
фильтровать по темам подписки и по правам; не отправлять то, что клиент не запросил.

## R-06. Агрегат для первого экрана

**Решение**: `GET /api/v1/overview` возвращает одним ответом: список локаций со снимками,
устройства с фактическим состоянием и состояниями автоматов, и вычисленные тревоги.
Права применяются так же, как в существующих чтениях (устройства — по доступу, локации —
агрегированное наблюдение).

**Обоснование**: FR-007…FR-011 и SC-001 требуют быстрого первого экрана; 3–4 параллельных
запроса на старте дают «водопад» и мерцание. Агрегат — один заход и один стабильный скелет.

**Альтернативы**: собирать экран на клиенте из существующих endpoint'ов (проще, но медленнее
и с мерцанием). Решение: агрегат — для «Дома», остальные разделы используют существующие
ресурсные endpoint'ы.

## R-07. Тревоги (молчание, недоступность, расхождение)

**Решение**: тревоги вычисляются на сервере из уже имеющихся данных и отдаются в
`/api/v1/overview`: молчащий датчик (`stale`), недоступная сущность (`unavailable`),
расхождение «автомат считает прибор включённым — прибор выключен» (источник — данные
сторожа вентиляции, если доступны; иначе правило выводится из состояния автомата и
фактического состояния прибора).

**Обоснование**: у наблюдателя локаций уже есть признаки `stale`/`unavailable` (спека 016),
а расхождение — уже известный класс дефектов (B54/B55). Вычисление на сервере даёт единую
правду для всех клиентов.

**Альтернативы**: считать на клиенте (разные правила на разных экранах, дублирование).

## R-08. Журнал без тормозов

**Решение**: `GET /api/v1/events` с фильтрами `device`, `location`, `level`, `trace`,
`from`/`to`,`limit` и курсором пагинации; на клиенте — виртуализированный список
(`@tanstack/react-virtual`) и добавление новых событий в начало без перерисовки существующих
узлов.

**Обоснование**: сегодня `/logs` тянет 1000 записей и перерисовывает всё каждые 2 с (B29).
Виртуализация и инкрементальное добавление снимают длинные задачи (SC-004).

**Альтернативы**: оставить перерисовку (противоречит SC-004); постраничная навигация без
живого хвоста (теряется смысл «наблюдать»).

## R-09. Диаграмма автомата

**Решение**: переиспользовать существующий `GET /api/fsm/{entity_id}/diagram` (готовая
Mermaid-строка); рендер `mermaid` на клиенте с подсветкой текущего состояния из живого
канала.

**Обоснование**: контракт уже есть и отдаёт чистый Mermaid (исправлено в спеке 007);
дублировать генерацию схемы не нужно.

**Альтернативы**: собственная отрисовка (лишняя работа, потеря совпадения со схемой FSM).

## R-10. Дизайн-система и облик

**Решение**: Tailwind CSS + shadcn/ui (Radix), тёмная тема по умолчанию, локальные шрифты;
ориентир — современный SaaS-дашборд (чистая типографика, спокойные поверхности, акцент
только на важном). Русский язык интерфейса, единственная локаль.

**Обоснование**: выбор владельца; shadcn/ui копируется в репозиторий (не CDN), доступен и
кастомизируем без зависимости от внешних сервисов.

**Альтернативы**: готовая компонентная библиотека целиком (тяжелее, труднее кастомизировать);
собственная с нуля (дольше, хуже доступность).

## R-11. Замена старых браузерных тестов

**Решение**: `tests/test_webui_playwright.py` (32 теста старого UI) удаляется; вместо него —
`frontend/tests/e2e` (Playwright) на новый интерфейс, запускаемый отдельной целью Makefile.

**Обоснование**: тесты проверяют HTML старого серверного рендера, которого больше не будет.

**Альтернативы**: адаптировать существующие — невозможно, разметка и механика меняются
целиком.

## R-12. Сборка и деплой

**Решение**: multi-stage `deploy/docker/Dockerfile`: стадия `node` собирает
`frontend/` → `out/`; стадия `python` копирует `out/` в образ. В рантайме Node нет.
`Makefile`: `frontend-install`, `frontend-build`, `frontend-test`, `dev-frontend`.
`docker-compose.prod.yml` — без изменения топологии (при необходимости только build-аргумент).

**Обоснование**: сохраняет один контейнер и текущую процедуру развёртывания; статика
поставляется с образом, интернет не нужен.

**Альтернативы**: сборка на хосте и копирование `out/` (ручной шаг, рассинхрон);
отдельный сервис (см. R-02).

## R-13. Система качества фронтенда

**Решение**: eslint (next/core-web-vitals) + `tsc --noEmit` + prettier + Vitest в
pre-commit **только для изменений в `frontend/`** (через фильтр путей), Playwright — в
pre-push/CI по отдельной цели. Покрытие нового кода ≥ 80% (Vitest coverage).

**Обоснование**: конституция требует TDD и качества; фронтенд — новая зона, ей нужны
зеркальные проверки, но полный прогон фронта на каждый коммит замедлил бы работу.

**Альтернативы**: гонять всё всегда (медленно); не проверять фронт (нарушает принцип II).
